# UX03 engine write contract — source-only proposal (2026-09-27)

Scope: a future deterministic Copy Settings write for the already merged pure `BatchSettingsDraft`; no backend/UI implementation or validation run is claimed here. Repository: `/Users/rutmehta/Developer/tessera`, main `4f7813d2`. Keep this a per-photo sidecar transaction inside the app process, not a general history framework.

## Actual writers and collision surface

* `crates/tessera-ffi/src/lib.rs:390-446`: `set_selection` and `set_recipe_json` read a `RecipeDocument`, call `record_write`, then `persist` under the **Engine catalog mutex**. `persist` writes authoritative recipe first, then XMP, then rebuildable index (`:257-277`). `set_recipe_json` checks append-only history prefix and copies unknown recipe fields, but does not compare a complete old revision; a stale caller may replace current settings/head/selection while passing that check.
* `crates/tessera-ffi/src/develop.rs:823-910,919-949,1196-1245,2424-2430`: an opened Develop session owns a local recipe; commit schedules a debounced writer. `save_develop` takes the catalog mutex and overlays **settings, history, process version, source kind** from that local snapshot onto the latest document before recipe/XMP/index writes. It preserves current selection/unknown fields, but a save after batch would overwrite the batch settings/history. `DevelopController.close()` flushes then awaits the backend close (`apps/mac/Sources/TesseraCore/DevelopController.swift:156-174`); `AppModel.pendingDevelopSaveBarrier` waits tracked opens/closes, not every live session or arbitrary FFI caller (`AppModel.swift:1019-1027`). A write mutex alone does not solve this stale-snapshot race.
* `crates/tessera-ffi/src/agent_runs.rs:451-475,576-740`: `run_agent` invokes `agent.edit` per image and later resyncs XMP/index. The agent and MCP console write recipe directly in `crates/agent/src/lib.rs:280-281,333-334` and `crates/tessera-mcp/src/console.rs:216-217`; provenance/status changes use `update_agent_extension`, also writing recipe before `resync`. These do **not** hold the Engine catalog mutex across the edit. `AgentController.isMutating` has host-side image/source ownership checks (`AgentController.swift:90-120`) but is not an engine write exclusion.
* Also recipe writers: `crates/tessera-ffi/src/lrcat.rs:1303-1331` import, `crates/tessera-ffi/src/merge.rs:381-382` new output, and Culling selection via `crates/cull/src/persistence.rs:144-170` (`tessera-ffi/src/session.rs` uses Culling). `crates/style-profile/src/library.rs:158-159` and standalone MCP may write sidecars outside this Engine path. XMP-only metadata in `tessera-ffi/src/metadata.rs:229` does not change an existing recipe but is relevant when a recipe is absent and `catalog::document` falls back to XMP (`catalog.rs:15-35`). `agent_runs.rs:451-463` resync writes XMP/index from a recipe and must not overtake a recipe mutation. These are inventory items, not evidence that the current app already serializes them.
* `RecipeDocument` includes recipe, vector clock and last writer (`crates/sidecar/src/lib.rs:68-109`); `Sidecar::write_recipe` atomically replaces it (`:160-165`). `Recipe::recipe_hash` intentionally includes only render state and excludes history, selection, IDs and unknown fields (`crates/engine-api/src/recipe/mod.rs:293-303`), so it is unsuitable as a write revision or ABA guard.

## Smallest safe in-process contract

1. Add one recipe-write coordinator in `tessera-ffi`, shared by all `Engine::open` instances **in this process**, keyed by the canonical resolved recipe sidecar path plus a resolved source-file identity. Resolve the indexed image ID to its current path again under admission. Normalize symlinks; use device/inode when available to detect a source/reference/target alias even when image IDs differ. Since sidecars are derived from image path/stem, two aliases may address different sidecars: reject ambiguous source/target or target/target aliases for this operation instead of silently treating them as independent. Fail closed if identity cannot be checked consistently. A bounded weak-lock table or keyed token with cleanup avoids a growing map. Fix lock order as per-photo gate, then catalog mutex; never acquire a gate while holding catalog. Multi-target batch writes acquire only **one** target gate at a time in frozen order.
2. Route every recipe mutation the app can run concurrently with batch through that gate: Engine `set_selection`/`set_recipe_json`/Develop save/Agent per-image edit through final resync and extension changes/Culling selection. Import and new-output publication should at least reject or use the gate for an existing target path. Agent's tool-level writes happen inside `agent.edit`; hold its target gate for that entire per-image call rather than wrapping only its final resync. The coordinator cannot cover a separate MCP process, independent cull CLI, or a third-party editor. A standalone style-profile write in the same process must join before claiming a general app-process guarantee. Audit all `Sidecar::write_recipe` sites again when implementing; do not expose batch Apply until the active-app paths are covered.
3. At preview/admission, freeze source recipe/settings, selected paths, image IDs, canonical identities and a **complete target revision**. Revision should record sidecar existence and a digest of the exact on-disk recipe document bytes (whole recipe including settings/history/head/snapshots/groups/selection/IDs/unknown fields, vector clock and writer stamp), plus exact fallback XMP bytes when no recipe exists; do not use `recipe_hash`, mtime or JSON normalization alone. Include a coordinator monotonic epoch for in-process ABA, and validate image ID/path identity again at Apply. Preserve all existing recipe/envelope members in the output: `RecipeDocument` currently has no envelope-unknown flatten field, so either make round-trip retention explicit or reject unknown envelope members in this first slice. No forced overwrite on mismatch.
4. For each target Apply: acquire its gate; reject if a Develop session for that canonical source is open, has pending/debounced save, is closing or draining (tracked by backend session lifecycle, not just a Swift view flag); read target bytes and compare full revision/epoch; validate captured source/target alias and library owner; construct selected absolute patch against **current target** settings, retaining excluded nested fields; append one Sync history entry; advance `record_write`; commit recipe then XMP/index under the existing catalog path; release gate. Unchanged is explicit and makes no history entry. A stale revision returns a typed conflict with no write. Do not block a user editing session indefinitely to obtain a batch slot: skip/conflict and let a later preview retry. The source snapshot must already be frozen, so never reread the source midway through the run.
5. Gate all backend Develop opens and saves with the same identity check. Register the session as active before releasing its open gate; keep it active through final `flush`/writer drain, then unregister on all error/Drop paths. Batch rejects active or draining sessions. This avoids the dangerous interval where batch writes after the check but before an older debounced save. Host `pendingDevelopSaveBarrier` remains useful for UI flow but is not the backend correctness primitive. Maintain gate->catalog order and avoid waiting on Develop's writer while holding the gate.

This is per-image **in-process** exclusion only. Exact-byte recheck catches an external edit already present at Apply, but an external process can write between that check and our atomic replace; atomic rename is not filesystem compare-and-swap. A cross-process lock/protocol or explicit conflict/merge mechanism is separate work. XMP/index may fail after authoritative recipe commit, so report committed-with-resync-error and repair index rather than claiming transaction rollback. Neither coordinator nor revision token serializes unrelated files or process lifetimes.

## Durable run and revert dependency (design, not first slice)

`Author::Sync { from }` has no run ID; `HistoryGroup` only has id/name (`crates/engine-api/src/recipe/history.rs:20-42,131-139`). Add an optional, schema-versioned `run_id` to Sync edit metadata or a typed history extension (serde default for old recipes), with source image/library identity and selected path set in a durable run record. Do not encode identity only in a display label or volatile Swift queue. Create a UUID run record under isolated app support **before** target writes, store frozen source/settings/paths and per-target expected revision/status, then update it atomically after each authoritative recipe commit. Recipe entry must carry the same run ID so relaunch can reconcile ledger-vs-sidecar interruption. Store no user catalog data in test app support. UUID uniqueness and duplicate-apply idempotence are checked per target.

Revert is a later engine operation, not agent group disable: verify exact run ID/source/entry, target branch reachability and current full revision under the same gate. Reconstruct the current lineage with only that run's Sync changes omitted, replay later entries where their JSON-pointer patches remain meaningful, and append a **new ordinary compensating history edit** to the resulting settings; do not move head backwards or replace the whole document. Because history diffs can replace an entire array/scalar and later absolute edits may overlap a copied path, detect overlap/structural conflicts and report per-target conflict instead of guessing intent. Preserve later manual changes and unknown fields. A second revert of the same run is idempotent; overlapping batch runs or off-lineage Sync entries require explicit conflict tests. `History` entries are immutable and per-image; a run ledger is not a substitute for sidecar provenance.

## Bounded first implementation slice and tiny tests

First slice should be **backend admission plus one checked target write**, with no new UI, multi-photo orchestration or revert claim: coordinator + canonical identity, active Develop lease, exact full revision snapshot/compare, selected-path patch, one run-tagged Sync entry, and typed `applied/unchanged/conflict/develop_busy/error` result. Gate the listed active-app mutation paths before exposing the API. Keep run ledger implementation in the next slice if durable run ID schema/commit reconciliation is not ready; do not ship an Apply UI until both are ready.

Tiny generated sidecar tests (no RAW decode or GPU):

1. Three images: frozen source plus two targets; copy Tone only. Assert exact selected fields change, crop/local masks/history/selection/unknown recipe members and envelope clock retain semantics, source and unrelated target stay byte-identical; one Sync entry has source/run ID.
2. Two recipes with identical render hash but different history head, selection, unknown field or writer clock: an expected revision from one conflicts against the other. Existing-sidecar and absent-sidecar/XMP fallback cases; a same-process edit-and-restore of bytes is caught by epoch.
3. Deterministic barrier: pause a Develop writer before its debounced save; batch sees active/draining and writes nothing, then close/flush completes and a fresh preview can apply. Reverse ordering: batch gate first, a Develop open cannot snapshot stale state and later overwrite it. No sleeps.
4. Deterministic Agent tool and Culling selection interleavings: gate acquired around their actual sidecar writes; batch either commits before and makes later checked writes see new revision, or reports conflict, never silent lost update. Include `set_recipe_json` stale-history-prefix case. Lock-order test with two targets and concurrent opposite-order operations shows no deadlock.
5. Symlink/hardlink aliases and path replacement: source-to-target alias and two target aliases reject, including distinct IDs and derived sidecar names. Missing/unresolvable identity rejects rather than proceeding on a guessed key.
6. Inject XMP/index failure after recipe replace: result records authoritative recipe committed and retry/resync repairs the derived state. Inject failure before recipe replace: no Sync entry or run-target success. Later ledger tests cover interruption between recipe commit and ledger update, relaunch reconciliation, duplicate apply and run-specific revert after a later manual edit plus an overlapping-path conflict.

Acceptance for this first slice is narrow: one checked in-process target mutation cannot silently erase an app-originated edit or pending Develop save. It is not cross-process CAS, a batch UI, a durable multi-target run, or a proven lossless merge with arbitrary external sidecar writers.
