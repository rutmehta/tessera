# Exported JPEG reopen: active develop settings are reapplied

Source-only audit, 2026-09-27, `/Users/rutmehta/Developer/tessera` main `4f7813d2`. Inspected the disposable `/tmp/tessera-raw-edit-smoke-20260927/export/sony-arw.jpg.xmp` and source XMP; no build, GUI or product change. Root observed the exported JPEG pixels look correctly developed once. The finding below concerns **later catalog reopen**, not the initial output pixels.

## Verified flow

1. `crates/tessera-ffi/src/export.rs:803-816,1182-1205` reads the source recipe and XMP, then passes both to export. `crates/export/src/lib.rs:205-232,568-640` renders the recipe settings into output pixels. Default export metadata policy is `Metadata::All` (`:145-151`). `metadata_packet` keeps the source XMP's CRS development properties under that policy (`:901-935`); its filter removes none of those properties for `All` (`crates/sidecar/src/export_policy.rs:187-295`). `crates/export/src/lib.rs:665-676` strips development instructions **only for DNG**. The returned packet is embedded in the JPEG and written to an adjacent `.jpg.xmp` (`:690-734`).
2. The disposable output sidecar actually contains `<crs:Exposure2012>0.10000000149011612</...>`, `<crs:Temperature>5132.2841796875</...>`, `<crs:Tint>3.448204755783081</...>` and `ts:ExportHash`, matching the source RAW XMP. The output folder has `sony-arw.jpg` and `sony-arw.jpg.xmp`, with no `.edits/sony-arw.json` recipe. `ExportHash` is a CRS edit detector/native revision companion (`crates/sidecar/src/develop.rs:34-74,205-230`); it does not say that JPEG pixels already contain those edits.
3. When that JPEG is indexed and opened, `catalog::document` checks for a recipe first, then reads `.jpg.xmp` and calls `to_recipe()` if no recipe exists (`crates/tessera-ffi/src/catalog.rs:15-35`). `XmpPacket::to_recipe` decodes the CRS values into active `DevelopSettings` and records an `Import XMP` history edit (`crates/sidecar/src/develop.rs:80-137`). `Engine::open_develop_session` uses that recipe and opens the JPEG as RGB (`crates/tessera-ffi/src/develop.rs:823-837`; `crates/image-core/src/source.rs:53-66`). The RGB renderer applies its recipe white-balance matrix, then tone settings including exposure (`crates/pipeline-cpu/src/render.rs:202-225,382-397`). Thus the already-developed JPEG is developed again in Tessera on reopen. The same active recipe would be used by a later export of the indexed JPEG (`tessera-ffi/src/export.rs:803-816,1182-1205`). This conclusion follows from source flow and the inspected sidecar; a pixel-difference run was not performed.

## Scope and minimal repair direction

This is a **reopen contract bug for rendered exports that carry CRS settings**, especially the default Metadata::All JPEG shown. It does not imply that the initial JPEG output was rendered twice. A metadata-none export or a rendered output without a develop-bearing sidecar does not take this path. Other baked raster formats may have the same issue when their export packet retains CRS, but this audit did not exercise them.

`XmpPacket::without_development` already removes CRS and Tessera private development properties while preserving descriptive/camera/contact metadata (`crates/sidecar/src/export_policy.rs:149-169`), and the DNG path uses it explicitly. The narrow fix is to apply that baked-output policy to JPEG (and review all other rendered formats) before **both** embedded and adjacent XMP are written, while keeping Original/RAW-copy export semantics intact. If source recipe provenance is desired, store it as non-active provenance in a separate schema, not as importable `crs:*` instructions on the baked output. A tiny regression should export an edited generated RGB/RAW fixture with `Metadata::All`, index the output folder, assert the reopened recipe's active exposure/WB are neutral (and descriptive metadata/selection survive), then compare reopened displayed/export pixels against the baked output within codec tolerance. Cover JPEG sidecar and embedded packet, and keep the developed-DNG existing test.
