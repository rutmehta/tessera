# Smart Preview engine boundary — source-only design

2026-09-28; inspected main `7f98ab797faf503a5e24dfd3f6b6fb1a6ff47fd7`. No decoder, build, test, GUI, or product change executed. All paths below are relative to `/Users/rutmehta/Developer/tessera`.

## Recommendation

Implement an explicit **camera-linear, pre-camera-matrix/pre-white-balance proxy source**, retaining the original RAW recipe owner. Do not route it through the current working-space RGB source, and do not begin with CFA binning. The first engine addition should be an in-memory, bounded camera-linear source plus CPU reference rendering and discriminating tests. Persistence/codec and offline ownership then consume this proven boundary; a constructor alone is not usable Smart Previews.

This follows the local specification's demosaiced/downscaled representation (`docs/01-lightroom-classic-spec.md:140–145`). It cannot preserve the ability to recompute arbitrary pre-demosaic RAW operations without the original. Record the generation prefix and reject incompatible requests instead of claiming full sensor equivalence. Proxy rendering is an approximation at reduced resolution; the current renderer already documents different ordering of downsampling and nonlinear tone at preview levels (`crates/image-core/src/render.rs:22–34`).

## Why existing RGB / developed DNG is unsafe

* `pipeline-cpu/src/render.rs:14–22` defines RGB as linear Rec.2020/D65. Its RGB branch uses identity-camera/as-shot-one WB (`202–227`); CFA uses original `cam_xyz`, camera profile and `as_shot_wb` (`248–258`, `349–356`). These are observably different semantics for the same RAW WB settings.
* `image-core/src/rgb.rs:82–133` converts LinearDNG camera pixels through adaptation/matrix to working Rec.2020 and applies orientation. `source.rs:88–123` then synthesizes camera-neutral metadata; `source_kind` is RGB at `131–132`. `tessera-ffi/src/develop.rs:1006–1015` derives and overwrites recipe source kind from the opened source. Substituting a DNG path here would change the recipe contract.
* Although `image-core/src/render.rs:1084–1090,1144–1153` already admits three-plane pixels at the demosaic boundary then applies camera/WB matrices, its M2 scalar prefix maps every `rgb()` to working RGB at `699–709`. `resident_render.rs:542–551` resolves RGB optics without RAW metadata; `rgb_render.rs:68–86` is explicitly a working-RGB entry point. Adding a constructor that puts camera pixels in existing `RgbSource` without explicit dispatch changes is insufficient.
* `export/src/dng.rs` is developed-image export. `merge/src/dng.rs:1–9` writes uncompressed float32 LinearRaw, and `raw-decode/src/linear_dng.rs:50–84` accepts a bounded uncompressed float32/u16 strip. Neither is a lossy Smart Preview codec. No export/display transform, sigmoid, tone, default sharpening or output quantization may enter proxy generation.

## Minimal code contract

1. Add a distinct source representation, e.g. `CameraLinearProxy`, rather than overloading `RgbSource`. Store finite three-plane float pixels, proxy extent, original active extent/crop and orientation mapping, original camera calibration/as-shot WB, original source-content identity, generator revision, generation-prefix settings, and payload identity. Keep physical original metadata separate from proxy-addressing metadata: retaining original width/height against smaller planes violates source extent invariants; blindly scaling all metadata falsely validates sensor opcodes.
2. Add `pipeline_cpu::RenderSource::CameraLinear { ... }`. It enters immediately before camera-profile/WB matrices, applies the same original-camera matrices as the CFA branch, then the existing shared detail/tone/color/local/effect/geometry tail (`render.rs:349–443`). Reject incompatible source-prefix settings before rendering. Preserve exact supplied settings; never silently neutralize unsupported settings in the persisted recipe.
3. Generate camera-linear pixels by linearized CFA -> explicitly recorded highlight reconstruction -> chosen demosaic -> active-area RGB area average. `CfaImage` already contains linearized finite sensor samples (`raw-decode/src/lib.rs:100–121`). `Image::downsample_crop` is an existing linear area-average primitive (`pipeline-cpu/src/image.rs:145–180`); choose integer scale `ceil(max(active_width,active_height)/2560)`, giving a maximum rather than necessarily exact 2560 edge. Do not average CFA samples across color phases.
4. Initially admit Native revision 2, supported CFA/demosaic methods, raw denoise Off, and a prefix with no embedded opcodes or sensor/lens corrections. Generation records the actual highlight method (default is ReconstructColor, **not Clip**, `engine-api/src/recipe/settings.rs:131–150`) and actual demosaic algorithm. Rendering requires those prefix fields to match; otherwise return an explicit original-required/regenerate result. A later lens-capable prefix needs a separate coordinate/order design, especially OpcodeList3 after WB. Default Auto lens must not be silently interpreted as neutral: require an explicitly validated no-op correction or decline this initial profile. This is a meaningful first engine slice, not broad camera admission.
5. In `image-core`, keep `source_kind` RAW for proxy-backed RAW; add explicit source access/dispatch instead of using `rgb().is_some()` as the semantic discriminator. For the first integration force this representation through the new CPU reference branch; deny resident/export-row dispatch until camera-linear source handling is explicit. A fresh CPU Renderer alone does not repair the incorrect M2 `RenderSource::Rgb` branch. No GPU/native resident support claim follows from the scalar test.
6. Rendering/cache identity must include representation, proxy payload/generator identity and scale; recipe/catalog owner stays the original ImageId. Original and proxy cannot share stale tile/lens/depth/mask cache entries solely because they share the recipe owner (`image-core/src/graph.rs:1–46`; `resident_render.rs:535–560`). Process-version dispatch must remain explicit; no Adobe recipe interpreted as Native2.

The immediate implementable test boundary is steps 1–4 in pipeline-cpu plus typed source tests; step 5 requires a separate image-core dispatch review before editor wiring. Do not expose an apparently functioning offline editor while the scalar fallback uses different WB semantics.

## Editable versus original-required operations

* **WB and supported camera calibration:** continue from retained original camera calibration and as-shot multipliers. Must be compared against the original CFA reference at scale 1 before downsampling; nonneutral WB is essential to catch accidental working-RGB treatment. Native camera-profile fields must continue to obey the existing validator; this proposal does not add DCP/Adobe support.
* **Tone/exposure/color:** reusable downstream recipe values. Nonlinear operations after downsampling differ from full-resolution render then reduction; preserve recipe semantics and document proxy approximation, not pixel equality.
* **Geometry:** normalized recipe crop/rotation can operate on the proxy active area, with original crop/orientation metadata retained for reconnect. EXIF rotation is applied exactly once. Test odd active crops, odd dimensions, 90-degree orientations, and cropped output bounds; do not infer geometry from the proxy file's path or fabricated full-sensor dimensions.
* **Manual masks:** normalized brush radius is explicit in `engine-api/src/recipe/mask.rs:184–205`; normalized masks can be evaluated in the same active-area frame. Test placement/coverage after crop/orientation. Color/luminance masks are approximate because samples differ. AI/depth masks and cached retouch results require source-representation-aware regeneration or original-required refusal, not reuse of original-sized planes. Existing external model hooks are not automatically available merely because pixels are RGB.
* **Detail:** retain default and edited sharpening/noise-reduction controls in the downstream pipeline, with proxy-resolution approximation explicit. Native sharpening radius is a pixel-space field (`settings.rs:576–587`); it cannot reproduce original-resolution detail/noise after downsampling. A true 100% original-detail view, raw denoise, demosaic changes and unsupported highlight reconstruction changes require the original (or a newly generated prefix). Do not label upsampled proxy pixels as original 1:1 detail.
* **Lens/embedded correction:** current CPU RAW order crosses the proposed boundary: OpcodeList1 before highlights, CFA/database CA before re-demosaic, OpcodeList2 before matrices, OpcodeList3 after WB (`pipeline-cpu/src/render.rs:269–359`). Reapplying these to downscaled coordinates is not justified by retaining their bytes. First gate refuses these non-neutral dependencies; expanding admission is separate work.

CFA-preserving cell averaging avoids the existing RGB type problem but creates an artificial sensor grid/noise distribution, requires Bayer/X-Trans phase and crop mappings, and does not preserve original demosaic/highlight/CA behavior. The current pipeline expressly forbids plain CFA decimation (`pipeline-cpu/src/render.rs:28–30`). Phase-aware averaging would be a new algorithm needing those proofs, not a shorter correct route. It also diverges from the local demosaiced-proxy specification.

## Discriminating tests before editor wiring

1. Synthetic non-gray CFA with asymmetric channels, nonidentity `cam_xyz`, unequal as-shot WB: scale-1 camera-linear proxy render vs the same CFA prefix/reference for as-shot and custom WB; test matrix ordering and assert a working-RGB interpretation differs.
2. Confirm generation pixels are invariant under downstream exposure/tone, default sharpening, geometry and manual-mask changes; change those settings after generation and confirm output changes. Prefix changes must refuse or request regeneration, never silently reuse.
3. Multi-tile/odd active crop, finite HDR samples above 1 and below 0 where supported, exact sample count/alpha, scale bounds and independently assembled coordinates. Quantization/codec tests must prove no U8 display baking or clipping.
4. Detail default versus zero and nonzero tone/color tests compare against the **same proxy resolution** scalar reference; do not use full-resolution-export equality as an impossible oracle. Geometry/mask coordinate fixtures include orientation and original/proxy extent mapping.
5. Unsupported raw denoise, prefix mismatch, embedded opcodes, non-neutral lens, unsupported process and unavailable external dependencies produce typed original-required/unsupported outcomes before partial render. No hidden settings rewrite.
6. Image-core M2 and ordinary paths both use the camera-linear source contract; source-switch/reconnect renders invalidate stale memoized results. Retain original recipe owner/source kind after save/reopen. GPU path remains explicitly bypassed until separately qualified.
7. Later filesystem/editor tests: generate while original exists, persist on local reachable storage, remove original availability, reopen/edit/save same recipe, reconnect only the matching original content, and export latest recipe from full original. Missing original must not silently export an upscaled proxy as full quality.

## Persistence, codec and SSD answer

Original RAW bytes are necessary to build the first proxy and for full-quality original rendering/export; they are not necessary for subsequent admitted offline edits once a verified proxy and writable recipe/catalog storage are available locally. A Smart Preview stored only on the same disconnected SSD would not solve offline editing. No original deletion is implied.

The local spec calls for lossy DNG. Existing code supplies only an uncompressed bounded LinearDNG reader/writer, not that codec. At 2560×1707, float RGB alone is about 52.4 MB decimal: bounded resolution does not necessarily mean much smaller disk storage than a compressed RAW. Choosing a new compressed internal camera-linear format can provide an honest initial lightweight proxy implementation, but must be an explicit scope/format decision and not be called implemented lossy DNG. Float16/uint16/lossy encoding each needs a declared dynamic-range/error policy; existing uint16 normalization is not automatically safe for negative/highlight values.

Bind a persisted proxy to original byte digest/length, decoder/generator/process-prefix revision, camera metadata and payload digest. Original path is a reconnect hint, not identity. This is independent of current edits: changing tone does not invalidate a pre-tone proxy. The new pinned RAW descriptor is not this evolving recipe/proxy association. Capturing and hashing a file while another process mutates it also needs the coherent-capture policy already documented; metadata size/mtime alone is not content identity.

No implementation, codec availability beyond the inspected paths, measured performance, camera acceptance, or offline end-to-end success is claimed by this note.

## Shipping-default extension (required before calling the feature usable)

The neutral-lens admission in step 4 above is **only the first engine component's unit gate**. The requested feature must open ordinary default RAW recipes (`LensSettings::default` is Auto, CA enabled and 100% correction scales at `settings.rs:386–406`) without asking the user to disable them. Use a recipe-aware, explicitly recorded **upstream prefix**, while keeping WB, camera calibration, tone and later edits unbaked:

* Extract the existing CFA branch through the point immediately **before** `CameraProfile`/`WhiteBalance` at `pipeline-cpu/src/render.rs:349`. Run embedded stage 0, reconstruction, allowed raw-denoise policy (initially Off), demosaic, lens resolution against the ORIGINAL metadata/full camera pixels, database/CFA CA re-demosaic or RGB CA, embedded stage 1 and manual CA, preserving their existing order. Area-average that camera-linear result. This supports actual default Auto/CA resolution instead of pretending defaults mean no correction.
* Retain a bounded, versioned owned resolved-lens snapshot and the exact upstream settings/dependency identity. Current `ResolvedLens` is Clone/Debug, with private `sample`, `embedded` and manual-CA state (`lens_resolve.rs:66–71`), **not a ready persistence schema**. Add an explicit representation/validation/round-trip contract; do not serialize a Rust debug string or re-resolve image-derived CA on the small proxy. Existing `LensPlan` documents the three-stage order and normalized map (`lens_plan.rs:1–16,37–41`), but also is not a general serializable catch-all.
* Continue proxy rendering with camera profile/WB, then the remaining corrections in their current positions: embedded stage 2, profile vignette/point corrections, detail, tone/color/masks/effects, and final common lens+recipe geometry. Record which operations were completed so CA is not applied twice. `profile_vignette` already evaluates normalized active-area coordinates (`optics.rs:76–111`), and `ResolvedLens::map` uses normalized coordinates (`lens_resolve.rs:85–120`); these are practical reusable pieces when supplied the original resolved correction.
* Keep lens settings used by the captured prefix fixed for this generation. A changed lens profile/CA/reconstruction/demosaic field requires the original and regeneration (or shows a typed unavailable preview), while downstream WB/tone/recipe geometry remain editable. This preserves the requested RAW recipe rather than secretly rewriting it. Later refinement may narrow which lens changes invalidate the prefix; coarse whole-lens invalidation is safe initially.
* OpcodeList3 cannot generally be moved before matrices: `embedded_lens.rs:109–214` supports per-channel warps and plane-specific GainMap operations, which do not commute with channel mixing. Persist/evaluate it AFTER WB with an explicit original-sensor↔proxy coordinate transform. For a crop-first proxy, a proxy center maps back to its original active-crop bin center; partial edge bins require their actual centers. Gain-map areas/pitches and per-channel warps need separate tests—blindly scaling integer opcode bytes is invalid. Initially, original-required refusal can target unsupported **specific late-opcode forms**. It must not reject every ordinary default recipe simply because its selection says Auto.
* Common geometry must remain unbaked and compose with current recipe geometry after Effects, as the current scalar path does. Prefix corrections already applied can themselves warp pixels; preserve that operation history and avoid treating them as an additional final map. Reconnect uses the original's full metadata and full prefix; it does not reverse the small proxy's corrections.

Add default-Auto/CA tests with an observable nonidentity resolved correction, proving proxy generation bakes only the pre-matrix part, downstream WB still changes correctly, the late vignette/map is applied once, and lens-prefix changes explicitly invalidate. Add supported embedded-stage fixtures and a late per-channel opcode refusal test before enabling those cameras. This is a bounded extension of the first component, not permission to claim all cameras/opcodes work.
