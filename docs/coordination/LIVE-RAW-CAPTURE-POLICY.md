# UX-05 coherent RAW capture policy — source/design only

Audited main7e97f5993c333a5727558dcf74a5574a1849644d. No file capture/staging, decoder execution, build, tests, app or B-owned edits. Proposed first contract: **a bounded, privately owned staged capture, hashed and decoded from the same frozen artifact**. It identifies captured bytes, not a guaranteed point-in-time snapshot of an externally writable RAW or an atomic RAW+recipe transaction.

## Evidence and options

[FFI Source::open](/Users/rutmehta/Developer/tessera/crates/tessera-ffi/src/export.rs:835) opens by path and returns owned CFA+metadata or RGB pixels. [RawSource](/Users/rutmehta/Developer/tessera/crates/raw-decode/src/lib.rs:178) owns a RawFile whose current safe Rust API calls only [libraw_open_file](/Users/rutmehta/Developer/tessera/crates/libraw-ffi/src/lib.rs:63); unpack may read later. [RawImage::open](/Users/rutmehta/Developer/tessera/crates/image-core/src/source.rs:50) first opens for a LinearDNG probe, then can reopen through RGB or RawSource. Therefore keeping an original File handle while hashing and later passing the original pathname to Source/RawImage does not bind decoding to the hashed bytes. Metadata and auxiliary parsing must also use the captured artifact.

An owned immutable byte buffer is technically feasible, but not exposed by the current safe wrapper. Vendored [libraw_open_buffer](/Users/rutmehta/Developer/tessera/crates/libraw-ffi/vendor/LibRaw/LibRaw-0.22.2/libraw/libraw.h:104) exists and build.rs allowlists libraw functions. Its [buffer datastream](/Users/rutmehta/Developer/tessera/crates/libraw-ffi/vendor/LibRaw/LibRaw-0.22.2/src/libraw_datastream.cpp:323) stores the caller pointer and does not free/copy the buffer. A future Rust constructor must own stable, non-mutated bytes for the entire LibRaw handle lifetime, close LibRaw before dropping them, and close correctly on open/unpack failure. Passing a temporary slice is unsound. This requires a new safe API and lifetime/error-path tests. It also adds the compressed file-size allocation to decoder/CFA/render memory. An ordinary file-backed mmap is not an immutable snapshot under external writes. Do not select an unbounded RAM duplicate as the default.

A private staged file works with the existing path APIs and adds bounded disk/stream-buffer overhead rather than an explicit full compressed-input RAM allocation. It still needs an ownership contract: the application never mutates/replaces/unlinks the stage while decoding or lazily reading it; no write handle escapes, and callers cannot substitute another path. Private permissions/no-clobber creation prevent accidental sharing, not privileged or same-user malicious writes. No absolute external immutability claim is available from pathname ownership alone.

## Concrete first capture contract

1. Resolve the physical asset locator once and open one readable regular-file handle. Separately capture the pinned recipe under the existing read-only recipe gate/path revalidation. Release the recipe/catalog locks before long capture/decode. Record these as independent captured inputs; do not claim one cross-file transaction or consume unsaved Develop state.
2. Stream that handle into a fresh file in a private, application-owned staging directory using exclusive creation and fixed-size chunks. Require a configured finite asset-byte limit, available staging quota, cancellation, bounded concurrency and explicit failure cleanup. Enforce the limit while reading (read at most limit+1), not only from initial size metadata. Fail rather than silently fall back to the original path or an unbounded memory read. Keep the source-format routing hint/extension when required; do not let a renamed `.bin` accidentally choose a different path-based decoder route.
3. Finish all writes and freeze application ownership. Hash the completed stage bytes and record exact byte length. Use the repo's [Digest](/Users/rutmehta/Developer/tessera/crates/engine-api/src/id.rs:14): 256-bit BLAKE3 with a **fixed, versioned asset-capture domain**, distinct from RecipeHash. Its current `Digest::derive` accepts a slice; bounded streaming can use equivalent `blake3::Hasher::new_derive_key(context)` and construct Digest from the result, with equivalence tests. Domain/algorithm must be part of the descriptor schema; do not label a bare/default BLAKE3 or SHA256 value as the same identity. A typed asset-digest wrapper keeps it separate from recipe identity. Existing [ChannelRasterRef](/Users/rutmehta/Developer/tessera/crates/engine-api/src/document.rs:784) is a precedent for host-resolved digest references, not an already implemented RAW store.
4. Only a capture-owner token may invoke decode, and it supplies the private stage path to **all** metadata/probe/unpack reads. A useful type boundary is a staged-capture owner versus an untrusted original locator; a digest string plus caller-supplied arbitrary path is insufficient. Decode fully into owned RawImage/Source before releasing an ephemeral stage. Current Source/RawImage retain owned decoded samples and metadata after open returns; any future lazy decoder extends the owner lifetime.
5. On reopen against an expected asset digest, recapture candidate locator bytes, compare the completed capture digest/length, and only then decode that capture. Different bytes are mismatch/unavailable, not a refresh. The descriptor needs a resolver hint; an ephemeral private pathname is not a persisted asset locator. If persistent content-addressed storage is later chosen, publication must never overwrite existing objects, readers must retain object lifetime, and quota/retention/reverification semantics need explicit acceptance. That store is not required for the first ephemeral capture contract.

Size/mtime/file identity checks before/after reading are useful rejection heuristics for observed mutation; they do not prove the source was stable throughout. Concurrent in-place writes may produce a mixture never present at one instant. Hashing a second time, file locks, or checking metadata does not retroactively prove atomicity against noncooperating writers. The narrow guarantee is instead: within the cooperating process, the recorded digest names the frozen captured stream subsequently decoded; replacing the **original** after capture cannot switch decoding to replacement B. If a point-in-time snapshot is required, it needs a separate filesystem/cooperating-writer contract, not stronger wording around this algorithm.

Minimal later tests: compare streaming/domain digest to Digest::derive for exact bytes; inject capture read/size/quota/cancel failures with no publish; replace original after freeze and ensure decoder adapter is handed only the captured artifact; require digest mismatch before invoking decoder on reopen; hold capture alive through delayed decoder reads and release afterward. An injected mixed-read source should demonstrate the honest captured-stream semantics, not assert atomic external source history. No new graph, live-follow behavior, document schema implementation or render-version/color guarantee follows from this capture contract.

## Independent pinned-descriptor review and unresolved render boundary

Reviewed the writer's `/tmp/tessera-ux05-pinned-raw-source-contract-20260928.md` after its schema/header, recipe-owner, geometry, route and mutation-detection corrections on 2026-09-28. The descriptor/capture direction is grounded, but **render admission remains an implementation blocker**, not an available-pixels guarantee. Raw bytes plus recipe bytes freeze two inputs, not every input to rendered pixels.

Concrete evidence: [ModelRef](/Users/rutmehta/Developer/tessera/crates/engine-api/src/id.rs:310) stores id plus version string (semver or content digest); [ModelRegistry::resolve_cached_ref](/Users/rutmehta/Developer/tessera/crates/ml-runtime/src/registry.rs:228) resolves that pair through a separately loaded manifest's SHA256 and verifies the selected file. Thus identical recipe ModelRef need not prove identical manifest/content across environments. [CameraProfileRef](/Users/rutmehta/Developer/tessera/crates/engine-api/src/recipe/settings.rs:449) explicitly uses a verbatim Adobe digest string, not engine Digest; LUT settings use a style ID/amount (settings.rs:853). These serialized references alone are not immutable dependency bytes. This does not imply those fields are all active or accepted by today's native renderer: [CPU validation](/Users/rutmehta/Developer/tessera/crates/pipeline-cpu/src/render.rs:494) rejects unsupported changed controls. Conversely, [renderer_snapshot](/Users/rutmehta/Developer/tessera/crates/tessera-ffi/src/develop.rs:1404) injects caller-owned inference and depth; recipe data alone does not reconstruct those hooks. [Explicit DCP injection](/Users/rutmehta/Developer/tessera/crates/image-core/src/render.rs:374) has its own content hash and is not automatic resolution of a recipe name.

Do not invent an exhaustive self-contained Native2 settings allowlist in this source review. Before a renderer-backed implementation, define and test the actual allowed settings/dependencies and explicit renderer/decoder/backend contract revision. Missing dependency and **unbound or mismatched dependency revision** are different reasons to refuse a render; the mere presence of a model/profile is insufficient. Until that admission contract is grounded, descriptor/capture tests may establish identity and safe byte ownership without claiming pixels are reproducible or renderable. A full dependency bundle/store is deferred.

For the same reason, `(asset_digest, render_state_digest, output_contract_version)` identifies requested inputs, not a complete persistent rendered-pixel cache key across engine versions or changed dependency bindings. A later rendered cache must include its admitted renderer/dependency identity or invalidate/refuse reuse on mismatch. Avoid promising backend bit equality: [renderer documentation](/Users/rutmehta/Developer/tessera/crates/image-core/src/render.rs:35) explicitly records f16 cache rounding and preview-level approximations. This review does not select a backend or extend acceptance to pixel fidelity.

Two small draft clarifications remain necessary: distinguish a capture-owner token that retains a sealed stage through decode from an owned decoded RawImage/Source returned after stage cleanup; an unowned pathname/ambiguous stable handle is not the capture contract. Also replace “no sharpening” with “no additional output sharpening” if pinned recipe detail is intended: [default sharpening amount is 40](/Users/rutmehta/Developer/tessera/crates/engine-api/src/recipe/settings.rs:583), and the CPU [default-detail test](/Users/rutmehta/Developer/tessera/crates/pipeline-cpu/src/color_detail.rs:495) verifies that sharpening applies. Silently stripping it would break pinned recipe fidelity.

Decision: recommend the bounded captured-stream descriptor/ownership contract; explicitly defer render admission, dependency identity, full-resolution output fidelity and rendered-cache acceptance. No product code, source staging, decoder execution, tests or builds were performed for this review.
