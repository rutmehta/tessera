## Finding supported by source

`App/KeyRouter.swift:38–46` installs a local key monitor and drops handled events. `isBusyWindow` at54–58 protects only NSText, NSTextField and custom KeyOwningControl (plus modal/sheet windows). `handle` at90–100 otherwise enters document routing. `DocumentKeyMap.swift:64` maps plainTab to togglePanels; KeyRouter253 performs it. An ordinary focused button outside those three responder types therefore loses Tab to panel toggling before native focus traversal. Properties “Load3DLUT” at `Document/AdjustmentEditors.swift:367` uses the ordinary SwiftUI Button helper at87–92; no explicit keyownership/focus registration is attached.

This is a concrete generic routing gap: native ordinary buttons are not covered by the existing keyboard ownership exemption. It is consistent with the observed transition from a protected name field to Load3DLUT then panel hiding. AXfocused is not, by itself, proof that window.firstResponder is an NSButton: SwiftUI may mediate focus through a hosting responder. Capture its class/identity at the failed secondTab before choosing the exact recognition implementation. Do not claim that merely adding `is NSButton` fixes the actual SwiftUI case without that evidence.

## History distinction

`DocumentHistoryHeightControl.swift:105–115` HistoryHeightButton accepts first responder when enabled, conforms to KeyOwningControl and handles Space/Return/keypadEnter only once per non-repeat event. It has no mouseDown override explicitly acquiring first responder, no explicit nextKeyView wiring or SwiftUI focus binding. Pointer/AX press successfully activating a button does not prove keyboard focus moved there; observed Space doing nothing after such activation does not contradict this handler.

`DocumentHistoryHeightControlTests.swift:153–158` directly calls window.makeFirstResponder(button), then KeyRouter.handle and button.keyDown. It proves activation WHEN focused, not that pointer/Tab/AX navigation can reach it. The AX press tests are valuable separate action tests, also not keyboard reachability. Current source does not justify blaming History's keyDown implementation.

Ordinary-button inclusion in native keyboard traversal depends on the user's keyboard-navigation configuration. Do not require every button to join Tab traversal when that preference excludes ordinary controls, and do not change global preferences as a product fix. Conversely, once a control owns keyboard focus, an application shortcut should not swallow its navigation/activation keys. History's intended accessibility needs an actual reachable focus/action path regardless of whether a pointer press transfers focus.
