# Owned document-save presenter: UI/source review

No build, test, GUI run, or checkout mutation was performed.

## Findings

I found no source-level blocker in the binding-generation, ownership, or Save As interaction changes. The implementation keeps three identities distinct: the presenter binding UUID, the host `NSWindow` identity, and the individual save-presentation token. `DocumentSaveParentBridge.ParentView` creates a new binding UUID per representable incarnation (`DocumentSheets.swift:183-192`). Updates and teardown are accepted only for the current binding, and close-observer cleanup also checks the captured window identity (`DocumentSavePresenter.swift:81-110`; `DocumentSheets.swift:204-224`). That protects a replacement bridge on the same window from stale updates, old-window close notifications, and delayed dismantle.

Ownership is deliberately retained across asynchronous AppKit completion. The AppKit session captures its parent and exact sheet, listens for end/close notifications, and does not retire until completion has been observed and the sheet is absent from both `attachedSheet` and `sheets` (`DocumentSavePresenter.swift:166-290`). The bridge's factory captures the window weakly; the active session owns what it needs while the sheet is in flight. Child folder-panel state is retained until its modal call returns and cancellation targets that child (`DocumentSavePresenter.swift:245-290`). This matches the handoff's stated lifecycle model.

The user-facing controls preserve clear labels, accessibility identifiers, and native keyboard roles. The name field retains `document.saveAs.name`, is focused after presentation, and submits on Return only for valid input. Cancel and Save use `.cancelAction` and `.defaultAction`; format, folder path, Choose, validation, and export-format hint remain represented (`DocumentSheets.swift:227-297`). I saw no material source regression in the focus, keyboard, or accessibility wiring. Those behaviors still need actual-AppKit confirmation.

The inspected diff is scoped to the save presenter/sheet and save orchestration. `DocumentWorkspace` load, open, Layers, activation, and status-publication paths are unchanged; the legacy `save`/`saveAs` wrappers still request the headless-compatible path (`DocumentWorkspace.swift:336-386`). The headless branch is present in source, but the new Save settlement suite should include a direct regression that invokes the legacy wrapper without a window and verifies its automatic destination behavior. This is a coverage recommendation, not an observed source defect.

## Coverage and acceptance gaps

The migrated tests retain meaningful outcomes: missing-window rejection, stale presentation/supersession, cancel and replacement sequencing, write failure without false success/folder updates, and a completion that outlives the SwiftUI view. The old “unseen lifetime” outcome remains represented by `DocumentSaveSettlementTests.testKnownGapEntireAttachmentAfterCancelWithoutAnyObservationNeedsProgress`: with no view callbacks, cancellation does not advance the successor until the owned completion and exact sheet detachment arrive. That test establishes presenter state-machine behavior under a supplied completion/detach event; it does not establish that AppKit will deliver those events for a queued sheet.

The remaining acceptance blocker is therefore the native queued-sheet contract recorded in the handoff and gate plan: on a real parent window with an unrelated sheet ahead of the owned save sheet, end only the owned invocation, observe that invocation's completion and removal from parent membership, leave the unrelated sheet untouched, and demonstrate that a successor proceeds only after the owned sheet drains. Fake-driver tests cannot close this gap. The actual `NSViewRepresentable` same-window rebind/dismantle path, native parent-close behavior, and Return/Escape/focus behavior also need the planned native/GUI checks.

The tests for same-window generation protection exercise presenter registration with synthetic IDs; they do not invoke the real representable's `dismantleNSView`. Source guards look correct, but retain an actual bridge lifecycle check in the acceptance run if the test harness permits it. No additional production change is indicated by this review.
