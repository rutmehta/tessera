# Destination filename-alias exclusivity: decision note

## Decision

Keep the current Stage C contract as an exact canonical-parent plus exact recipe-filename in-process key. Do not add case folding, Unicode normalization, inode identity, or an unreviewed filesystem sentinel to the current candidate. The observed APFS case alias is a real limitation for a stronger physical-path claim, but fixing it is not a one-line extension of the existing gate.

If product requirements later require one Develop editor per filesystem-equivalent recipe pathname, the smallest general candidate is a persistent reservation entry in a dedicated hidden namespace directory under the canonical `.edits` directory, with the sentinel basename exactly equal to the recipe basename. Acquire it with an OS advisory lock (`flock(LOCK_EX | LOCK_NB)`) through opened directory descriptors. The kernel's actual directory-entry lookup, rather than guessed string normalization, resolves case/normalization aliases even when the recipe file is absent. Keep each sentinel file permanently; the process-held advisory lock is the lease. This is a coordinator scope/design decision because it changes persistent sidecar-directory contents and may extend coordination across Tessera processes; it does not by itself create a user approval requirement. It is a follow-up candidate, not a fix already present or accepted.

## Current source behavior

`crates/tessera-ffi/src/recipe_write.rs:24-43` derives the recipe path with `Sidecar::paths`, canonicalizes an existing `.edits` directory (or canonicalizes the image parent and appends `.edits` if that directory is absent), then appends the exact filename as a `PathBuf`. `gate_for` at `:45-64` indexes a process-global weak map by that exact path. `check_image` at `:146-151` compares the same key. `reserve_develop` at `:210-243` holds the per-key epoch lock while it installs one owner and captures its snapshot. Thus different Rust spellings can produce distinct in-process `GateState`s even if a case-insensitive volume resolves them to the same directory entry.

`crates/sidecar/src/lib.rs:128-148` derives `.edits/<file-stem>.json`; exact same stems across image extensions intentionally share one recipe destination. `atomic_write` at `:28-57` writes a unique sibling temporary file, syncs it, then renames it over the target. That final rename replaces the directory entry. It does not preserve a hard link from the replaced recipe path to another name. `DevelopSession::save_develop` in `crates/tessera-ffi/src/develop.rs:1185-1244` checks its gate authority before reading/writing the recipe, XMP, and index. The current mechanism is explicitly in-process and does not claim filesystem CAS or protection from arbitrary external writers.

`docs/coordination/DEVELOP-DESTINATION-ALIAS-LIMITATION.md` already records root's disposable-volume observation: case variants resolved to the same inode while `PathBuf` spellings differed. It correctly treats this as an alias limitation and rejects naive lowercase keys, inode-only identity, and directory-wide serialization.

## Why the proposed sentinel is the bounded general option if stronger semantics are required

- **Name equivalence and component limits:** Create/open a fixed hidden lock namespace such as `.tessera-develop-locks-v1` under the canonical `.edits` directory, then use the exact recipe filename as the sentinel basename. Keeping the filename as one unchanged component lets the mounted filesystem resolve aliases and avoids appending bytes to a basename already near `NAME_MAX`. Do not lowercase or normalize the filename in application code. A destination filename that is itself too long remains invalid under the existing sidecar contract; no hashed/casefolded fallback is safe because it would reintroduce guessed volume equivalence. This handles aliases according to the actual mounted volume's lookup rules, including currently absent recipe names, but does not promise equivalence across filesystems or volume collation versions.
- **Lifecycle/crash recovery:** Keep an open file descriptor and advisory lock in the lease object for the full Develop session. Normal close/drop unlocks by closing the descriptor; process crash/termination also closes descriptors and releases the kernel lock. The sentinel remains as an inert reusable file; it is not a stale PID record and needs no crash scavenger. Never unlink it during ordinary teardown: unlinking while another process has it open can let a later opener create a second inode and split the lock namespace.
- **Atomic rename:** The recipe itself continues to be written by the existing temporary-file + rename path. Since the sentinel is a separate persistent directory entry, replacing the recipe inode does not release or split the alias reservation. After rename, aliases still open the same sentinel.
- **Symlinks, sentinel namespace and path anchoring:** Resolve/open the `.edits` directory and its fixed lock namespace as directory descriptors; use descriptor-relative operations and `O_NOFOLLOW`. Require each sentinel to be a regular file in the reserved namespace, with a recognized small format marker and a single link (`st_nlink == 1`); reject symlink sentinels, unexpected types, hard-linked sentinels, and unexpected directory ownership/permissions rather than following or adopting them. Never unlink a sentinel on release: unlink/recreate while another participant holds an fd can split the lock namespace. This only detects link tampering at inspection time; a nonparticipating actor with write access can still rename/unlink entries and is outside the guarantee. If `.edits` or the lock namespace can be renamed/replaced while a lease is active, descriptor-relative locking alone does not make the current path-based recipe writer target the same directory. Either revalidate directory identity at each guarded write and fail closed on mismatch, or make the relevant temp-create/rename operations descriptor-relative as a separate scoped change. Do not claim protection against uncooperative processes that replace directories or write files directly.
- **Hard links:** Do not key by the existing recipe inode. Two different recipe pathnames that happen to be hard links are two replacement destinations: atomic rename of one pathname replaces only that directory entry. Different sentinel pathnames should therefore remain independent. Case/normalization aliases, in contrast, resolve the same sentinel entry on a volume that treats those names as equivalent.
- **Persistent-sentinel tradeoff:** Creating the sentinel requires write permission and, when missing, creation of `.edits` and the hidden lock namespace during editor admission rather than first save. Each distinct edited destination leaves a persistent hidden file. This is observable user-data-directory state and can accumulate; it is a coordinator scope/design choice to accept it, not a reason to add an approval gate. The implementation must verify scanners ignore the namespace, document its retention, fail closed on permission errors, and never silently delete entries. This cost is why deferring the stronger promise is preferable unless alias exclusion is a product requirement.
- **Scope:** Advisory locking coordinates only Tessera participants that use the protocol. It is not a lock against Lightroom, scripts, direct `Sidecar::write_recipe`, or other uncooperative writers. If the intended scope remains one process, the sentinel is probably too broad and the exact-key limitation should simply remain explicit.

## Rejected approaches

1. **`to_lowercase`, Unicode normalization, generic case folding, or hashing a normalized name:** These do not encode per-volume case sensitivity or the filesystem's Unicode collation version. They can merge distinct names on case-sensitive volumes or fail to merge names that the volume considers equivalent. Hashing the exact filename also breaks alias grouping; hashing a guessed normalization repeats the same problem. No guessed key should overstate volume semantics.
2. **Canonicalize/stat the recipe target:** It works only when the target exists. It cannot reserve an absent target; after atomic rename its inode changes anyway.
3. **Use recipe inode identity:** It collapses distinct hard-linked path destinations, although replacing one path does not update the other hard link.
4. **Probe by creating and deleting a temporary recipe-like file:** It mutates `.edits`, is visible to filesystem watchers and backup software, has crash-cleanup races, and still needs a safe cross-process protocol.
5. **Delete lock sentinels on final release:** This creates an unlink/recreate race and can split live advisory locks across old and new inodes.
6. **One lock for all of `.edits`:** It prevents the alias race by serializing unrelated photos and violates the existing independent-destination progress requirement.
7. **Stable-ID sidecar migration:** Potentially avoids filename collation, but changes the established sidecar path contract and requires legacy discovery, migration, and collision behavior; this is not a minimal alias fix.

## Deterministic follow-up acceptance matrix

Run only on explicitly identified disposable volumes. The test harness must record filesystem type, volume case-sensitivity mode, exact spellings, canonical parent path, sentinel path, and file IDs. Do not infer volume behavior from the host default.

1. **Missing target, case-insensitive volume:** With `.edits` absent, start two independent processes (or otherwise prove independent descriptors) reserving `photo.jpg` and `PHOTO.png`, which derive `photo.json` / `PHOTO.json`. Exactly one holds the reservation; the other receives conflict before opening its editor. Confirm admission created only the documented `.edits` and persistent sentinel, not a recipe file. Release the first lease and prove the second can then reserve.
2. **Existing target, case-insensitive volume:** Pre-create a recipe at one spelling. Reserve through both case variants. Prove one lease only and byte-preserve the recipe on rejected admission.
3. **Case-sensitive control volume:** The same case-distinct names receive distinct sentinels and can both reserve; exact same destination still conflicts.
4. **Unicode spelling control:** On each explicitly supported volume, exercise a known normalization-equivalent filename pair and record what the volume itself resolves. Expect conflict only when both names resolve to the same sentinel entry. Do not encode a generic Unicode-fold assertion.
5. **Hard-link semantics:** Create two differently named recipe files as hard links. Both path destinations may reserve independently; atomic replacement of one leaves the other path's previous content intact. Verify sentinels differ.
6. **Recipe atomic replacement while leased:** Save/rename the recipe during a lease, then try the alias. It must still conflict on the same persistent sentinel; after lease drop it may acquire. This proves the lock is not tied to the replaceable recipe inode.
7. **Crash/process exit:** Kill only the disposable child holding a lock. A second participant should acquire after the OS releases the descriptor lock, while the sentinel entry remains. Do not require sentinel deletion.
8. **Symlink/type/error controls:** A symlink `.edits` directory resolving to the same canonical directory must map consistently. A symlink or non-regular sentinel must fail closed without following it. Permission denial must fail admission, not fall back to the exact lexical key.
9. **Long-name and namespace controls:** A valid recipe component near the mounted volume's `NAME_MAX` still has a same-length sentinel basename in the lock namespace and can reserve; no suffix is appended. A recipe basename that the volume rejects remains a clean failed admission with no lexical-key fallback. Pre-existing unknown files/directories in the reserved lock namespace, sentinels with the wrong marker, `nlink > 1`, permission errors, and symlinks all fail closed without being rewritten.
10. **Sentinel unlink/hardlink controls:** A cooperative lease release closes its descriptor but leaves the sentinel path/inode. A test-only hostile unlink/recreate or hardlink must either be detected and fail closed on the next admission or be clearly classified as outside the nonparticipating-tamper guarantee; do not state that `flock` prevents namespace mutation. Never clean the persistent entry as ordinary release.
11. **Isolation and scanner controls:** An unrelated recipe destination must progress while one destination is leased. Library scanning and sidecar enumeration must not treat the sentinel namespace as a recipe, XMP, image, or user-facing item.
12. **Existing behavior controls:** Preserve same-stem/different-extension exact collision, owner/generation authority, snapshot rollback, selection's intended orthogonality, and exact-key participating Engine writer tests. State separately that uncooperative external writers remain outside the guarantee.

## Disposition

For the current Stage C acceptance, retain the exact-path key and make no product change. The acceptable claim is “one active lease per canonical parent plus exact recipe filename among participating in-process Engine callers.” The observed APFS alias gap blocks any broader physical-file exclusivity claim. If the broader claim is required, first accept the persistent sentinel side effect and cross-process participation contract, then implement and gate the above small protocol; do not patch with application-side case folding.
