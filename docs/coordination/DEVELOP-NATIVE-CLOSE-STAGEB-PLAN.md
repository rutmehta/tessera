# Stage B native Develop close: bounded test-first plan

Source review of `crates/tessera-ffi/src/develop.rs` on `origin/main` `99dd8c46` after Stage A. This plans only the Rust session lifecycle. The Swift navigation/recovery gate in [DEVELOP-CLOSE-RECOVERY-CONTRACT.md](DEVELOP-CLOSE-RECOVERY-CONTRACT.md) remains a separate required slice; merging this backend change alone must not enable a writer lease or imply that failed UI transitions are safe.

## Observed gap

`DevelopSession::close` currently calls `flush` and then `Shared::close` regardless of the result (near line 2629). `Shared::close` sets `State.closed` and cancels rendering (near 1492), while the save thread is shut down and joined only by `Drop` (near 1896). Thus a failed close leaves a retained session unable to render but with a live writer, and a successful close retains the worker until the last `Arc` drops. `Shared::lock` does not reject closed state; exported mutators can still edit it. Several history mutators release `State` before `schedule_save` (near 2168, 2202, 2265, 2277, 2304, 2461, 2489, 3248), so a close check inside `schedule_save` alone would allow an in-memory edit to be separated from its save. `flush` itself can commit pending live settings and enqueue a save (near 2579). Stage A correctly retains failed-save retry work, so close must not discard it.

## Minimal native implementation

1. Add one session lifecycle admission mutex, with `Open`, `Closing(attempt)`, and `Closed`. An attempt is a small `Arc` containing a completion result and condition variable. A first `close` caller changes `Open` to `Closing`, releases the mutex, and runs the existing flush through a private close-authorized path. Concurrent callers that observed `Closing` wait on the same attempt and receive its **same outcome**; they do not start another save. A failure publishes that attempt's error and restores `Open`, preserving `Shared::state`, save retry, listener, and writer. A later *new* `close` call may retry. A successful attempt drains the save worker once, calls `Shared::close` once, records `Closed`, and publishes success; later close calls return success. Keep the attempt result in its `Arc`, so a later retry cannot overwrite the result still owed to an earlier waiter. Do not hold the lifecycle mutex while waiting for save, joining the worker, cancelling renders, or invoking listeners.
2. Use the same admission mutex for every state-changing session operation, not just `schedule_save`. Hold a short admission guard across its `State` mutation **and** corresponding save enqueue, preserving lock order `admission → State → SaveState`; release it before any blocking flush, disk work, or callback. This closes the current edit/enqueue gap. Reject persistence edits, live-setting edits, and render/presentation mutations when `Closing` or `Closed` using the existing `Result` error type. `commit`, history/reset/snapshot/process/mask paths must share the guard. `flush` invoked externally during `Closing` should join that close attempt (or return a clear closing error); the internal close flush is privileged and cannot reacquire admission. A public `flush` after `Closed` must not enqueue work. Audit every `schedule_save` call and every state mutation before calling this complete. Existing void cleanup methods such as `detach_surfaces` may be idempotent no-ops after close; `plan_surface` and immutable getters can remain readable. Avoid an ABI change solely to make those void methods throwing.
3. On success, only after `flush` has observed no due/busy/retry work, set `SaveState.shutdown`, notify, take the `JoinHandle` once, and join without holding `State`, `SaveState`, or lifecycle locks. Then close rendering and publish `Closed`. `Drop` uses the same idempotent worker-stop helper for abandonment, but **does not attempt an implicit save or change a reported close failure into success**. The Swift recovery owner must keep a strong `Arc` after failure; dropping the last `Arc` necessarily abandons volatile edits. Poison recovery follows the existing save/state policy rather than panicking in cleanup.
4. Keep a failed close save-capable and render-capable. It may have published a recipe before an XMP/index failure, so retry must reuse Stage A's repair-only state and preserve its first error visibility. Do not reset `SaveState.retry`, clear `State.live`, or mark `State.closed` on failure. No lease, cross-process CAS, rollback, or new public API belongs in this slice.

`save_now` calls `DevelopListener::saved` on the save worker before `SaveState.busy` is cleared. A listener can retain a session and call back into `close` or `flush`; either would wait for its own worker, and `close` might try to join itself. Record the worker thread ID at construction and reject these two blocking calls promptly when invoked on that thread. The worker holds no `State`/`SaveState`/listener mutex during `saved`, so ordinary callback state edits may be admitted while `Open` and queue the next save; while `Closing` they must be rejected. Take the join handle under its mutex, release that mutex, and only then join. A test listener using a `Weak<DevelopSession>` should call `close`/`flush` from `saved` and record prompt errors, with a bounded external watchdog. This is a lifecycle check, not permission to hold admission across callbacks.

The admission guard is the critical implementation cost. A `closed` check only in `Shared::lock` or `schedule_save` is insufficient because the edit and save enqueue are separated today. The implementation should centralize the guard acquisition so a newly added mutator cannot bypass it. Verify that no guard is held across a save-worker callback, thread join, or synchronous render wait before accepting the patch.

## Deterministic tiny tests, before implementation

- **Repair-only retry:** with an indexed 2×2 JPEG outside the support directory, inject the existing one-shot post-recipe failure. First `close` returns that error and leaves the session/worker open; recipe remains published while XMP/index lag. Call `close` again **without any edit**: auxiliary outputs repair and close succeeds. Check exact saved exposure and recipe/XMP/index state. The first failure must remain reported, not silently consumed by a concurrent close.
- **Edit after failed close:** in a separate fixture, fail first close, then edit/commit through a retained `Arc` and retry close. Check the later edit is saved and render state was not marked closed by the first failure. Do not use this test as evidence for repair-only retry.
- **Concurrent callers:** use the existing post-recipe pause to block the save thread, then start two `close` calls. Add a test-only close-attempt/waiter observation hook rather than sleeps; release the pause and assert both callers receive the same injected failure and exactly one save attempt occurred. Then retry in a separate call and assert success. Also exercise two callers on a successful attempt and repeated `close` after success.
- **Drain and retained `Arc`:** after successful close, assert the writer handle has been taken/joined and no due, busy, or retry work remains; retain a cloned session and call settings/history/commit/flush operations. They must fail promptly with a closed-session error, with unchanged recipe and no new `due` work. Drop all references under a bounded watchdog to catch a hidden worker wait. Before success, pause a mutator between state edit and save enqueue with a test-only admission hook and start close: close must wait for that enqueue and persist the edit. After `Closing` starts, a different mutator must fail without changing live/history state or queuing a save.
- **Failed-close retry with retained references:** keep two session `Arc`s, fail close, then edit through the second and retry close; the edit must save. This proves failure did not mark `State.closed` or shut down the worker. A persistent injected fault should make each *explicit* later close return an error once without automatic retry spin.
- **Histogram control:** `Engine::depth_histogram` currently creates and drops a temporary Develop session (near 902). Test it while an editor session for the same tiny image is open and after that editor closes; results should remain available and no temporary save worker remains running. Stage B adds no exclusive lease. A future lease slice must separate this read-only constructor or borrow a read-only context before activating exclusivity.

Keep all tests bounded and independent of GUI/GPU/large RAWs. Preserve each RED failure, source freeze, and direct test exit before implementation; then focused lifecycle tests, existing Stage A save/repair tests, adjacent Develop tests, and strict formatting/lint checks. The Swift failure-safe close/navigation tests in the parent contract are still required before user-facing recovery can be claimed.
