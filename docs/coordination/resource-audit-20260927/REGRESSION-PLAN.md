# B5-16 compositor resource regression plan (source-only, 2026-09-27)

Repository: `/Users/rutmehta/Developer/tessera`. B audit: `origin/wp/B5-16:tools/orchestrate/wp/B5-16/RESOURCE-AUDIT.md` at `131af17`. Product source inspected at that ref and `origin/main`. No workload was run; B's resource hold remains in force.

## Root cause and minimal first patch

`render/mod.rs:690-723` sends cold full-level tiles through `par_iter`. Each tile reaches `smart_tile` (`:411`) and `filtered_source` (`smart_filters.rs:288-415`), where a cache miss computes the whole child image outside the mutex. Concurrent misses for the same key can all evaluate. The lock-free evaluation is intentional: `tests/smart_filter_deadlock.rs:33-58,68-113` proves an evaluator can re-enter the same compositor from Rayon. A blocking per-key mutex/OnceLock is unsafe. `filter_evaluations` increments only for the winner at publication (`smart_filters.rs:394-414`), hiding duplicate attempts. If `source+result` exceeds the filter cache budget (`:388,400-413`), no result is retained, so each later tile can repeat it. `FilteredSource.key = next_doc_key()` (`:465-468`) also prevents child composite tiles from reusing keys across calls; verify its invalidation semantics before changing it.

First patch should be additive observability plus a tiny regression; it must not claim a global memory cap. Add monotone counters to `FilterRuntime`/public compositor accessors for: `stack_attempts` (increment when a cold stack starts, including eventual errors and duplicate losers), `stage_attempts` (increment immediately before each enabled nonzero stage evaluation, including failed/duplicate stages), `duplicate_publications` (computed entry lost to another winner), `oversize_results` (completed entry rejected by budget), `active_stacks` and `peak_active_stacks` (RAII decrement on every exit). Keep existing accepted `filter_evaluations` contract for old tests. Expose `cache_bytes` separately. A `working_bytes`/peak counter must only be named *estimated known owned bytes* until every allocation is reserved: source/output rasters, `evaluate_transform`'s four planar vectors and result, blend copies, masks, and external evaluator allocations are not all covered by the current `bytes = area*32` cache charge. For exact memory attribution use process footprint/allocator profiling, not this estimate.

## Tiny regression and expected observations

Extend `tests/smart_filter_deadlock.rs` (its child-process timeout keeps deadlock regressions bounded) or add `tests/smart_filter_resource.rs`. Use 257×1 or 257×2 F32 fill: two horizontal tiles but only ~8.2 KiB source+result for 257×1. Run inside a 2-worker Rayon pool. A deterministic two-tile cold race with its existing Barrier evaluator should assert `stack_attempts=2`, `stage_attempts=2`, `duplicate_publications=1`, `peak_active_stacks=2`, while accepted `filter_evaluations=1` and pixels remain correct. Clear composites, rerender, and assert attempts do not increase when the entry fits budget. Do not replace that race with a blocking initializer.

A separate, non-barrier case uses a budget of 8 KiB, just below the 257×1 result's nominal 8,224 bytes. Under current behavior, a second tile or second frame repeats whole-image evaluation; assert `oversize_results>0` and attempted count rises, with correct pixels. This is the failing resource regression to preserve for the production fix. Add a nested smart object with a leaf evaluator and an outer evaluator that invokes two nested `render_level_rgba` calls, as in the current re-entry test; run 1 and 2 workers under the child-process deadline. The target is no deadlock and no duplicate full-image attempt within a full-level frame once orchestration is in place. Direct concurrent `render_tile` calls may still duplicate unless their API also gains a render-scope coordinator; test/describe that boundary separately.

## Production approach to review before implementation

Move full-image preparation above `par_iter` for `render_level`/`render_level_rgba`: traverse visible smart-object dependencies bottom-up and evaluate each needed filtered source once on the caller before tile fanout. The traversal must happen without holding the filter-cache mutex. This removes same-frame cold races for cacheable results and respects nested Rayon re-entry. Cache misses from direct `render_tile` or external evaluator calls remain lock-free.

For entries larger than the persistent filter-cache budget, a serial prepass alone is insufficient: tiles would recompute them after the prepass. Give the full-level render a scoped `Arc<Cached>` result map shared by its tile tasks, then release it after frame assembly; retain no oversized entry in the persistent map. Admit a prepared result only after a *separate hard working-memory reservation* accounting for all simultaneously live source/result/intermediate allocations; on admission failure return `ResourceExhausted` before CPU fanout. A single global reservation must cover concurrent frame renders and nested evaluations; never wait for memory while holding a Rayon worker or filter-cache mutex. Fail fast or schedule at the frame coordinator, with cancellation releases via RAII. This design is broader than the first counters/test patch and needs a separate review. If a scoped map is too invasive, keep the safe first patch and report the oversized case as unresolved; merely raising the cache budget or keeping an unbounded oversize entry is not a resource fix.
