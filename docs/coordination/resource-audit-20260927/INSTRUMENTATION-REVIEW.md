## Counters and tiny test

`ActiveStack` begins before `source_raster` (`smart_filters.rs:368–382`) and drops on ordinary errors or panic unwind, so attempts include duplicated source composites that coalesce at the second lookup. `attempted_stages` increments just before actual transform/evaluator invocation (`:401–410`); disabled/zero-opacity stages and transform parameter parse failures do not count as invoked stages. `oversized_stacks` increments only after a complete result loses cache eligibility (`:454–468`). `filter_evaluations` retains its older accepted-stage meaning. The public stats are independent relaxed atomic loads, suitable as post-run counters but not a coherent live snapshot. Nested stack recursion increases `active_stacks` even on one OS thread; its peak measures simultaneous live stack frames, not thread count or bytes.

`duplicate_stacks` is the one misleading label: it only counts a completed computation discarded because another **retained** entry exists at publication (`:454–459`). Oversized same-key evaluations have no retained winner and therefore report zero despite duplicated work. Document it as `discarded_publications`/`duplicate_publications`; `attempted_stacks` remains the broad actual-work counter. The direct two-tile Barrier test and the existing nested re-entry child-process coverage remain intact. Their added assertions are consistent with the lock-free path.

The RED fixture is genuinely tiny: 257×1 pixels, two intersecting tiles, nominal source+result charge 8,224 bytes, cache budget 8,223. Both tile calls must compute even if scheduling is serial, so baseline should show at least two attempts. The evaluator is nonblocking, which is correct for a future one-attempt prepass. One important test-contract correction: do not accept `ResourceExhausted` merely because the **persistent cache** budget is 8,223 bytes. That budget historically controls retention, not whether an 8 KiB operation can run. Keep this RED case about one successful evaluation per frame; test a fail-fast admission path separately with an explicit working-memory limit. Otherwise an implementation could make the regression green by rejecting useful work for the wrong reason.

## Lowest-risk boundaries for a later frame scope

1. Scope the new result map to one `render_level_premultiplied` invocation. Build it before `par_iter`; pass an explicit `Arc<RenderPass>` (or an optional reference through internal `DocRef`/`TileJob` context) down `render_tile_premultiplied → composite_premult → TileJob::load_src → smart_tile → filtered_source`, and through `source_raster` for nested smart objects. Public direct `render_tile` keeps the current no-pass path. Avoid thread-local state: Rayon tiles run on other workers and external evaluators may re-enter the same compositor.
2. Split `filtered_source` so the shared unit is an `Arc<Cached { source, result, bytes }>` **before** mask application. Store that by the existing `(so.key, child revision, filter digest, context digest)` key. Keep masks and `FilteredSource` construction after lookup: mask-only edits intentionally reuse the unmasked result, while `FilteredSource.key = next_doc_key()` currently gives each final raster a fresh namespace. Caching that final masked state by the old key would serve stale pixels.
3. A pass map may use a short mutex for lookup/insertion, but never hold it while `source_raster`, a filter, or a transform runs; never make Rayon tile workers wait on a per-key initializer. The prepass must mirror `TileJob::compile_list` reachability, including hidden bases suppressing clipped children, hidden groups, styles, and transformed smart bounds. Build deepest-first, then let tile workers read completed entries. Missing keys use the current lock-free fallback, not a wait.
4. Keep pass identity/lifetime independent for overlapping `render_level` callers. An evaluator can invoke nested `render_level_rgba` on the same compositor from a Rayon worker; that nested call gets its own pass. Pass entries and permits are released only after all tasks finish or error, via RAII. Concurrent passes can still duplicate the same key unless a higher-level coordinator admits/schedules them; do not claim cross-call deduplication.
5. Frame retention can turn an oversized cache miss into a large live allocation. Do not enable unbounded pass retention as a production fix or call `cache_budget` a hard working-memory cap. Add a separate explicit admission policy that estimates known source/result/intermediate allocations before computation, shares a fail-fast permit across concurrent passes, and records what it cannot count (external evaluator and GPU allocations). The 257×1 success case is a small correctness test; it does not prove a process-wide memory bound.
