# Swift stub Save As destination intent — source review

Read-only 2026-09-28. Main and Resource's `codex/document-save-destination-intent` (`75a1b9a6`) were inspected; no build or edit. The native candidate declares `DocumentSaveDestinationIntent.{CreateIfAbsent,ReplaceConfirmed}` and typed `DocumentSaveAsResult.{Saved,DestinationExists}` in `crates/tessera-ffi/src/document.rs:127-139`, and `save_as_checked` in `:2131-2144`. Its `io::stage_bytes` uses a unique `NamedTempFile` in the destination directory, writes/syncs it, then `persist_noclobber` for create or `persist` for confirmed replace (`document/io.rs:345-387`). This is the right atomic commit boundary; native tests are owned by Resource and were not run for this review.

The existing Swift boundary remains path-only: `DocumentBackend.saveAs(path:)` at `apps/mac/Sources/TesseraCore/Document/DocumentBackend.swift:421-425`, `EngineDocumentBackend.saveAs` at `EngineDocumentBackend.swift:579-584`, and UI `DocumentWorkspace.finishSaveAs`/`admitDocumentWrite` at `apps/mac/Sources/Tessera/Document/DocumentWorkspace.swift:487-529`. The UI must preserve the **actual** decision: create when no Replace was shown, confirmed replace only after the Replace response. The stale `fileExists` result at `:492` may choose whether to present the alert, but must not be used as final no-clobber enforcement. The new typed conflict must not call the success branch (`:512-520`), update `lastSaveFolder`, emit `Saved`, or advance the document path/title/saved marker. Legacy `saveAs(path:)` stays for existing callers.

`StubDocumentBackend.saveAs(path:)` at `StubDocumentBackend.swift:912-935` currently encodes a snapshot then `Data.write(to: url, options: .atomic)` at `:924`, which replaces the final path. A second `fileExists` or `FileManager.createFile` followed by this write is still check-then-write. Add an opt-in stub `saveAs(path:intent:)` returning the same two-case outcome as the engine, with shared snapshot/metadata code but without changing established-path `save()` and legacy replacement semantics. For `CreateIfAbsent` on macOS:

1. Encode the captured state fully before publication. Create a **unique same-directory staging file exclusively** (`mkstemp`, or `open` with `O_CREAT|O_EXCL`) and write/sync/close it. A random filename with ordinary `Data.write(.atomic)` is not itself a collision-proof staging reservation. Same-directory placement makes hard-link publication same-volume.
2. Prefer `Darwin.renamex_np(stagePath, destinationPath, UInt32(RENAME_EXCL))` or `renameatx_np` with `RENAME_EXCL`, matching the pinned native `tempfile` route. The installed MacOSX SDK declares the flag as `0x4` and both calls in `sys/stdio.h:37,52-53`, available since macOS 10.12. This is an atomic no-replace move. Map `EEXIST` to typed `.destinationExists`. Fall back **only** when this primitive is unsupported (`ENOSYS`/`EINVAL`) to `Darwin.link(stagePath, destinationPath)` (`unistd.h:476`) followed by stage unlink. That fallback is also atomic no-clobber on a same-directory staging file. Existing regular file, symlink, or directory must remain untouched. Do not fall back on collision or arbitrary I/O errors, and never fall back to a replacing write. Clean the stage on conflict/error. After successful hard-link publication, an unlink cleanup error must not be reported as failed save: the destination already exists and retry could mislead the caller. Neither `NSFileCoordinator` nor `Data.write(.atomic)` makes absent-path creation conditional against an uncooperative writer.
3. `ReplaceConfirmed` may retain the existing replacing atomic write or use the same unique stage plus replacing rename, preserving the accepted path-overwrite convention. It is *not* an external-version compare-and-swap; an external edit after approval can still be replaced. Preserve ordinary `save()` and direct legacy `saveAs` replacing behavior; share the save gate without reading ordinary Save’s path before taking that gate.

Capture both `live` and `head` while holding the stub lock (`StubDocumentBackend.swift:919-922`), and set `savedHead` to that **captured** head only after a successful commit, rather than the then-current `head` at `:932`. Otherwise an edit during encoding/I/O can be incorrectly marked saved. Path/title, `engine.forget/remember`, and `post` at `:928-935` also run only after successful publication; on conflict, preserve the prior document identity and dirty state. Note that `appendEntry("Change", live)` at `:920` may commit a pending interactive edit before I/O even if I/O conflicts; tests should state whether the conflict contract permits that local history finalization (it must not pretend disk publication occurred).

Minimal tests: pause after staging and create a sentinel at an initially absent path, then resume and assert `.destinationExists`, sentinel bytes/inode unchanged, owned stage cleanup on normal error paths, old document path/title/saved marker; then retry a different name and reopen. Run same-name concurrent stub saves and assert exactly one success. Test existing regular file/symlink/directory controls, confirmed Replace success, and a mutation during delayed I/O to prove captured `savedHead` leaves the newer edit dirty. At the UI boundary, inject the sentinel after Save but before backend commit and require visible conflict rather than “Saved”; only actual Replace response sends `.replaceConfirmed`. Keep the native and stub tests distinct, and do not infer their behavior from file existence checks.

Root integration clarification: take the dedicated save gate before reading the current ordinary-Save path and before the model snapshot; never invert save/model lock order. Post-publication cleanup is best effort with honest diagnostics, not a universal no-stage-leak guarantee. All proposed Swift behavior remains UNRUN until actual generated bindings and A gates.
