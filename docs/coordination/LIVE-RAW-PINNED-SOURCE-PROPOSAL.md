# UX-05 proposed engine contract: pinned RAW source

Implementation update: the pure descriptor subset is accepted at source083018a9 (98 engine-api tests/strict/fmt). Current settings are authoritative; history is opaque. See the implementation plan and evidence package. All resolver, physical capture, decoder, rendering and UI portions below remain proposed. This is not an editable Smart Preview feature.

Status: proposed design only; no product implementation or acceptance. This narrows the source-only direction in `docs/coordination/LIVE-RAW-GRAPH-PERSISTENCE-AUDIT.md` to one reproducible, fail-closed engine contract before any compositor node or B-owned Document/FFI work. It does not add automatic follow, shared undo, or a UI promise.

## Recommended boundary

Define an engine-owned serializable `PinnedRawSource` descriptor and a read-only resolver. Pinning captures one indexed RAW byte stream and one recipe payload as separate inputs; it does not claim an atomic source-plus-recipe transaction. Resolving later returns a captured/decoded input plus the pinned recipe; any render is a separate future contract and must never substitute the current sidecar recipe. The current Open in Layers flattened-copy API stays unchanged.

Keep two identities separate:

- `asset_digest`: BLAKE3 derive-key digest using a domain such as `tessera pinned RAW asset v1`, over the complete RAW file bytes. This identifies physical bytes; path/name and size/mtime are locator hints only.
- `recipe_image_id`: existing `ImageId` attached to the recipe sidecar. It identifies the recipe owner and may represent a virtual copy; it is not the physical file identity.

A descriptor carries `descriptor_version: 1`, a non-authoritative path hint, the normalized original file suffix/decoder route, `asset_digest`, byte length, `recipe_image_id`, exact recipe JSON bytes as read at pin time, and a canonical render-state digest. Store suffix/route separately from the path hint; relocation or a temporary stage filename must not silently select another decoder. Keep the exact JSON payload, not only `recipe_hash`: require an explicit raw JSON `schema_version` field equal to 3 and `image_id` equal to `recipe_image_id` before calling `Recipe::from_json` (which migrates older schemas to the current schema). Then require `source_kind == Raw` and `process_version == Native revision 2`. Compute `render_state_digest` over a versioned canonical tuple of source kind, process family/revision, and complete `DevelopSettings`; verify it against the parsed payload on resolve. The exact recipe bytes preserve the selected recipe snapshot; the render digest is an integrity key for that captured state, not a complete rendered-pixel/cache identity.

The first descriptor/capture contract accepts only recipe schema 3, RAW source kind, Native revision 2, and neutral output geometry. This is input validation scope, not a claim that every such recipe is render-ready. Require `settings.geometry == GeometrySettings::default()` (orientation 1, Upright off/no guides, identity transform, unconstrained full crop); otherwise return `UnsupportedGeometry` before source decoding. This deliberately excludes recipe crop, straighten, Upright, rotation, and transforms until a source-backed layer can define their relationship to document extent and provide matching renderer behavior. Reject any other recipe schema, source kind, or process family/revision before source decoding or renderer construction. In particular, do not silently send Adobe revisions through the current export CPU fallback. A future broader matrix can add a process only after it has a version-aware renderer path and focused fidelity tests.

## Pin and resolve behavior

`pin_raw_source(image_id)` obtains the indexed physical path and recipe under the existing read-only gate → catalog/path revalidation sequence. Capture exact recipe sidecar bytes while that read gate/catalog/path are coherent; inspect raw `schema_version` and `image_id` before normalization, then parse and validate. Do not reserve a Develop writer, create a session, or write sidecar/XMP. Recipe capture is independent of RAW capture; do not claim that the two external files were read atomically. Make a bounded streaming copy of the RAW bytes into a fresh private staged artifact while computing `asset_digest`; the configured capture byte limit is an explicit caller/policy input, and exceeding it returns `CaptureLimitExceeded` before rendering. Preserve the stored original suffix/decoder route on the stage. All probes and decode must use only that sealed staged path, never reopen the original path. Current RAW decode probes DNG and may reopen paths, so hashing the original and later decoding that original is unsafe. Use the staged path for the complete probe/decode lifetime; discard it after the owned decoded source is produced unless durable RAW availability is an explicit later product policy. Do not assume an unbounded in-memory buffer wrapper exists. Metadata/read errors and observable file identity/length/time changes during staging can fail as `SourceChangedDuringRead`; this is best-effort detection only. The guaranteed identity is the exact captured stream whose digest is stored, not an atomic point-in-time snapshot of a concurrently mutable original file.

`resolve_pinned_raw_source(descriptor, capture_limit)` treats the stored path as a hint. Try the hint first; if unavailable, allow a catalog/path relocation lookup by `recipe_image_id` only when the captured bytes’ complete digest matches `asset_digest`. Do not accept a different file just because it reuses the path or has the same `ImageId`. Stream the candidate into a fresh private staged artifact while hashing; verify digest and byte length before any probe/decode, then use only that sealed artifact for every probe/decode read. Select the decoder using the stored original suffix/route, not the current candidate or stage path spelling. Do not read current Develop sidecar state during resolution. Return `CaptureLimitExceeded` distinctly if the configured limit is exceeded.

Use typed capture/decode outcomes rather than fallback pixels:

- Before decode: `CapturedRawInput { stage_owner, recipe_snapshot, asset_digest, decoder_route }`, where `stage_owner` keeps the private stage alive through every probe and decoder read.
- After decode: `PinnedRawDecodedInput { owned_raw_image, recipe_snapshot, asset_digest, decoder_route }`; clean up the stage only after decoder return. Do not use the stage guard/path as long-lived document reopen storage.
- `MissingSource`
- `AssetMismatch { expected, actual }`
- `UnsupportedDescriptorVersion { found }`
- `UnsupportedRecipeSchema { found }`
- `UnsupportedSourceKind`
- `UnsupportedProcessVersion { family, revision }`
- `UnsupportedGeometry`
- `SourceChangedDuringRead`
- `CaptureLimitExceeded { limit_bytes }`
- `InvalidPinnedPayload` (malformed JSON or render digest mismatch)

Dependency errors are gates for a future render API, not claims about this descriptor/capture result. Before that API is enabled, it must return `DependencyUnavailable`, `DependencyMismatch { kind, expected, actual }`, or `UnpinnableDependency { kind }` rather than silently changing render behavior.

No resolver outcome may silently substitute stale raster pixels. The descriptor remains unchanged on all failures so a future explicit relink/rebase UI can preserve the document graph.

## Frozen output contract for this first slice

For the first source-backed pixel boundary, recommend full source extent after EXIF display orientation; opaque RGBA; 16-bit unsigned samples; sRGB IEC 61966-2.1 encoded transfer function and matching ICC profile. This is a future renderer requirement, not evidence that a renderer currently meets it. No linear/HDR output or resampling is proposed. Do not strip recipe detail sharpening; specify only no *additional output sharpening*. The neutral-geometry admission rule avoids silently dropping crop/Upright/transform settings. Output profile and renderer behavior remain unqualified.

Any future renderer must receive the parsed pinned `Recipe`/explicit `ProcessVersion` and use a version-aware path such as the current image-core `Renderer::for_recipe` boundary. It must not use `export::render_pixels` as proof of process fidelity: the source audit found its CPU fallback passes settings without process version, and the GPU path declines non-current-native recipes. **Render admission remains blocked on an explicit renderer/dependency profile.** Native revision 2 alone does not freeze optional resources: Auto camera/lens profile resolution, LUTs, learned demosaic/denoise models, depth/mask models, ICC/DCP bytes, and injected renderer hooks can affect output. Before claiming render support, either define and verify identities/digests for every selected dependency, or define a small admitted-settings subset that rejects unpinned external dependencies. Do not invent a broad allowlist in this descriptor proposal. Missing or changed dependencies must fail before pixel publication, never fall back silently. `render_state_digest` is not final pixel/cache identity; this proposal makes no rendered-pixel reproducibility claim.

## Deterministic acceptance tests for this contract

1. **Descriptor round trip:** serialize and parse a descriptor; exact recipe bytes, asset digest, recipe ImageId, render-state digest, and original decoder suffix/route remain identical; mutated render-state digest rejects before decode.
2. **Virtual copies:** two recipes with different `ImageId`s for one unchanged RAW produce equal `asset_digest` but distinct recipe identity and pinned render-state digest when settings differ. Do not collapse them into one current-recipe lookup.
3. **Immutable recipe:** pin, change the live sidecar settings/history, then resolve; the result uses the pinned bytes/settings/process and does not modify/read-as-authoritative the later sidecar. Assert no writer/session construction and sidecar bytes remain unchanged. Missing/non-3 raw schema and recipe ImageId mismatch reject before decode.
4. **Same-path replacement:** pin file A, replace bytes at the same path with file B (including same-size replacement); resolution returns `AssetMismatch`, before decode/render, even if size/mtime or recipe `ImageId` appear unchanged.
5. **Relocation:** move the identical byte sequence and update the resolver/catalog path; resolution may return a captured input only after full digest equality. A different file with a copied sidecar ID must mismatch. The decoder route remains the route captured from the original suffix, even if the relocated filename has a different suffix.
6. **Unsupported inputs:** missing/non-3 raw schema, mismatched recipe ImageId, RGB source kind, Adobe process version, unsupported native revision, and non-default geometry each return the corresponding typed failure before decoder invocation. Schema 3 + matching ImageId + Raw + Native 2 + default geometry is the descriptor/capture positive control only; it does not prove render admission.
7. **Captured-stream identity:** replace the original after stage copy completes but before the decoder starts; probes and decode still consume sealed staged bytes, and the result digest matches those bytes. Inject an observable path replacement, metadata/length change, read error, and byte-limit overflow during staging; require `SourceChangedDuringRead`, I/O failure, or `CaptureLimitExceeded` as appropriate, with no pixel publication. Do not claim detection of every same-size in-place mutation with preserved/coarse timestamps: identity is the exact captured stream, not an atomic point-in-time source snapshot. Use deterministic barriers, not sleeps. Assert stored suffix/decoder route is used and the stage is removed after decode completion/failure.
8. **Geometry admission:** default geometry is the positive control; crop, non-default recipe orientation, straighten, Upright, and transform variants each return `UnsupportedGeometry` before decode. No output-render result is claimed by this descriptor/capture contract.
9. **Requested-input identity:** changing asset digest, recipe render-state digest, or decoder route changes captured-input identity; changing only locator path with identical bytes does not. This is not complete rendered-pixel cache identity. Recipe ImageId alone never keys physical source bytes.
10. **Future dependency admission:** before any renderer uses this descriptor, test selected Auto profiles, LUTs, learned models, depth/mask inputs, and injected hooks. Until each dependency has a resolvable identity/digest policy, require the typed dependency error before pixel publication; do not treat Native 2 alone as sufficient.
11. **Copy-path preservation:** existing `Open in Layers` tests still prove first-open saved adjustments and existing-copy pixel stability after later Develop edits. This contract adds no source-node or automatic-follow behavior.

## Explicitly deferred

No compositor `LayerKind`/format variant, FFI, Swift model/UI, automatic Develop-follow, shared undo, layer masks/transforms, arbitrary Adobe PV, linear/HDR samples, relink UI, performance guarantee, or document migration code is included. The existing `.tessera-doc` v1 future-version preflight at integrated `main372dbbcc` / validated source `26845eed` is a prerequisite already completed, not work proposed here. A source-backed node still requires a later jointly reviewed graph serialization and B-owned adapter contract.
