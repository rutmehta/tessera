# Smart Preview storage and UI design (source-only)

Audit target: `/Users/rutmehta/Developer/tessera`, `main` at `7f98ab797faf503a5e24dfd3f6b6fb1a6ff47fd7` (2026-09-28). No source files, builds, tests, or UI were changed/run.

## Current behavior and constraints

Smart Previews are not implemented. `docs/coordination/SMART-PREVIEW-STATUS.md` says current previews are display JPEGs, the develop opener reads the indexed original, and the DNG exporter has no lossy-DNG option. The intended ~2560 px lossy-DNG behavior in `docs/05-catalog-storage-and-import.md` §2.2 and `docs/01-lightroom-classic-spec.md` §1.11 is design intent, not an existing path.

The current source identity is the catalog image ID derived from its original path: `crates/index/src/lib.rs:251` computes `stable_id(&path_s)`. `EngineImageReference` carries that ID (`apps/mac/Sources/TesseraCore/EngineLibrary.swift:23-32`); `EngineLibrary.scan` indexes the selected folder and opens its cull session (`:108-134`). `Index::scan` canonicalizes and walks a mounted directory (`crates/index/src/lib.rs:190-212`). The DB and ordinary display-preview cache live under application support (`crates/tessera-ffi/src/lib.rs:310-322`); on macOS this defaults to `~/Library/Application Support/Tessera` (`EngineLibrary.swift:73-87`), independently of the photo volume. This is the appropriate home for a proxy store and local offline journal, not the removable photo volume.

The editor currently treats catalog path as both pixel source and recipe owner. `Engine::develop_disk_snapshot` resolves the indexed original path and reads its recipe/XMP document while taking the destination gate and capturing `OwnerBaseline` (`crates/tessera-ffi/src/develop.rs:1103-1145`). `open_develop_session` decodes that path and rewrites `recipe.source_kind` from the decoded input (`:1003-1015`); the shared session retains the same path and owner baseline (`:1017-1030`). Saves reacquire the original path gate, revalidate catalog path and baseline, then write `.edits` recipe, XMP and rescan the original parent (`:1178-1240`). Gate keys canonicalize the `.edits` directory or its image parent (`crates/tessera-ffi/src/recipe_write.rs:20-43`). Thus an offline proxy alone cannot make an offline edit durable: opening after unmount cannot read the authoritative sidecars or canonicalize the destination parent, and saving writes beside the original.

The existing preview cache is unsuitable as an edit source. `PreviewStore::from_raw_cancellable` selects an embedded JPEG or makes a reduced Bilinear display render and stores JPEGs (`crates/previews/src/raw.rs:17-100`); `develop.rs::store_previews` stores a rendered edited frame keyed by original file bytes and recipe (`:1815-1868`). These are display caches, not editable proxies. The current DNG export path renders a developed image before writing; it must not be reused as a pre-edit proxy or fed back through RAW controls (`docs/coordination/SMART-PREVIEW-STATUS.md`; `crates/tessera-ffi/src/export.rs:1153-1190`). Normal export currently resolves `item.path` for both original-copy and rendered output (`export.rs:1153-1183`); that original-source behavior should remain authoritative.

## Recommended minimal product contract

Keep one logical photo and recipe owner: the original catalog `ImageId`. A Smart Preview is a separate local pixel artifact and source route attached to that ID. It never gets indexed as another photo, never changes `Recipe.image_id` or the saved RAW `source_kind`, and is never a full-resolution export source.

Store artifacts and their manifest under app support, e.g. `Application Support/Tessera/smart-previews/`, with manifest rows in the catalog DB (or a small versioned side database there). Each record should carry original `ImageId`, canonical original locator, original-byte digest and observed file facts, proxy-byte digest, proxy format/version, proxy dimensions/orientation, generation profile/version, and state (`building`, `ready`, `stale`, `missing`, `failed`). The proxy is created in a private temporary file in that directory and atomically published only after successful validation; cancellation/failure removes the owned temporary artifact. The build API takes caller-supplied limits/cancellation and reports progress; no product quota or size threshold is proposed here. The original path is only a locator and decoder-format hint, never the proxy decoder path or owner key.

A separate local Develop journal is necessary for useful offline work. On build while online, capture the effective recipe document and XMP/selection baseline into a versioned local record keyed by original `ImageId`, preserving the sidecar's unknown top-level data and the full owner baseline. An offline editor reads and writes only this local journal while using the proxy pixels. It must retain the original recipe's `source_kind` and process version; the decode/render route is explicitly `SmartPreview`, not inferred from `RawImage::source_kind()`. Save/recovery state must remain durable in app support when the source volume is absent. On reconnect, compare the original sidecars with the captured `OwnerBaseline`; publish only if the baseline still matches, preserving foreign-owned members as current save does. Otherwise keep both copies and report a visible conflict requiring resolution. Do not silently overwrite the original recipe, drop offline edits, or pretend the current `gate_for(original_path)` protects an absent destination.

This offline owner requires a small but important admission extension. A preview-only lease keyed by `ImageId` would not conflict with current path-keyed `gate_for` leases/direct setters; a lease taken before unmount does not solve opening the same image offline after restart. Before enabling offline open, define one stable per-image edit-owner key that ordinary editor opens and direct recipe setters also consult, while retaining current destination-key validation and `OwnerBaseline` checks for online sidecar publication. If that common admission path is out of scope, ship build/discard + visible proxy status first and explicitly defer offline editing; a proxy-only implementation is not offline editing.

Use a `DevelopInput`/source-selection parameter (e.g. `.original` or `.smartPreview`) separately from recipe data. `open_develop_session(image_id, input: .smartPreview)` resolves the artifact from the manifest, validates it, loads the local journal, and obtains the stable owner lease. `DevelopSession` keeps both original locator and proxy pixel path/identity, so save targets the journal offline and the original sidecars online. Preserve a clear supported-control contract for proxy dimensions, geometry, masks, and RAW-only operations; do not silently reinterpret an RGB/Linear-DNG proxy as RAW or claim all controls match. This depends on a yet-unimplemented genuine pre-edit lossy-DNG generator and fidelity/control matrix.

On reconnect, normal full-quality export always uses the original `item.path` and current reconciled recipe. If the original is offline/missing, full-quality export fails visibly as unavailable; it must not substitute the reduced proxy silently. A separate explicitly named “export preview” could be considered later, but is outside this contract.

## UI flow

Add `Library > Build Smart Previews for Selection` and `Library > Discard Smart Previews for Selection` adjacent to existing library actions in `apps/mac/Sources/Tessera/App/AppCommands.swift:175-200`. Route only engine-backed selected RAW items through `EngineLibrary`/`EngineImageReference`; show job progress, cancellation and per-item results. The existing menu is selection/library-oriented, unlike the current focused-photo Develop opener. `AppModel.openDevelop(for:)` already has generation-safe loading, recovery and visible unavailable state (`apps/mac/Sources/Tessera/App/AppModel.swift:2133-2188`): use its opener seam to select Original vs Smart Preview, and explain whether edits are using an offline proxy. Add a preference for automatic proxy use only after build/use semantics are stable; initially explicit per-photo choice is safer.

Show a compact “Smart Preview”/“Original missing” badge and accessibility label alongside current cull/status overlays in `apps/mac/Sources/Tessera/Grid/ThumbnailCell.swift:41-65`. Keep preview display requests (`ThumbnailLoader`) independent from edit-source selection. Status must distinguish `Original available`, `Editing Smart Preview`, `Original offline — preview available`, `Preview stale`, and `Unavailable`; a thumbnail image alone must never imply editability.

## Smallest implementation sequence and acceptance tests

1. Define manifest/journal schema and source-route types; add app-support store APIs with temporary-file atomic publish, caller quota, cancellation and cleanup. Keep source generation behind a separately validated pre-edit lossy-DNG writer.
2. Add stable per-ImageId owner admission and local-journal save/recovery for Smart Preview mode; prove it conflicts with ordinary editor/direct setter and preserves current online `OwnerBaseline`/lease guarantees. Without this gate, do not expose offline-open.
3. Add EngineLibrary/AppModel build/discard/open actions and status badge. Preserve normal export path and existing preview pyramid behavior.

Deterministic tests before UI release:

- Build from a tiny RAW fixture: manifest records the original ImageId/locator/digests, proxy is not indexed as a second photo, source recipe bytes/`source_kind` and sidecars remain byte-identical; cancellation and write failure leave no published partial artifact.
- Discard removes only the selected image's owned proxy/journal artifact, not original or unrelated preview pyramid; repeated discard is safe.
- Open `.smartPreview` keeps original ImageId, recipe `source_kind`/process version and owner baseline while decode uses proxy; regular `.original` still selects original. The proxy never becomes recipe owner or export source.
- With original volume unavailable after app restart, proxy and local recipe journal reopen; save, close, app-reopen and reopen preserve edits. Verify no read/write is attempted under original mount path during this path.
- With original reattached and unchanged sidecars, explicit sync publishes local recipe/XMP preserving unknown owner fields. If recipe/XMP changed externally, conflict is surfaced and bytes remain untouched. If original bytes changed, preview becomes stale and cannot auto-open.
- Ordinary editor/direct setter races with preview-mode lease are rejected; closing/failing open releases the lease safely. Preserve existing `OwnerBaseline`, owner-conflict and save-recovery tests.
- Full-resolution and Original export use original bytes; while offline they return an explicit unavailable error rather than emitting the proxy. Existing JPEG display-preview cache events continue to invalidate independently.
- UI tests cover batch build/cancel/discard, status transitions/accessibility, explicit proxy selection, offline reopen, conflict state and selection-generation safety.

## Open prerequisites

The storage/UI shape is grounded; two product/engine prerequisites remain before implementation can claim Smart Preview behavior: (a) specify and implement the pre-edit lossy-DNG proxy generator and exact supported Develop controls/fidelity at reduced dimensions; existing DNG export is post-develop and current preview fallback is JPEG display-only; (b) settle stable per-image owner admission plus local journal/reconnect conflict semantics. Do not start by changing `DocumentSaveAs` or treating a proxy as a layered-document source.
