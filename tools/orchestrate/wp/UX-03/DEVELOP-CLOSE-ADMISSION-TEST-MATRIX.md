# Core Develop close admission: deterministic acceptance matrix

Against merged mask retention `447772f5` (main snapshot `2aa8ec6c`): current `close()` has no result, invokes `flushPending()` before publishing `closeTask`, sets `closed` and removes listeners before native close succeeds (`DevelopController.swift:159-179`). Settings mutate local/pending state before flush (`:290-331`, `:374-379`, `:385-420`); mask flush returns only Bool and reports failure via callback while retaining rejected suffix (`DevelopController+Masks.swift:89-124`, `:216-298`). Tests need result-bearing close and a synchronous `closing` admission state before callbacks.

## Proposed deterministic cases

1. **Mask write rejection blocks close and remains retryable.** Create a real group, set `onNeedsFlush = {}` and queue one interactive mask parameter. Inject one `setMaskParam` rejection. `close()` returns that same failure, reports it once, does not invoke native `close`, leaves `closed == false`, retains the pending key/value, and leaves listeners attached. A later explicit retry succeeds, sends the retained value exactly once, then closes. This directly verifies the merged mask-retention behavior is connected to close’s result path; `flushMaskPending() -> Bool` cannot be the close result.

2. **Admission blocks edits before any state/backend change.** Gate native close after a successful host drain. While it is in flight, synchronously attempt a settings slider/path patch, `setAsShotWhiteBalance`, a history operation (`undo` or `commit`), a mask-group update, an interactive mask parameter/component, and a brush sample/stroke end. For each category assert rejection is reported, `settingsObject`/pending fields and mask queues remain byte/value-equal to the pre-call snapshot, no wrapped session mutator count changes, and no new flush task is scheduled. Release the gate with an injected native close failure; verify admission reopens and one new edit can be queued and saved by explicit retry. Use category representatives plus a source inventory review; do not try to duplicate every wrapper in one oversized test.

3. **Close cancels stale deferred settings and mask drains on host-drain failure.** Deterministically create a pending settings follow-on from a reentrant `onPatchSent` callback and a mask follow-on from a mask-session callback while each flush flight is active. Capture `deferredSettingsFlush` and `scheduledMaskFlushTask`, configure the next host drain to reject, then call close before either task runs. Assert close returns the host error, native close count stays zero, pending retry data is retained, and both captured tasks settle without another backend attempt or failure callback. Await task handles/continuations; no sleeps or `Task.yield` polling loops.

4. **Synchronous callback reentry joins the published close attempt.** Make the first host mask/settings send reject; in `onFailure`, schedule another `close()` call. Both callers must receive the same failure, only one drain is attempted, native close is never invoked, and there is no recursion/deadlock. This detects publishing `closeTask` only after `flushPending()` callbacks. A parallel `onPatchSent` reentry variant may use the success path if the one test cannot force failure before reentry.

5. **Canceling one waiter does not cancel shared close.** Hold one native close behind an explicit continuation gate, start two close callers, deterministically prove both joined one stored attempt, cancel the first task, and release the gate. The remaining caller receives success, controller closes once, and backend close count is one. Do not require the canceled waiter to return early; the invariant is that it cannot cancel the shared attempt/other waiter.

6. **Successful close is idempotent.** Queue one settings patch and one coalesced mask value; successful close drains each once and closes native session once. A subsequent close returns success without new sends/close calls. Verify listener/callback detachment occurs only after native success and edits after success do not reach the session.

## Mutation-entry inventory to audit against admission guard

Settings/recipe: `set`, `set(path:)`, `apply(patch:)`, `setAsShotWhiteBalance`, `commit`, `undo`, `redo`, `reset`, `snapshot`, `restoreSnapshot`, `checkoutHistory`, `setHistoryStep`, `previewGroupAmount`, `commitGroupAmount`, `applyPreset`.

Mask edits: `addMask`, `addMaskComponent`, `setMaskComponentMode`, `removeMaskComponent`, `deleteMask`, `duplicateMask`, `resetMaskParams`, `retryAIMask`, `updateMaskGroup`, `setMaskParam`, `setMaskComponent`, `beginBrushStroke`, `addBrushSample`, `endBrushStroke`, `addRangeMask`, `addColorRangeSample`, `addAIMask`.

Session-control mutations that are not recipe edits still need explicit close-state policy because they call the same session: `setCropEditing`, `setMaskingPreview`, `setMaskOverlay`, `attachSurfaces`, `attachMaskOverlaySurfaces`. Ensure guards precede side effects: e.g. `updateMaskGroup`/`setMaskParam`/`setMaskComponent` currently remove or replace queued values before `run`; `endBrushStroke` clears `pendingStroke` before calling `run`; `apply` updates live settings before it flushes. Structural mask operations funnel through `run`, so guard there too, but interactive queue methods require their own early guard. `relink` mutates host identity; explicitly decide whether it is rejected while closing. Read-only queries (`value`, `maskGroups`, history queries, surface lookups, thumbnails) can remain available if native close is gated and no listener ownership is released early.

## Test seam constraints

Extend the existing `BlockingCloseSession` wrapper with one-shot settings/mask/close failures, operation counts, and explicit entered/release continuations. Its native-close failure must throw before delegating so retryability is real. Internal test-only read-only access to the shared close attempt/task and deferred-task handles is preferable to timing-based checks. For reentry, callback-created tasks need a deterministic completion signal. Assert exact errors and before/after state; do not equate callback notification or Bool “attempted” with successful drain.
