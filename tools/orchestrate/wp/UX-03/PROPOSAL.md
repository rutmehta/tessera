# UX03 selective Copy Settings: minimum safe slice (proposal only)

Proposed design as of 2026-09-27. Only the pure draft/preview model is approved for implementation; the engine write, durable run, revert and UI below are unimplemented proposals requiring a separate contract review. Spec: `docs/coordination/TASK-BOARD.md` UX-03; `tools/orchestrate/audits/ux/REPORT.md` §3B and P1.3; `docs/01-lightroom-classic-spec.md` §2.17. This is the first deterministic **absolute Copy Settings** operation, not relative adjustment, appearance matching, AI planning, or full UX03 acceptance.

## Existing contract and gap

- `apps/mac/Sources/TesseraCore/Develop/PresetStore.swift` defines `PresetGroup` paths and constructs a partial `DevelopSettings` merge patch; its preset default excludes crop. `DevelopController.applyPreset` (`apps/mac/Sources/TesseraCore/DevelopController.swift:449`) records **one current-photo** history step. `DevelopTools.applyPreset` (`apps/mac/Sources/Tessera/App/DevelopTools.swift:342`) requires the open Develop controller. This is a reusable field-selection vocabulary, not a batch executor.
- `AutoEditSheet` shows provider, selection/view/shoot count and guardrails; `AgentController.itemIDs(for:)` (`apps/mac/Sources/Tessera/Agent/AgentController.swift:209`) derives mutable item indices, and `start` maps them to image IDs before work (`:231-275`). Its queue/revert is agent-specific and not a safe shortcut for deterministic sync. Current Review resume work remains separately owned.
- `AppModel.targetIDs` (`apps/mac/Sources/Tessera/App/AppModel.swift:1485`) falls back to focused/compare-active photo; batch copy must use an **explicit frozen selected set** instead. Source/view/filter and selection may change while a job runs. `AppModel.undo` (`:1311-1368`) routes only Develop, Culling, People and Document history. There is no cross-photo batch undo.
- `engine-api/src/recipe/history.rs:25-43` already has `Author::Sync { from }` and per-photo branching history; `Recipe::edit` records a per-photo step (`engine-api/src/recipe/mod.rs:318-337`). The FFI `DevelopSession.set_settings`/`commit` path (`crates/tessera-ffi/src/develop.rs:1936-1994`) is one open session. No exported deterministic batch-sync API, run ledger, or shared agent/batch recipe-write exclusion exists today.

## User-visible first slice

From Library with at least two explicitly selected engine photos, choose **Develop ▸ Copy Settings to Selected…** (menu/toolbar button; **no single-key shortcut**). A sheet pins the focused photo as **Reference** with filename/thumbnail, displays the source collection/filter and exact frozen target count/names, and excludes the reference from targets. It never silently expands to Current View or Whole Shoot. The user can choose named field groups; initial on-set is White Balance, Tone, Presence, Tone Curve, HSL and Color Grading, while Detail/Effects are opt-in. Crop is off. Geometry, local masks, retouch and generated operations are outside this slice and visibly stated as excluded. Show the exact included groups/values every time, even after prior use. The final button says **Copy 6 setting groups to N photos**.

At Apply, capture stable library identity, source image ID and settings snapshot, target image IDs, and a future **complete relevant write-revision token** for each target. Persist that snapshot as a run ID. Incoming tether frames, selection/filter changes and renames cannot join the run. Skip a target whose recipe changed before its write, whose source identity aliases another target, or whose library has changed. Preserve source settings as a frozen snapshot rather than reading a later edit. Do not write masks/crop. Produce a visible per-target summary: applied, unchanged, skipped/conflicted, failed, cancelled. `Review changed photos` opens only applied targets; it is not an Agent Review queue or an implied acceptance state. `Recipe::recipe_hash` is render-state-only and excludes selection/history/IDs/unknown fields, so it cannot be used as this write-revision token or an ABA guard.

Each successful target would need one named `Copy settings from <reference>` recipe step with `Author::Sync { from }` and a common durable run ID. `Author::Sync` currently stores only `from`; run identity needs an explicit new schema/extension contract. An explicit **Revert this copy** action should reverse only that run's contribution while preserving later manual steps, reporting conflicts/partial outcomes rather than resetting whole recipes. Existing group-amount/revert logic is agent-specific and cannot be assumed to disable an arbitrary Sync group; this needs its own engine design and tests. Ordinary photo-level ⌘Z remains per-photo; Library ⌘Z must not silently target an unseen batch. Keep run summary/revert identity across relaunch under isolated app support. Generic ⌘Z routing and fuller visual review can follow separately.

## Implementation boundaries

1. **Pure draft/preview — approved now:** New `apps/mac/Sources/TesseraCore/Develop/BatchSettingsDraft.swift` owns frozen library/source/target image IDs, explicit focused-reference membership, deduplicated target order, selected `PresetGroup` paths, and partial patch. Tests in `apps/mac/Tests/TesseraCoreTests/BatchSettingsDraftTests.swift` prove changed selection cannot alter a prepared draft; crop/geometry/masks never enter this slice; absent focused reference, empty/duplicate-only targets, malformed source JSON, or no fields block preparation. The model makes no sidecar write or undo claim.
2. **Checked engine write + run record — proposed later:** New `crates/tessera-ffi/src/batch_settings.rs` and export in `crates/tessera-ffi/src/lib.rs`; reuse `catalog::document`, `Sidecar::write_recipe`, XMP/index resync patterns from `crates/tessera-ffi/src/agent_runs.rs:445-485`. For each target, compare a *complete relevant write revision*, not `recipe_hash`, inside the same serialized write decision before applying captured partial settings; record Sync author/run identity and exact outcome. Add a durable run ledger under app support (new `apps/mac/Sources/TesseraCore/Develop/BatchSettingsRunStore.swift` if Swift owns it, or FFI if atomicity requires it). Design run-specific revert before claiming it: an arbitrary Sync group cannot currently be disabled by the agent group machinery. Rust tiny three-photo sidecar tests should cover source unchanged, target conflict, cancel after first committed target, relaunch record, and revert after a later manual mask/tone edit.
3. **Scoped UI/controller:** New `apps/mac/Sources/Tessera/Batch/BatchSettingsController.swift` and `BatchSettingsSheet.swift`; attach only through `AppModel.swift`, `AppCommands.swift`, and `Shell/ContentView.swift`. Controller holds the immutable run snapshot, progress/cancel, results and library owner. The menu is disabled in Review, Document and text-entry contexts; no keyboard shortcut. Swift tests cover source label, count, exclusions, changed selection before Apply, cancel/partial summary, and no action after owner/library switch. Existing Develop/Cull/Review routing stays intact.

**Ownership dependency before later execution:** recipe writes from Auto Edit and open Develop sessions must not race the new batch write. `AgentController.isMutating` and `AppModel.pendingDevelopSaveBarrier` provide useful reads/barriers, but not a shared write lock. Agree a small shared per-image writer exclusion and Agent start guard *after* UX02b owner work lands; alternatively defer Apply behind those active operations with an engine-enforced complete-revision compare/write guarantee. Do not ship a UI-only loop of `openDevelopSession`/`setSettings`/`commit`: it would reopen/render every target and could clobber concurrent edits between a check and sidecar write. This is the main implementation gate, not a reason to modify current Review/Document work now.

**Acceptance:** with three tiny generated photos, a selected reference and two targets, Copy Tone changes only chosen target fields; crop and a local mask stay byte/semantic-equivalent; source and any newly tethered/filtered-out photo remain unchanged. A manual edit during the run yields a skipped conflict, cancel reports the exact committed subset, relaunch restores the run summary, and Revert removes only the sync group while preserving a subsequent manual mask. A keyboard-only pass confirms no single-key operation starts or affects an unseen batch. Full mixed-camera consistency and AI mask recomputation remain later UX03 work.
