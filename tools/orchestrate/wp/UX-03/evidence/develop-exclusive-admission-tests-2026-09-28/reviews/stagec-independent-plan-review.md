## Must-cover implementation hazards

1. **A session-field lease alone is unsafe on the writer-thread Drop path.** `DevelopSession::drop` closes `Shared` then calls `stop_writer` (`crates/tessera-ffi/src/develop.rs:2216-2220`). `stop_writer` signals shutdown but deliberately does not join itself when Drop runs on the save worker (`:2228-2240`). The writer loop can still have a due save to finish; it drains `Some(due)` even when `shutdown` is set and exits only at `None if shutdown` (`:1630-1678`). Therefore a lease stored only in `DevelopSession` can disappear when the callback drops its final session Arc, before the detached worker finishes publishing. Keep fallback ownership alive through the writer task/`Shared` lifetime (or equivalent worker-owned guard), and release only after the loop actually exits. Preserve the existing self-join avoidance; do not make Drop join its own thread. Also check whether the current Drop ordering (`Shared::close` before `stop_writer`) can overlap preview storage with renderer shutdown; explicit close already uses flush → stop/join → shared close (`:3017-3022`).

2. **Every Develop full/repair write must authenticate the original lease state, not reacquire an arbitrary current gate.** Today `save_develop` and `repair_develop` independently call `gate_for(path)` then `begin_write` (`develop.rs:1140-1144`, `1202-1206`). `gate_for` derives a key afresh (`recipe_write.rs:21-59`), resolving `.edits` via filesystem canonicalization. A session lease token should carry both the retained `Arc<GateState>` and checked owner identity; the guarded save must compare the token/state identity and re-run the existing `check_image` destination-key comparison (`recipe_write.rs:120-132`) before the first publish. Otherwise a moved/repointed destination could send the session through a different `GateState`, or a stale token could authorize/clear a later owner. This is path/key validation inside the declared in-process destination gate, not a request for filesystem CAS or a broader alias database.

3. **Acquire owner plus disk snapshot without a self-deadlocking rollback.** Current open obtains the path, then `develop_disk_snapshot` locks gate → catalog, revalidates the ID/path, and captures recipe plus `OwnerBaseline` (`develop.rs:998-1001`, `1077-1101`). Stage C needs that same critical section to reserve the owner and capture the snapshot. If it sets the owner slot, constructs an RAII token whose `Drop` reacquires the gate mutex, and then `?` returns from catalog/path/baseline work while that mutex guard is still live, token Drop can deadlock trying to clear itself. Materialize the token only after the snapshot closure succeeds, or clear the tentative owner directly under the already-held guard on failure. Keep the short mutex guard separate from the longer-lived reservation: release the guard before RAW decode, render/model setup, or worker spawn, while the owner slot remains reserved. Test a deterministic failure after reservation but before session transfer and prove a subsequent open succeeds.

4. **Retain the lock order and do not wait on a worker while holding the destination mutex.** Existing writers use destination-gate → catalog order (`lib.rs:413-416`, `449-452`; `develop.rs:1142-1145`, `1204-1207`). `open` currently releases its initial catalog lookup before acquiring the gate, then reacquires catalog beneath the gate (`develop.rs:1077-1090`). Preserve this order; `gate_for` also uses the process-global `GATES` mutex (`recipe_write.rs:42-59`), which must be released before taking the per-key state mutex. Never hold the destination mutex while doing `RawImage::open`, waiting for `flush_inner`, joining the worker, or stopping rendering. `save_now` currently snapshots `State` and `owner_baseline` before entering Engine save (`develop.rs:1715-1725`); preserve that no-state-lock-while-waiting boundary.

5. **Differentiate exclusive whole-recipe replacement from selection writes.** Both public Engine paths currently use `gate.begin_write()` (`lib.rs:407-424` and `438-452`). Lease admission must reject `set_recipe_json` while a Develop owner is active, but still allow `set_selection`; the Develop publisher intentionally merges the current selection into recipe/XMP (`develop.rs:1150-1179`). A blanket rejection in `begin_write` would regress selection. The test should check selection persists both while the lease is held and after a later Develop save, while a validated direct `set_recipe_json` returns the admission conflict and leaves recipe/XMP bytes exactly unchanged. After successful close/release, direct replacement should work again.

6. **Release is a successful-close-only transition; failed close and repair retain the same owner.** `close` has one leader plus concurrent waiters, marks `closing`, flushes, joins the worker, and closes render state; failed flush restores open state (`develop.rs:2991-3030`). The existing partial-publication retry test demonstrates recipe written/XMP failed, followed by repair on retry (`:3991-4048`). Keep the lease on the failed attempt so a second Engine cannot open between partial recipe publication and auxiliary repair; only the leader releases after final repair, joined worker, and render close. Waiters share the same close outcome and must not each release. Existing retained-Arc checks after successful close (`:4083+`) should be paired with admission assertions before/after release.

7. **Identity exhaustion and stale-release behavior need checked, deterministic tests.** `WriteGuard` currently rejects `u64::MAX` while locked before its Drop increments epoch (`recipe_write.rs:127-132`, `178-183`). Use a separate checked owner generation (do not reuse the write epoch, because selection writes advance that epoch) and fail closed on exhaustion. Test old token A cannot authorize a write or clear token B after close/reacquire on the same retained `GateState`; compare both Arc/state identity and owner ID. Include wrong-image/wrong-key token use, with the existing same-stem `.jpg`/`.raw` recipe destination collision semantics preserved (`recipe_write.rs:19-40`).

## Plan wording and scope correction

The plan says the current baseline “retains unknown nested owner members” and also says it rejects before publication. The actual behavior is fail-closed, not persistence/retention: `OwnerBaseline::from_disk` records `has_unrepresented_nested` (`develop.rs:1241-1287`), and `save_develop` returns a conflict when either baseline/current has such fields (`:1153-1161`). Please change the description to “preserves latest top-level unknown document fields; rejects publication when unsupported nested owner fields are present.” Existing fail-closed tests cover both preexisting and foreign nested fields (`:3805-3853`).

The bounded lease is an in-process fence for the declared Engine APIs: `Engine::set_selection`, `Engine::set_recipe_json`, and Develop save/repair. It does not fence direct `Sidecar::write_recipe` callers, other app/agent/import/export writers, or external processes; the existing `OwnerBaseline` remains a conflict defense for those changes. Keep the proposal explicit about that boundary and do not describe it as external filesystem CAS or all-writer serialization.

## Minimum deterministic additions beyond the current plan

- Failed open after reservation (RawImage decode or injected post-snapshot error): no writer is constructed, then same destination immediately opens.
- Failed recipe/XMP repair close: owner still blocks second Engine; retry repairs and drains; open succeeds only after success.
- Drop while writer callback drops the final session Arc on the worker: pause a save with a deterministic barrier, trigger final Arc drop, verify second open remains blocked until the writer loop reports exit, then opens. This specifically covers the self-detach path absent from the current tests.
- Token A vs B on same `GateState`: stale save rejected and stale Drop leaves B active.
- Direct recipe setter conflict with exact recipe/XMP byte oracle, plus selection-success control while lease held.
- Destination revalidation while an old token exists: re-point/change the indexed path/key under a deterministic seam, prove old token cannot publish through a newly resolved gate; do not claim arbitrary external filesystem races are prevented.

No other blocker to the bounded in-process lease direction found. The plan's out-of-scope external/all-writer limitation is appropriate once the unknown-nested wording is corrected.
