# Stage C Swift recovery and admission readiness — independent source audit

2026-09-28. Reviewer: hdr_nonuniform_diagnosis. Source-only: no compiler, native probe, test, app, or GUI was run; no product source was changed. B was not contacted.

## Decision

The current A-owned Swift recovery design is sufficient to proceed with the bounded native Stage C implementation. I found no demonstrated UI product blocker requiring another recovery/navigation rewrite before that work. The old lease proposal's descriptions of discarded close errors and eagerly released controllers are historical and do not describe current source.

Before activation/integration, add a small Swift behavioral gate for the newly expected native **open admission failure**: injected opener rejection must publish the current error, settle its pending ownership, permit leaving the workspace, and permit a fresh successful open when the conflict is gone. Add a held/superseded failure control proving an older opener cannot replace a newer owner's loading/ready/error state. This is a missing direct regression, not a demonstrated source defect or a demand for new UI. It can accompany Stage C validation; it need not block native tests-only preparation. The native lease must separately prove failed-open cleanup and release only after successful close/drain.

## Open rejection, second editor, and pending ownership

`apps/mac/Sources/TesseraCore/DevelopController.swift:172` propagates `openDevelopSession` errors. `AppModel.swift:2133` reuses an already attached matching controller, rejects a matching local recovery/open/reservation through `canOpen`, and otherwise calls the asynchronous opener. The catch at 2178 checks cancellation, active token, library generation/identity, and focused image before publishing `.unavailable(error.localizedDescription)`. The deferred settlement at 2162 calls `settlePendingDevelopOpen` and `finishOpen` on every exit. Settlement at 2193 preserves an already published `.unavailable` and cannot clear a newer token.

`DevelopRecoveryCoordinator.swift:222` covers retained sessions, pending opens, and scoped reservations using owner/image identity plus canonical source-path/inode aliases. This is intentionally a local recovery/admission registry, not proof of process-wide native lease ownership. A conflict from a second Engine or another native client therefore legitimately reaches the ordinary throwing-opener path. The source does not swallow that error or install a nonexistent controller. Its produced-controller path (`AppModel.swift:2167`, coordinator 252–292) retains late/canceled successful opens, transfers exact controller/owner identity, and closes them through recovery; a failed cleanup remains recoverable.

Errors are visible through `photoEditAvailabilityHint` (`AppModel.swift:1130`) and `Inspector/PhotoEditInspectorView.swift:28`; editing controls use `.ready`. There is no dedicated automatic lease-expiry retry or new admission-failure Retry button. Existing explicit navigation/re-entry invokes `Loupe/LoupeView.swift:71–112` and can try again; leaving a failed open with no produced session is not blocked by a recovery record. A new UI button is not necessary for correctness of this bounded activation.

Existing tests cover local same-photo refusal after failed close (`DevelopRecoveryCoordinatorTests.swift:19,57`), pending cancellation and owner changes (`AgentReviewOwnershipTests.swift:594–636`), and produced/stale transfer cleanup (`DevelopRecoveryStateTests.swift:135,194,222,252`). They do not directly demonstrate the current, noncancelled opener throwing an admission conflict and then successfully reopening. That is the narrow test gate requested above. Prefer observable `.unavailable` reason, no controller/recovery/reservation, unchanged library/focus, and opener call count/new controller over private token assertions. Exercise actual user navigation out/re-entry; do not merely call a private cleanup method.

A controller initializer can also throw after native construction (`DevelopController.swift:179–190`). Its event owner is weak (`:719`), so there is no evident listener→controller strong ownership cycle in this path. Current native Drop closes/stops the worker (`crates/tessera-ffi/src/develop.rs:2216`). The Stage C implementation must extend that fallback to release the lease correctly; a Swift catch alone cannot prove native lease release. This is a native lifecycle test requirement, not evidence that the current UI loses a dirty installed controller.

## Failed close, retry, ownership, and reopen

`DevelopController.close` (197–257) joins one close task; pending-patch drain or native close failure resets `closing`, reports failure, and retains session/listeners/callbacks. Only success marks closed and removes callbacks. `AppModel.closeDevelop` (2270) requests close without clearing the installed controller/owner. `publishDevelopClose` (2246) checks exact session identity, retains failed editor state, and clears the installed controller only after successful native completion.

The coordinator's Record strongly retains both EngineLibrary and controller (114–138). `requestClose` (300), `retryClose` (329), and `finishClose` (339) share an in-flight result, retain the failed result without automatic retry, and remove the record only on success. This is compatible with a native failed close retaining the same lease. Keep Editing (`AppModel.swift:434`) cancels the blocked navigation intent; it does not discard the native owner or claim a save. Retry uses the same session and commits a still-current destination only when the registry and reservations have drained (403–431). Native success must mean writer drain/join and lease release before returning, making fresh open safe after this UI cleanup.

`DevelopRecoveryStateTests.swift:20,66,92,116` cover strong retained owner/controller, joined failure, ownerless fail-closed behavior, and admission held until gate finish. `DevelopRecoveryAdmissionBehaviorTests.swift:21` requires the same controller/workspace after failure and a distinct fresh controller after successful Retry. Lines 62 and 90 cover recovery-owned status cleanup and unrelated newer status preservation. Accepted GUI evidence also exercises Keep Editing and persistence/reopen. No new Swift discard flow is needed merely to enforce second-editor admission; Keep Editing is not represented as discard.

## Folder, window, and dependent navigation

`AppModel.navigateAfterDevelopSave` (339–400) captures the owner, load generation, and navigation intent, holds a recipe reservation, and only commits the current destination after successful close and no unresolved sessions. Superseding destinations replace the pending intent without orphaning the old controller. `openFolder` (594–615) enters this gate; only `commitOpenFolder` (624) starts replacement loading. Old callbacks cannot publish into a new generation. The folder callback reentry/once-only test is `DevelopRecoveryAdmissionBehaviorTests.swift:476`; retained old-owner tests are in `DevelopRecoveryStateTests.swift:20` and owner-sensitive pending-open tests in `AgentReviewOwnershipTests.swift:625`.

The production app uses one main `Window("Tessera", id: "main")` and `AppModel.shared` (`App/TesseraApp.swift:15–20`). `RecoveryWindowCloseGuard.swift:48–81` blocks that main window while its coordinator has unresolved sessions or reservations and preserves the old window delegate. `RecoveryWindowCloseGuardTests.swift` covers blocked close, unrelated window isolation, forwarding, and stale cleanup; the saved GUI evidence confirms the real close button was vetoed during failed save. This source does not promise global multi-window Quit composition, and Stage C's bounded native admission does not introduce that separate requirement.

A-owned dependent read/write callers use the result-bearing reservation (`AppModel.swift:2285`), so an unresolved failed editor is not treated as a completed save. The accepted full suite covers adjacent Review/Layers/Agent behavior. Direct `setRecipeJson` has no hand-written Swift caller found under `apps/mac/Sources` (only generated bindings); native setter admission therefore adds no newly unhandled direct AppModel setter call site identified by this audit. This is not an audit of every native Agent/Cull/import writer.

## Native coordination and limits

Luna's stated bounded plan matches this UI contract: destination-keyed second-editor/direct-setter admission, selection allowed, read-only histogram unleased, lease/baseline acquisition under gate→catalog/path revalidation, failed-open release, failed-close retention, successful-close drain before release, and Drop fallback. I sent Luna the direct-open-failure regression gap and the finding that current recovery product prerequisites are already implemented. Clarification: “release before decode” must mean releasing the gate/catalog critical section, not releasing the acquired editor lease.

This review accepts source readiness, not the as-yet-unimplemented Stage C runtime. It does not approve global Quit, crash durability, filesystem CAS, all-writer serialization, B's Document/Save As behavior, performance, or automatic conflict resolution. Native failed-open, close/drain, stale-identity, setter rejection, selection merge, and histogram controls still require exact-checkpoint validation. No broad UI rewrite or new B dependency is justified by the evidence reviewed here.
