# Develop writer admission: staged, failure-safe proposal

Status: source-only amendment; no product implementation or validation. The destination gate currently covers only two Engine writers. **Do not activate a Develop lease until the close-failure contract below is implemented and tested.** Batch Apply remains blocked.

## Current failure paths

`DevelopController.close()` discards `session.close()` errors with `try?`, marks itself closed, and removes listeners before the backend result (`apps/mac/Sources/TesseraCore/DevelopController.swift:156-174`). Its `flushPending()` removes a coalesced patch before `setSettings` succeeds (`:379-393`). `AppModel.closeDevelop()` clears the controller, owner, and failure callback before awaiting close (`apps/mac/Sources/Tessera/App/AppModel.swift:1752-1781`). `pendingDevelopSaveBarrier()` and `prepareForAgent()` return `Task<Void, Never>` (`:1022-1030`, `:1787-1810`), so dependent Layers, Review, and Agent work can proceed after failed saving.

Rust `DevelopSession::close()` calls `flush()`, then `shared.close()` **even when flush fails** (`crates/tessera-ffi/src/develop.rs:2424-2429`). `shared.close()` closes rendering; this is not currently a retryable editor state. The save worker clears `due` before writing and stores one error string (`:1202-1231`); `flush()` consumes that error (`:2400-2419`). A second flush with no new edit can report success without repairing failed XMP/index.

## Stage A — standalone save-retry correctness, no lease

This is the smallest independently testable backend repair. Track a persistent retry-pending phase separately from the most recent reported error. If the recipe rename succeeds but XMP or index fails, record the published recipe bytes as the new baseline and retain auxiliary-work debt. The first flush reports the real failure; a later flush with **no new edit** retries and verifies XMP/index rather than returning false success. Retain the dirty recipe or a reconstructible packet until repair completes. If the retry observes a foreign owner edit, stop rather than overwrite it. Preserve the original error and repair result as distinct observable outcomes. No new writer admission, batch API, or global transaction claim.

Tiny deterministic test: inject a failure after recipe rename and before XMP/index, assert the first flush fails and outputs are not falsely declared complete; remove the fault, flush again without editing, and verify the actual recipe, XMP, and index state. Repeat with an intervening foreign Develop-owned edit and assert no overwrite. This requires a narrow post-recipe-write fault seam; merely checking that retry returns `Ok` is insufficient. Recipe, XMP, and index still are not a multi-file transaction; no parent-directory fsync or rollback is claimed.

## Stage B — close failure contract before lease activation

Backend close must leave a failed save **save-capable and recoverable** instead of unconditionally calling `shared.close()` on a flush error. Define retry, cancellation, and explicit discard semantics, and keep the worker alive until retry/discard; an idempotent successful close drains and joins it. Swift `DevelopController.close()` must return an error/result, retain a rejected coalesced patch, and avoid setting `closed`/clearing recovery ownership before success. `AppModel` may detach the view during navigation but must keep a strong controller/session plus captured `EngineLibrary` and image ID in a recovery entry, surface the failure, and offer retry or explicit discard. Repeated close callers share the same in-flight result. On successful retry/drain only, remove the recovery entry and listener ownership. This is asynchronous and does not block the MainActor.

Captured save barriers must propagate success/failure. Layers, Review preview, Agent, and other barrier consumers must withhold dependent reads/writes when closing failed; they must not treat a completed `Task<Void, Never>` as a successful save. Test with an injected deterministic failure, no sleeps/network: navigation retains the dirty edit and correct old-library owner; the error is visible; retry really saves then cleans up; repeat close shares its outcome; explicit discard is the only path that abandons dirty work; failure blocks each dependent handoff; rejected `setSettings` keeps its patch. Also test cancellation and a folder switch without orphaning recovery.

Candidate Stage A: `crates/tessera-ffi/src/develop.rs` and focused Rust tests. Candidate Stage B: the same backend close lifecycle, `apps/mac/Sources/TesseraCore/DevelopController.swift`, `apps/mac/Sources/Tessera/App/AppModel.swift`, Layers/Review/Agent barrier consumers, and focused Swift tests. Stage A can merge alone. Stage B must be complete before lease-induced conflicts can reach users.

## Stage C — Develop lease and owner conflict, only after Stage B

`Engine::open_develop_session` reads `catalog::document`, then normalizes `recipe.source_kind` after `RawImage::open` (`develop.rs:823-836`). Capture the initial **disk** owner fields before normalization, else a legacy RGB document falsely conflicts on its first flush. `Shared::save_now` snapshots session state and `Engine::save_develop` reloads the latest document, then overwrites `process_version`, `settings`, `history`, and `source_kind` (`:1234-1244`, `:922-949`). Preserve its current merge of latest selection and unknown members. The owner baseline comprises those Develop-owned fields; a full raw revision would make benign rating/mark changes conflict.

Extend `recipe_write::GateState` with one live Develop owner and monotonic lease identity. The lease retains its `Arc<GateState>` so weak-table pruning cannot reset the identity. Acquire by resolved recipe destination; under gate → catalog order, revalidate image ID → path and capture the pre-normalization disk baseline. Release the gate before decode/render/wait. Second editor open and direct `set_recipe_json` fail fast while leased; selection remains allowed. A failed open releases the lease. `save_develop` takes the gate before catalog, validates lease and current path, compares current disk owner fields with the last published baseline, and merges into the latest document. Do not hold `Shared::state` or `SaveState` while waiting for the gate. Unknown raw bytes and full revision remain separate future batch work.

`Engine::depth_histogram` currently opens a temporary full Develop session (`develop.rs:819-820`). Split its read-only saved-recipe construction/borrow from writer lease acquisition before enforcing one editor per destination. Histogram must work during an active editor without minting another writer lease; document whether it reads saved or live recipe, and preserve current saved-recipe behavior unless deliberately changed.

All mutators, commits, and save-scheduling entries must atomically reject closing/closed. A retained `Arc<DevelopSession>` must not enqueue after writer shutdown or hang in `flush()`. Close drains and joins the worker off the MainActor, then releases the lease; Drop is the fallback release on every path. A stale lease ID cannot publish. Failed close retains Stage B recovery ownership until retry or explicit discard. Gate → catalog lock order is mandatory; no holder waits for flush, join, render, or lease expiry.

Stage C tiny tests: legacy RGB first flush; second-editor/direct-setter conflict; orthogonal selection during Develop; read-only histogram while editor active; held-gate admission while unrelated same-Engine write completes; retained Arc after close cannot mutate/enqueue/hang; close drain before release and reopen; foreign owner-field edit conflicts without touching newer disk bytes; Stage A post-recipe failure/repair remains green. Use deterministic seams, no sleeps or MainActor blocking. External processes and unadopted Agent/Cull/import/merge writers still bypass this gate; it is not filesystem CAS or all-writer serialization. Batch UI/API, complete batch revision, and run-specific revert remain outside scope.
