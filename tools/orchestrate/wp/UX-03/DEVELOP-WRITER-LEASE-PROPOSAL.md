# Develop writer admission: next bounded backend slice

Status: source-only proposal, **no implementation or validation yet**. Prepared against main `34963862` after the two direct Engine writers gained the destination gate. Batch Apply remains blocked.

## Current overwrite path

`Engine::open_develop_session` resolves the image path and reads `catalog::document` into a session recipe without a destination gate (`crates/tessera-ffi/src/develop.rs:823-831`). The session keeps that recipe across interactive edits. A debounced worker clones it in `Shared::save_now` (`:1202-1244`); `Engine::save_develop` then loads the latest document and replaces its `process_version`, `settings`, and entire `history` from the older session snapshot (`:922-949`). It preserves current selection and unknown recipe members, and takes the maximum of the two ID counters, but neither its Engine-local catalog mutex nor the newly merged gate serializes it against a second Engine. A later session flush can therefore overwrite newer Develop state. `flush` waits on the save condition without holding `Shared::state` (`:2400-2419`). `close` calls `flush` and closes rendering (`:2424-2429`); the save thread is joined only in `DevelopSession::drop` (`:1717-1728`). Swift `DevelopController.close` calls backend `session.close()` off the main actor but currently discards its error with `try?` (`apps/mac/Sources/TesseraCore/DevelopController.swift:156-174`).

## Smallest safe contract to implement next

Extend the existing `recipe_write::GateState` with one active Develop lease slot and a monotonic lease identity. Keep the weak gate table: a live lease holds a strong `Arc<GateState>`, as a retained revision does. Acquire a lease by resolved recipe destination while opening; reject a second Develop session for that destination. Under gate → catalog order, revalidate `image_id` to the same path and read the initial document. Release the gate before image decode, renderer/model setup, or any wait. A failed open releases the lease. A lease ID must cease to authorize saves once released; a stale `Shared` cannot write using an old ID.

Adopt `save_develop` into the same gate, acquired **before** the catalog mutex and held through recipe/XMP/index work. `save_now` snapshots session state under `Shared::state`, releases that mutex, then enters the gate; it must not hold `Shared::state` or `SaveState` while waiting. Under the gate, verify lease ID, revalidate current index ID → path, and compare the current disk document's **Develop-owned** baseline with the last successfully published baseline for this session: `process_version`, `source_kind`, `settings`, and `history`. If another writer changed those fields, return an explicit conflict before writing. The worker's own successful recipe write advances the baseline, even if later XMP/index work fails, so a retry does not misclassify its own partial commit as a foreign edit. Keep the existing disjoint merge: `set_selection` can run during the lease; its decision/grade/mark survives a later Develop save. Do not use the full raw revision as this owner comparison, because a benign selection or descriptive metadata change alters raw bytes and would make routine rating during Develop fail. Preserve the full raw revision separately for a future batch compare-and-write.

`Engine::set_recipe_json` should inspect the lease under its already-held destination gate and fail fast while Develop owns that destination; it must not wait for session close. The same fail-fast check is required of a future batch writer. Do **not** make selection wait for the lease. Open, save, direct setter, and selection use gate → catalog order, never catalog → gate. A caller holding the gate must not synchronously wait for `flush`, `close`, writer join, rendering, or a lease to end. Close should drain pending saves and join the worker off the main actor before releasing the lease. `drop` must perform the same release after joining on all paths. A save attempt using an invalidated lease, including one scheduled after close, must fail before disk publication; `flush` on an already closed/drained session must not wait on a stopped worker. Session mutator error semantics after close and Swift presentation of a failed flush remain separate user-facing work.

Recipe, XMP, and index still are not one transaction. A recipe rename can succeed before XMP or index fails. The proposed save result needs to carry both the recipe-commit boundary and any auxiliary error so the session baseline follows bytes already on disk while the caller still receives a failure. No parent-directory fsync or rollback is claimed. External processes and unadopted Agent/Cull/import/merge writers can still race inside this gate; the owner-baseline check detects an earlier foreign Develop change but cannot guarantee exclusion of a concurrent bypass writer.

## Test-first acceptance (tiny 2×2 JPEGs)

1. Open Develop, make a real history edit, then from another Engine call `set_recipe_json` for that image: it returns an explicit conflict without writing. The current UniFFI bridge exposes `BridgeError::Failure { message }`, so this is not yet a typed Swift conflict. `set_selection` from that second Engine still succeeds during the lease; after Develop `flush`, disk recipe, XMP, and index contain both the edit and the new rating/mark.
2. A second open of the same destination fails while the first lease is live. With a test-only blocked save boundary, `close` does not return or release the lease until the writer drains; a lease probe fails fast rather than waiting while holding the gate. After close, the old lease ID cannot publish; a new session may open. No sleeps or synchronous main-actor wait.
3. An explicitly unadopted sidecar writer changes a valid Develop-owned field/history between session open and flush. Flush reports conflict, and the newer disk state remains byte-for-byte unchanged by the stale session. A selection-only disk change is accepted and merged. This proves conflict detection, not exclusion of an overlapping external writer.
4. Hold the destination gate and observe a test-only contended gate admission from the Develop save worker. While it is blocked, an unrelated destination write through the **same Engine** completes, proving the worker did not keep the Engine catalog mutex while waiting. Release the gate and verify the save result.
5. Inject a failure after the recipe rename but before XMP/index completion. Flush reports that failure; a retry tracks the already-written recipe baseline and repairs downstream outputs without overwriting a newer foreign Develop edit.

Candidate file map: `crates/tessera-ffi/src/recipe_write.rs` (lease identity/admission), `crates/tessera-ffi/src/develop.rs` (open, save baseline, close/drop drain), `crates/tessera-ffi/src/lib.rs` (`set_recipe_json` fail-fast lease check), and one focused internal test module. No new UniFFI batch method, Swift UI, Agent mutation, or arbitrary Sync-history revert in this slice. The user-facing batch operation remains unavailable until the other writer bypasses, failure presentation, complete write revision comparison, and run-specific revert contract are handled.
