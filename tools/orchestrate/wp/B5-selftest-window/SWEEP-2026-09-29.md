### vector FAIL (step 372): real regression, not a background-window artifact

```
vector-selftest: check fill-only drag previews coalesce to frames FAIL 1
vector-selftest: fill-only affine drag on 20 MP: previews 60, frames 1, latency n 1 median 1287.8 ms …
fill-only preview engine calls (ms): 0.2–0.7 each (60 calls); frame render (ms): ["143.5"]
stroked-dashed affine drag latency on 20 MP: n 1, median 1425.1 ms; frame render (ms): ["313.1"]
```

Document frames are not paced by the host window or a display link. The engine's render thread renders after each
mutation and calls `on_frame` (`crates/tessera-ffi/src/document/render.rs`, `worker_loop`). Whether the window is
occluded doesn't matter. What changed is `Signal::request_frame` (render.rs:492, added in `bb020485` "bounded frame
cancellation"). Every mutation cancels the frame that is being rendered (`active_frame.cancel()`), and `begin_frame`
(render.rs:500) cancels it again. A draft preview now returns in about 0.3 ms and arrives every ~16 ms, while a
full-canvas fill-only frame takes about 143 ms. So every frame is cancelled before it finishes, and only the frame
after the pointer stops is published: 60 previews, 1 frame, 1.3 s latency. There is no forward-progress guarantee.
B5-11's measurement on 2026-09-27 02:19 was taken before `bb020485` (18:09 the same day). It recorded 51 previews
and 50 frames (median 517 ms), with the check passing. A foreground run would also starve, because nothing
host-side paces these frames. User impact: while a shape (or any layer with a slow render) is dragged continuously,
the canvas pixels freeze until the pointer pauses.

Likely fix (engine, not done here): don't cancel an in-flight frame from `request_frame` for interactive/draft
mutations. Alternatively, cancel at most once per N ms, or cancel only when the frame is older than a budget, so
that some frame completes during a steady stream of edits. A test is needed that sends mutations faster than
render time and expects at least one published frame.

**Step 372 check, proposed change:** the check is already meaningful. It fails for the right reason. Driving
frames from the self-test's display link or forcing redisplay would not change anything, because the engine publishes
the frames and the viewport never requests them. So nothing was changed in `VectorSelfTest.swift`. When render.rs is
fixed, this check should pass in background runs without changes.

Export/print not quitting: `AppModel+Output.swift:158` and `:182` call `NSApp.terminate(nil)` synchronously
from the exporter's `onFinish` / the print completion. Those callbacks run inside the job `Task` before its
`defer { gate.finish() }` (`ExportController.swift:327` vs `onFinish` at `:363`; `PrintController.swift:214` vs
`completion?(ok)` at `:267`). So `applicationShouldTerminate` (`TesseraApp.swift:303`) still sees
`developRecovery.hasActiveReservations` and returns `.terminateCancel`. The fix is to defer the terminate a runloop turn
(`DispatchQueue.main.async { NSApp.terminate(nil) }`) or to call the callbacks after `gate.finish()`. Timing
(`TimingSelfTest.swift:66`) probably hits the same guard through the open develop session (`hasUnresolvedSessions`).
