# WP M5-35 — URGENT: smart-filter cache deadlock in parallel tile rendering

Machine B (B5-12) hit an app hang at 0 % CPU: `Compositor::filtered_source` (crates/compositor/src/render/smart_filters.rs:286) holds its cache lock while a smart-filter stage runs on rayon; a parallel tile render that re-enters the same cache (another tile, or a nested stage) waits on the lock while the lock holder waits on the rayon pool → deadlock. Minimal repro and details: `git fetch origin wp/B5-12 && git show origin/wp/B5-12:tools/orchestrate/wp/B5-12/NEEDS.md` (item 1). Exposed paths: the CPU backend, the layer-style CPU fallback in crates/tessera-ffi/src/document/render.rs, native_filtered, and any caller rendering tiles in parallel over a document with smart-filter stages.
Fix in crates/compositor: never hold a cache lock across stage computation. Use a per-key single-flight (e.g. `OnceLock`/`OnceCell` per entry, or an entry state machine Pending→Ready with a Condvar that waiters block on *outside* rayon's pool, or compute outside the lock and insert with a double-check), and audit every other cache in crates/compositor/src/render/** and resident/filters.rs for the same pattern (lock held across work that may use rayon or re-enter the compositor). Add a regression test that reproduces the deadlock deterministically on the pre-fix code (e.g. a smart-filter stage that itself renders tiles in parallel, with a timeout that fails instead of hanging the test run) and passes after. Keep pixel output identical.
