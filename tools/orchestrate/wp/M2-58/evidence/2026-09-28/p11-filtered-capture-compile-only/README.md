## Source review and future capability limits

The helper rechecks its own screen-capture permission without requesting access. It restricts app identity by isolated bundle prefix, BetterSSD app path, PID and launch date, requires a foreground regular app and matching visible layer-zero window, and requires a bounded ROI inside that window and display. The filter includes only that exact selected window, excluding desktop/dock, menu bar, cursor and audio. This excludes unrelated application content from the stream; it cannot establish actual desktop occlusion or uninterrupted visibility. No protected prompt is accessed.

The source checks output configuration serialization before start, saves only complete BGRA frames with positive displayTime, validates dimensions/layout and successful pixel lock, rejects a null base address, strips row padding and retains raw metadata/hashes. It caps saved frames at 8 and metadata callbacks at 256. Identity/foreground/current geometry is checked before saving. Failures stop acceptance and produce a nonzero result; disk-write failure can necessarily prevent its own error artifact. A saved frame may precede a metadata-write failure, so only a successful final result plus matching metadata can qualify a capability attempt.

Installed public SDK SCStream.h documents SCStreamFrameInfoDisplayTime as mach absolute time when the frame was displayed by WindowServer; the helper retains that integer, callback mach ticks, and mach timebase numerator/denominator. Its sourceRect is expressed in display logical points, with a display-origin translation for global window containment. Raw contentRect, screenRect and scale attachments are preserved. No conversion to another clock, pixel/revision matcher, or latency evaluator is implemented.

Temporal limitation: the identity/window guard samples current state at callback-save time, not the historical state at displayTime. It does not reject stale/out-of-order displayTime values or prove geometry/foreground held continuously between the frame event and callback. It also outputs roughly one pixel per ROI point. Those limits are acceptable for the explicitly filtered API/pixels/timestamp capability, but insufficient for an exact-detail or <=200 ms window-server display oracle. A future oracle needs validated frame-time ordering, stable geometry over its qualified interval, correct scale/mapping, expected detail/revision matching, and clock/input association.

Bound limitation: enumeration/start/capture/stop have 2/2/2/1-second pump deadlines, and a background watchdog exits after 9 seconds once armed. The watchdog is armed only after reading config and creating the output directory. Thus this is not a hard process-start deadline and can block before arming on initial filesystem work. Future execution should use an external bounded launcher; do not characterize the current source as independently guaranteeing <=10 seconds from process launch. No source change or runtime was performed in this audit.
