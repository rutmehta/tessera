# EXP-45 gain-pattern isolation proposal (read-only)

ICC-only reciprocal copies are negative. The frozen A four-stop auxiliary JPEG (A file SHA-256 `bb08f44d…`) decodes to an **exact 80×16 vertical step**: every row has gain sample `0` for x=0–39 and `255` for x=40–79, with 640 pixels of each value, min/max 0/255. No seam values or y variation. This follows from reading its auxiliary JPEG bytes beginning at SOI offset 1436; the source fixture `crates/export/tests/gain_map.rs:671-724` expects dark plateau x<40 and bright plateau x≥40 after resize/sharpen. The pinned Google reference gain PGM/JPEG is uniformly 255 for all 1,280 pixels.

The exact-white Google control `bright-white/reference-16-bright255-explicit.jpg` uses unchanged `bright-white/base-bright255.jpg`: x=0–25 has RGB 64, x=26–52 RGB 128, and x=53–79 RGB 255 in every row. Its full-gain 255 region includes the entire white patch x=53–79. Its metadata `fixtures/cap-16.cfg` declares minContentBoost=1, maxContentBoost=16, gamma=1, offsets=0, hdrCapacityMin=1, hdrCapacityMax=16, useBaseColorSpace=1. These correspond to the same ISO log2 range 0..4 used by A. Thus replacing only the *gain input samples* with A's 0/255 step leaves all white pixels under maximum gain. A correct 16× expansion should still have a ~16 bright peak; x=0–39 should stay SDR and x=40–52 should receive 16×. This is a stronger test than merely observing whether an all-255 map reaches 16.

One bounded input experiment, if authorized:

1. Copy the pinned `fixtures/gain.pgm` P5 80×16 file, preserving its header; change only sample bytes at x=0–39 to 0, leave x=40–79 at 255. Record exact byte diffs/hash. The boundary x=40 is 8-pixel block-aligned, so the expected decoded sample pattern is unambiguous; still verify it from the resulting JPEG.
2. Use the **same pinned** `/opt/homebrew/bin/cjpeg` binary/options from `PROVENANCE-RECOVERED.md:27-28`: `-quality 100 -grayscale`, only substituting this PGM for the gain input. Keep the exact prior `bright-white/base-bright255.jpg`, `fixtures/cap-16.cfg`, pinned `build/ultrahdr_app -m 0`, and explicit-rational conversion script/options from `bright-white/COMMANDS-AND-PROVENANCE.md`. Do not re-encode the base or alter its ICC, ISO values, dimensions, MPF representative bit, color profile, or segment-order policy.
3. Verify the final base JPEG codestream/ICC and ISO fields match the prior white control, auxiliary decoded samples are exactly the specified 0/255 step, and only unavoidable gain JPEG codestream and MPF auxiliary size/offset bookkeeping differ. `JpegR::encodeJPEGR(compressed,compressed,metadata)` (`lib/src/jpegr.cpp:388-429`) calls `appendGainMap`; that method writes the compressed secondary bytes without re-rendering them (`jpegr.cpp:1327-1329`). Requalify with the reference decoder, then compare the original white control, new split-gain control, and A in one ImageIO/Core Image run.

This holds the producer/codec/profile/container *policy* fixed, but cannot keep every container byte fixed because a different compressed gain image may change secondary length and its MPF size. If Google split-gain still reaches ~16 on the white patch, simple uniform-versus-nonuniform gain is insufficient to explain A's ~8; if it drops to ~8, content/codestream-dependent handling is implicated, not yet the exact cause. The control does not replicate A's black/white base content or A's JPEG encoder, so a negative result does not exonerate every base/gain interaction. No product fix or gate waiver follows.
