# EXP-45 phase 2: explicit-denominator ISO diagnostic

Date 2026-09-28; same A host macOS 26.6.2 (25G83), arm64. This is a **scratch copy experiment** after phase-1 evidence was frozen in Git commit `99f806ed`. Original upstream Google JPEGs, retained Tessera A JPEG, upstream source, Tessera product source and the unchanged A ImageIO assertion were not modified. The only byte-level changes were the auxiliary ISO metadata representation and the necessary APP2 length/MPF auxiliary size. No representative-image bit was added. The approved source audit is in phase-1 `source-reviews/tessera-exp45-denominator-source-audit.md`.

## Exact transformation and qualification

Script `make_explicit.py` requires the exact unmodified Google v1.4.0 fixture SHA-256 values from phase 1, parses the MPF IFD and auxiliary JPEG APP2 rather than assuming absolute offsets, and validates flags, rational values, MPF sizes/offsets and SOI/EOI. It changes the auxiliary flag `0x48` (base color space, common denominator) to `0x40` (base color space, explicit denominators), representing the same seven values as numerator/denominator pairs. In the 4× file those are `0/1, 2/1, 0/1, 2/1, 1/1, 0/1, 0/1`; in the 16× file they are `0/1, 4/1, 0/1, 4/1, 1/1, 0/1, 0/1`. Both min/writer versions remain zero. The auxiliary ISO APP2 expands by 24 bytes (segment total 69→93; length field `0x0043`→`0x005b`), and MPF auxiliary size changes 416→440. Primary JPEG and auxiliary SOI stay at offsets 0 and 1479; the first MPF attribute remains Google's `0x00030000`. Exact source/replacement byte ranges, size-field before/after bytes, output SHA-256 and unchanged-prefix/suffix checks are in `make-explicit-{4,16}.json`.

A separate read-only JPEG parser (`payload_equivalence.py`) hashes the primary and auxiliary SOS-to-EOI entropy streams plus ICC APP2 payloads in source and explicit copies. For **both** 4× and 16× pairs, the base entropy hash is `f61ce3e7ae801b47a11f375762bd110f5cafd96f39f90039c3302f031c6b87bc`, gain entropy hash `6cec2cd09d24ff54ab2017a62ccf8fe5e58bae99a3204beb84c1dab7d073c0b5`, and base ICC payload hash `699539880ff71f48af3b95a468abb2e2db2290c440458caa9ab8a13d89124db7`, identical before/after. Gain ICC is absent in both. Raw offsets, lengths and direct exit are in `payload-equivalence-{4,16}.json` and `payload-equivalence.exit`. This complements the script's exact unchanged prefix/suffix checks around the two edited ranges.

Output fixture hashes: `reference-4-explicit.jpg` SHA-256 `43cbe202ddb275fa524fab7cbe40bdd1f119e1d933b5971bb54be7068ca9669d`; `reference-16-explicit.jpg` SHA-256 `cadfffeac4728b3536b738c6257bbc7c843bde5dc6153c160141fac5effc06ed`. Each is 1,919 bytes. `static-{4,16}-explicit.json` independently records MPF two-image offset/length, ExifTool auxiliary byte-exact extraction, ISO version0/flags and explicit numeric rationals. Libultrahdr reference decoder requested documented linear half-float RGBA; both outputs are **byte-identical** to their unmodified-upstream inputs' decoded outputs (direct exits 0), with bright patch 3.486328125 and 13.9453125 respectively (`decode-*-explicit.json`). This establishes equal decoded semantics before native comparison.

## Same-host native result

The exact phase-1 scratch ImageIO and software Core Image probe binaries were reused, without recompilation. `native/imageio.json` is **raw stdout** and begins with two `too few samples` diagnostic lines before a valid JSON array; direct process exit was 0 and `native/imageio-parsed.json` preserves a parsed copy without hiding the prefix. `native/coreimage.json` and both direct exits are preserved. All decoded pixels were finite and opaque.

The independent explicit-denominator control therefore proves that ImageIO on this exact A host can decode a recognized ISO JPEG gain map to **above 8×**, with headroom16 and an approximately16× HDR/SDR patch ratio. The retained A file, which already uses explicit denominator form (`0x40`), still stops near8 in ImageIO and reconstructs near16 in Core Image. The phase-1 unmodified Google common-denominator files and representative-bit-only copies remain unrecognized; the denominator representation is causal for admission of these Google controls under this isolated transformation, but it does **not** explain the A file's separate ~8 readback. The original frozen A core gate remains 4 pass/1 fail. No production encoder correctness or final A package acceptance is claimed.

## Limits and next decision

A controlled byte-level copy is not an unmodified upstream fixture, although its reference-decoded pixels and metadata values are identical. The native `too few samples` lines require preservation and should not be silently discarded. The probe's HDR CGImage reports an unknown copied color-space name but RGB model/three components and an ICC payload; the quantitative comparison uses explicit extended-linear-sRGB RGBAf output. Provider bytes are packed 10-bit and not direct linear measurements. The next A-specific question is why an already-admitted `0x40` Tessera file returns ImageIO headroom8 with exactly16 declared/reconstructed; that requires a separately scoped comparison of metadata/ICC/raster context or another controlled test, not a tolerance change or assertion waiver. No further mutation was performed here.
