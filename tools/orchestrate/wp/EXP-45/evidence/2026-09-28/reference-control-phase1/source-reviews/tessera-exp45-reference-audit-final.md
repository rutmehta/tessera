# EXP45 independent control source audit (read-only)

Source examined: `/Volumes/betterSSD/tessera-validation/exp45-independent-control/d52a0d13814ca399fc8a07e23de1d2c63f0e8404`; pinned `libultrahdr` checkout HEAD is `d52a0d13814ca399fc8a07e23de1d2c63f0e8404`, clean. The recorded encoder command uses its compressed SDR base, compressed gain JPEG, and `cap-16.cfg`; `decode-16.json` records `-m 1 -o 0 -O 4`. In the pinned sample application, `-o 0` is linear transfer and `-O 4` is RGBAHalfFloat (`examples/ultrahdr_app.cpp:1486-1495`); the API requires that pairing (`ultrahdr_api.h:644-662`, `lib/src/ultrahdr_api.cpp:1759-1767`). The API describes half-float nominal linear range `[0,10000/203]` (`ultrahdr_api.h:108-112`). Treat decoded values as linear multiples of SDR reference white (203 nits for that convention), not gamma-encoded bytes or an absolute 16-nit measurement. The recorded 80×16×8 = 10,240-byte raw output matches RGBA half-float dimensions. A raw file hash and patch-center values are recorded, but the current JSON does not itself include an independent unit assertion.

Declared maximum boost 16 is metadata capacity, not an assertion that every output patch equals 16. `fixtures/base.ppm` center pixel x=66 is 240/255 sRGB, while `gain.pgm` there is 255. Standard sRGB linearization gives `((240/255 + .055)/1.055)^2.4 = 0.8713671`; multiplied by 16 gives 13.94187. The reference decoder's 13.9453125 half-float center is within ~0.025% (JPEG/half quantization). Other centers are 64 and 128 in the PPM and produce the observed ~0.8218 and ~3.4609 after 16×. Thus 13.945 is expected from the deliberately non-white base and **does exceed 8**; it is a valid high-headroom reference-decoder control, not a 16.0-pixel fixture. `decode-4.json` analogously records ~3.4863 at the bright center.

`static-16.json` records two JPEG SOIs at offsets 0 and 1479, MPF APP2 at 648, auxiliary JPEG length 416 and ISO 21496-1 URNs/version 0 in both images. The MPF second-image offset calculation is coherent: the MPF TIFF origin is byte 652 and its second entry offset 827 points to auxiliary SOI 1479. This supports a structurally plausible ISO v0/MPF pair, but does not by itself prove ImageIO's association rules or cross-vendor acceptance. The reference decoder successfully reconstructed 13.945. The independent static JSON records offsets/metadata but not a second vendor's full decoded-pixel result.

Concrete MPF association difference: Google's first MP entry attribute is `0x00030000`; A's same-run 4-stop JPEG uses `0x20030000`. The pinned Google writer explicitly emits `kMPEntryAttributeFormatJpeg | kMPEntryAttributeTypePrimary` (`lib/src/multipictureformat.cpp:76-84`), with `kMPEntryAttributeTypePrimary = 0x030000` (`lib/include/ultrahdr/multipictureformat.h:68-69`). It omits the `0x20000000` representative bit present in A. This is a plausible format/association discriminator, **not a proven cause**. Differences in APP ordering or other metadata also remain possible. A controlled copy changing only that bit, with before/after SHA, static requalification and identical-host ImageIO probe, is the right narrow diagnostic; never alter the retained upstream original.

The current same-host `native/imageio.json` already shows both unmodified Google 4× and 16× files with `iso_aux_present=0`, `headroom=1`, SDR/HDR pixel arrays identical and max delta 0. The A 4-stop file in that same run reports `iso_aux_present=1`, headroom 8, and HDR peak 7.983762. Therefore the Google files are **not qualified positive ImageIO gain-map controls on this host yet**. This result cannot establish macOS's >8 limit, explain A's ~8 failure, or relax A's original 4% assertion. It only shows that libultrahdr's own decoder accepts this pinned output while ImageIO does not expose its auxiliary image in this probe.

Provenance limit: the encoded input JPEGs and raw PPM/PGM are retained, and output/decoder hashes are recorded, but the exact PPM/PGM-to-JPEG producer command is not present in the inspected top-level evidence. Pin those four input hashes and the JPEG conversion command when packaging the control.
