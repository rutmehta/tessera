# Transform resource source audit (read-only)

Repository: `/Users/rutmehta/Developer/tessera` (source key `origin/wp/B5-16` at audit time).

Source inspected at `origin/wp/B5-16` (`8e301f0`), with no runtime measurements. These paths explain substantial CPU/GPU and transient memory demand, but **do not establish the cause of Machine B's 43 GB swap** or prove a leak.

1. **Expected high-load test sequence.** `TransformSelfTest.swift:317-382` adds Perspective and Puppet stages to the 1600×1000 smart object; `:406-457` exercises amount-1 CPU content-aware scale, including a protected channel and then the same operation above three geometric stages; `:505-529` rasterizes the stack for PSD; `:548-582` creates and opens a 5472×3648 (19.96 MP) PNG, runs 90 drag steps, and applies an exact render. `writeCard` (`:165-193`) creates/encodes a full bitmap on the main actor, and `open` (`:196-203`) retains prior documents until explicitly closed. This is a plausible source of a high CPU observation during the test. Ask B for the last `transform-selftest:` check/shot line and timestamp, app PID CPU/resident size, and whether the CPU peak coincided with steps 389/390, 398, or 399. The orphaned `yes` process must be accounted for separately.

2. **CAS with a transform stack deliberately routes to CPU full-stack evaluation.** `filters.rs:560-573` excludes stacks containing ContentAwareScale from the direct compositor route. The filter worker calls `filtered` (`:1653-1669`), whose transform branch calls `native_stack` (`:1536-1548`); that function renders a document-size float RGBA image (`:578-612`). The GPU resident stack also explicitly falls back to CPU for CAS (`resident/filters.rs:237-292`). `transform.rs:793-823` disables reduced draft proxies whenever there are other stages and tells the UI that previews then render the whole stack at full resolution. Thus the stacked CAS edits at self-test `:437-457` can repeatedly run full-resolution CPU work, despite other transform previews using GPU. Confirmation: `doc-render` path/timings, `document-resources` CPU fallback count, Instruments stack samples around `native_stack`/`evaluate_transform`/seam carving, and per-step timing logs. The 1600×1000 card makes this expensive but does not alone imply tens of GB.

3. **Stale filter bakes can do avoidable work during rapid edits.** The bake queue stores only one pending job per layer (`filters.rs:1295`, `:1879-1885`), but an already-running bake uses a fresh `AtomicBool(false)` (`:1715`) and does not check whether its key is still current before `i.bakes.insert` and scheduling another frame (`:1685-1704`). `native_stack` checks cancellation only before and after its full-stack call (`:1536-1547`), so in-progress calculation cannot be interrupted there. This is a credible CPU amplification path during rapid CAS/stack changes, bounded by one running worker plus latest queued job, not an unbounded job queue. Confirm by comparing bake job keys/generations and completion times to current layer key, and sampling the `document-filters` thread while edits continue/after they stop.

4. **20 MP drag is proxied, but exact apply allocates large full-size intermediates.** `transform.rs:286-310` builds a <=1 MP F32 proxy when the layer has no other stages, and `:1148-1154` uses it only for draft previews; `:793-797` chooses it for the 20 MP case. On Apply, `:938-977` commits the exact op and the render path handles the exact stage. The resident transform path generates a CPU displacement array and uploads an RG32Float texture (`resident/transform_gpu.rs:151-177`), 8 bytes/output pixel (~160 MB at 19.96 MP); each F32 RGBA stage buffer is 16 bytes/pixel (~319 MB, `resident/filters.rs:114-129`), with multiple conversion/stage buffers (`:327-371`). Cache insertion is bounded by a per-renderer budget (`:52-77`), but transient and nested child-renderer memory can exceed one stage buffer. Confirm with app resident/private memory and GPU residency sampled at beginning of step 399, during the 90 drags, and after exact Apply. `doc-render` should show whether this app used viewport/full-level/GPU/CPU paths; avoid inferring GPU use from the feature alone.

5. **No obvious unbounded preview queue in these paths.** Swift has one `previewInFlight` plus a dirty bit (`DocumentTransforms.swift:339-381`); the engine render signal merges frame requests (`render.rs:475-489`, `:690-698`) and one worker processes them (`:766-809`); UI callback frames replace the pending frame (`EngineDocumentBackend.swift:325-353`). `latencies` grows for a long-lived app (`DocumentTransforms.swift:395-415`), but this self-test resets it before step 399 and it is too small to explain the reported swap. These bounds are useful to rule out the simplest runaway request-queue hypothesis.
