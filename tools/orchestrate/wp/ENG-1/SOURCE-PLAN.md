# ENG-1 Texture/Clarity luminance-conditioning source plan

Base inspected: main `b07993a1` (read-only). No implementation, builds, GPU/tests, or declined B5-32 numerical commits were used. Scope and acceptance are from the exact ENG-1 addition in `docs/coordination/CODEX-BRIEF-2026-09-30.md` line 67. It identifies signed RGB with nearly cancelling luminance after sharpening, a one-input-ulp texture/clarity shift around 0.08, and CPU/GPU worst divergence at 24 MP; asks to condition the division, preserve CPU/GPU agreement, rerun Develop goldens, then tighten resident-chain tolerance to absolute 0.01. It explicitly declines `635f69d8`.

## Source trace

- CPU detail/sharpen happens before global tone and Texture/Clarity: `crates/pipeline-cpu/src/render.rs` lines 294–320 call profile vignette/point corrections, then `detail_image`, then `tone` per tile. `tone_extra_image` follows basic tone in the M2 render path around lines 409–430. `color` comes afterward.
- CPU Texture/Clarity is `crates/pipeline-cpu/src/tone_extra.rs`, `presence()` around lines 193–240. It computes Rec.2020 linear luminance with left-associated `(0.2627 R + 0.678 G) + 0.0593 B`, derives encoded luminance `z`, guided fine/mid/wide scales, adds texture/clarity deltas, and clamps the new encoded value to a radius-1 neighborhood min/max (`range`). For `Y <= 0`, it skips that pixel. If output `z` changes, it computes `gain = finite(decode(out) / y)` and multiplies each signed RGB channel by this same gain. `finite()` saturates to f32 range; it does not prevent a large finite gain. The function is applied after `detail()` in CPU render, so sharpening can create signed/channel-cancelling RGB first.
- GPU resident equivalent lives in `crates/pipeline-gpu/src/presence.wgsl`: `luma`, `presence_from` (around lines 35 and 105–117), where `lum > 0.0` is the branch and `decode(adjusted) / lum` is the gain. A second equivalent division exists in `crates/pipeline-gpu/src/tone_local.wgsl` mode 6 (lines 81–96); both the resident and local compute paths need the policy. `resident_tone.rs` documents/dispatches the order: detail earlier in resident render, tone then presence, dehaze afterward (`crates/pipeline-gpu/src/resident_tone.rs`, comments around 590 and processing around 450–600). Keep the exact luminance expression/order aligned; GPU comment in `operators.wgsl` also cautions against algebraically regrouping equivalent gain math.
- Existing tests: `crates/pipeline-cpu/src/tone_extra.rs` has focused texture/clarity, constant-color and signed/general synthetic coverage. `crates/pipeline-gpu/tests/local_tone_resident.rs` compares resident operators against `pipeline_cpu::tone_extra_image` and has synthetic RGB values including negative samples; `level_mode.rs` and `resident_locals.rs` exercise integrated local/tone chains; `crates/pipeline-gpu/tests/tone_local_compute.rs` covers the separate local shader. The Develop resident golden is `crates/filters/tests/camera_raw_gpu.rs`, especially `resident_chain_matches_cpu_across_tile_edges_and_preserves_alpha` around lines 151–211. It checks every pixel and exact alpha, and currently asserts scaled error <0.002 plus absolute error <0.025 (comment cites measured 0.0205); that is not the new <=0.01 criterion. B5-32 report from `origin/wp/B5-32:tools/orchestrate/wp/B5-32/HANDOFF.md` is historical diagnostic evidence only: it says detail/tone/presence share ordering and records an illustrative one-ulp CPU output change of 0.08395. Its solution commits were declined and must not be adopted.

## Conditioning candidates (no product choice approved)

The first candidate considered here, `gain = target / max(Y, ε)`, is **superseded and blocked** by `INDEPENDENT-REVIEW.md`. Although it preserves the current `Y <= 0` branch, it creates a near-identity discontinuity for `0 < Y < ε`: exact `adjusted == z` skips scaling, while an arbitrarily small nonzero change scales all RGB approximately by `Y/ε`. With signed, cancelling RGB, that can cause a large RGB jump. Do not implement the direct total-gain denominator floor unchanged. The candidate `ε=1e-3` is likewise unvalidated and is not approved.

An identity-preserving alternative to investigate is `gain = 1 + (target - Y) / max(Y, ε)` below the floor, while retaining the original division/order for `Y >= ε` where possible. It is algebraically equivalent to `target/Y` above the floor, but below it blends the requested luminance change by `Y/ε`; this is a deliberate rendering semantic and can still fail continuity at `Y=0`. It is only a candidate for RED testing/review, not an accepted policy or Adobe equivalence claim. Choose no ε based on the guided filter's `EPS=0.001`: that is a variance regularizer with different units/role. Validate any chosen value against synthetic tests and all Develop goldens; document units, sign behavior, and expected adjustment attenuation. Keep existing luminance expression, neighborhood filters, operation order, per-channel multiplication, and untouched paths unchanged.

## Synthetic RED tests

1. Add a unit test in CPU tone_extra and a matched GPU resident test using identical tiny planar fixtures. Include RGB vectors with signed components and strictly positive near-cancelled Y: retain the B5-32 diagnostic vector `[-0.006959494, -0.005868249, 0.097931265]` (reported Y≈3.924e-7) as a candidate, plus a deterministically constructed cancellation vector using luminance coefficients and representable `next_up()` perturbations. Initially make RED assertions policy-independent: exact no-op continuity for substantial signed channels at positive sub-floor Y when `adjusted == z`, and compare adjacent representable nonzero `adjusted` cases against the exact no-op. Once a candidate is explicitly selected, add an independent equation-level oracle for its documented semantics; do not copy the production helper. Do not treat the historical sample as ground-truth Adobe output.
2. Exercise positive Y below/at/above candidate ε and both sides of the no-op branch, with an arbitrarily small `adjusted-z` change and substantial signed RGB channels. Exercise positive→zero→negative Y using a spatial fixture whose neighborhood makes the requested target non-neutral; compare exact zero and +/- one-ULP cancellation inputs to reveal any jump. Also test both adjustment signs and neighborhood clipping. Keep the current `Y<=0` skip behavior unless a separately reviewed policy changes it.
3. Include detail→presence chain with sharpening configured to create signed RGB, plus presence-only control. Verify that the chain no longer amplifies a one-f32-ulp perturbation beyond the agreed bound; retain the same `next_up()` pair in CPU and GPU input. ## Facts vs. unknowns

- Source evidence establishes the equations/ordering above and that input luma may be signed. It does not establish a desired `ε`, Adobe's intended clipping/floor behavior, or that any positive floor exactly matches Lightroom.
- For `Y <= 0`, current Texture/Clarity skips the RGB update. Preserving that branch is a narrow choice, not proof of continuity: even the correction-gain candidate may tend toward `1 + target/ε` as positive Y tends to zero while exactly zero/negative Y remain unchanged. Test this boundary explicitly.
- The direct `target/max(Y, ε)` candidate is rejected by the independent review because it creates an algebraically demonstrated discontinuity when a small nonzero adjustment crosses the existing `adjusted == z` skip. See `INDEPENDENT-REVIEW.md`. No epsilon or formula is approved.
- The 0.01 threshold is explicit in the new brief as the intended final resident-chain criterion, not current pass evidence. Only a complete all-pixel CPU/GPU resident-chain result after the fix can establish it; standalone operator parity is insufficient.
