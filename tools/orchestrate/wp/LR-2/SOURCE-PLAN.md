## Proposed synthetic RED coverage

Use the existing parser test homes `crates/import-lrcat/tests/lua_develop.rs` and `crates/import-lrcat/src/xmp.rs`, plus a CPU develop oracle in `crates/pipeline-cpu` (or the smallest import-to-render integration test that can call it). Keep all fixtures synthetic.

1. **B&W activation is a separate control from mixer values.** Make equivalent XMP and Lua fixtures with `ConvertToGrayscale=false` and nonzero, distinct GrayMixer controls; assert values are retained, diagnostics identify currently unsupported fields, and CPU output stays color (or follows confirmed Adobe behavior once verified). A second fixture with `ConvertToGrayscale=true` and all mixer channels neutral must render grayscale. A third changes just one band and uses saturated synthetic R/G/B/C/M swatches to prove that imported controls affect pixel values, not just parser presence. Compare against a hand-computed oracle derived from verified channel-mixer formulas or an Adobe-authored synthetic reference; current source alone cannot supply an Adobe parity golden.
2. **Preserve eight independent values.** Give each `GrayMixer*` a different small value (including zero, positive, negative, and a boundary-valid value after schema is established). Assert exact per-channel mapping, round-trip values, active switch behavior, and unchanged alpha. Never collapse the eight source values to one generic saturation knob. If the six-weight `Adjustment::BlackWhite` is chosen as the lower-level operator, separately prove the 8→6 conversion and its gamut/hue interpolation against the Adobe reference; the current generic operator's unit test is not that proof.
3. **Legacy PV separation.** Synthetic Lua and XMP pairs cover `Exposure2012`/`Contrast2012` alongside `Exposure`/`Brightness`/`Contrast`, with explicit `ProcessVersion` for PV1/2 and later PVs. RED assertions should show that old keys currently remain retained and do not silently overwrite modern values. After semantics are documented, test conversion at zero, positive/negative midrange and extrema for each supported process version; render a channel/ramp fixture and compare to a frozen reference. Do not infer a simple scale/offset from field ranges. Verify `Brightness` either maps through an evidenced transform or remains explicitly unsupported; existing Tone has no brightness slot.
4. **AutoToneDigest and DepthMapInfo are not slider effects by implication.** Pair fixtures with identical actual tone settings but different digest strings; until Adobe schema proves otherwise, assert only exact retention/diagnostics and that digest-only changes do not alter rendered pixels. Exercise `AutoToneDigestNoSat` independently. For `DepthMapInfo`, test exact structured source preservation and no accidental translation into a depth raster or `settings.geometry`/`effects` field. Only add render behavior after source/schema establishes whether it is metadata, an external resource locator, or an active instruction. Include absent, empty/default, and present/nonempty cases so presence is not mistaken for an applied effect.
5. **Codec/retention equivalence.** For equivalent scalar values, Lua and XMP imports must produce the same translated recipe and same effective CPU pixels. Assert exact raw values in the B5-29c per-key map (booleans remain booleans for Lua, not text generated by Lua→XMP; nested XMP values retain their source fragment). After translation, assert that the typed recipe field is populated, the lane matrix marks the key “translated,” and warnings no longer call it unsupported. Confirm post-translation raw retention assertions against the landed B5-29c contract; matrix status alone determines neither deletion nor permanent retention. Continue validating that unrelated unknown keys remain retained.

## Semantics currently uncertain; do not encode assumptions as RED or GREEN claims

- Adobe's `GrayMixer*` exact eight-band hue kernel, coefficient normalization, linear/encoded color domain, clipping, and whether sliders alone imply B&W mode are not documented by these repository sources. `ConvertToGrayscale` is a Boolean-looking name, but parser source has no schema/type evidence yet.
- The meaning, numeric domains and PV applicability of `AutoToneDigest*` and `DepthMapInfo` are not described in recipe/codec docs. A digest name is not proof it is inert metadata; raw retention is the safe current behavior while schema evidence is sought.
- No repo evidence establishes exact PV2010-to-PV2012 conversions for Exposure/Brightness/Contrast or whether current tone fields' `DisplayTransform::AdobePv6Compat` reproduces earlier Adobe PV math. Preserve process version and source values; conversions need supported formulas and golden evidence.
- Presence totals must not be reported as active/effective counts without an aggregate showing typed values, true flags, and nonzero sliders. No private catalog was inspected for this plan.
