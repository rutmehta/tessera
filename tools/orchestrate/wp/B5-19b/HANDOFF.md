## 1. Stack budget scales with physical memory

`stack_megapixels_for_memory(Option<u64>)` (Rust-only, re-exported for tests) = half of physical RAM at ~50 B per
source pixel, in whole megapixels, clamped to 1..=`MAX_STACK_MEGAPIXELS` (200, now the ceiling); `None` (unknown)
gives 200. Examples: 8 GiB ⇒ 85 MP, 16 GiB ⇒ 171 MP, 20 GiB or more ⇒ 200 MP. RAM comes from `sysctlbyname
("hw.memsize")` on macOS (a local `unsafe extern "C"` declaration, as `surface.rs` already does; no crate) and
`/proc/meminfo` elsewhere; read once (`OnceLock`). `stack_max_megapixels()` (uniffi, signature unchanged) now
returns this machine's budget, and every over-budget error names it: "… is limited to L megapixels in total on
this computer; these have N megapixels. Use fewer or smaller images."
Swift: `StackCommandRules.maxMegapixels` stays 200 as the documented ceiling (it is not used for enforcement; the
engine's `stackEligibility` and errors are).
Tests: `stack_budget_scales_with_physical_memory_up_to_200_megapixels` (injected values),
`stack_budget_uses_this_macs_physical_memory` (macOS: equals `sysctl -n hw.memsize` through the same formula),
unit `tests::the_error_names_the_actual_limit` (injected 85 MP limit); the two B5-19 budget tests now assert the
actual limit instead of 200. Swift `testLensTogglesNeedCalibration` asserts `1 ≤ stackMaxMegapixels() ≤ 200`.

## 2. Cancel never reports "finished"

Pure rule in TesseraCore: `StackCommandRules.end(cancelRequested:succeeded:)` → `.finished | .failed |
.cancelled | .cancelledAfterFinishing`, and `cancelledMessage(_:afterFinishing:newDocument:)`. DocumentStack
follows DocumentRetouch's discarded-but-succeeded pattern:
- Photomerge into the current document, Auto-Align, Auto-Blend: a cancel that arrives after the engine committed
  runs `doc.backend.undo()` ("Undo cancelled …", redoable) and says "X cancelled; the engine completed before it
  could stop, so the change was undone".
- Photomerge into a new document: the finished session is closed, never installed; "Photomerge cancelled; the
  engine completed before it could stop, so the new document was discarded".
- Cancelled before the edit (Photomerge while reading photos): "Photomerge cancelled; nothing changed".
Auto-Align / Auto-Blend busy sheets now also offer Cancel (a Swift-side `CancelFlag`; the engine calls still take
none), so the user can get the pre-run document back; the busy notes say that Cancel takes effect when alignment /
blending returns. `StackBusySheet` takes the note explicitly.
Tests: `testRunEndReflectsALateCancel`, `testCancelMessagesNeverSayFinished`.

## 3. Colour: profile identity before ICC bytes

`Source::load` now converts only when `same_profile(source, target)` is false; `icc()` (the "not embedded"
error) is reached only for a real conversion. `same_profile` = equal `handle`, or both embedded and byte-equal
except the ICC header's creation date (24..36) and profile ID (84..100).
Why the second clause: color-mgmt's built-in profiles are generated by lcms at call time and carry the creation
second in byte 35, so two sRGB `ColorProfile`s built a second apart have different handles (seen as a 50 % flaky
failure while writing the test). Engine ask for A: make `color_mgmt::builtin_icc` output deterministic (fixed
creation date) so `IccProfileHandle` identifies built-ins; until then, a document whose profile is a built-in with
no embedded bytes only matches sources carrying the exact same bytes.
Tests: `photomerge_skips_conversion_when_the_unembedded_target_is_the_same_profile` (P3-tagged PNGs into a
document whose Display P3 profile has a handle but no bytes: one history node, values unconverted; a different
unembedded profile (sRGB) is still refused with "is not embedded") — RED on dd2cf300 with "the colour profile
“Display P3” is not embedded"; unit `tests::profiles_match_by_handle_or_by_bytes_up_to_the_creation_date`.

## 4. Photomerge file sources: JPEG / PNG / TIFF only

Since B5-19's review fixes, Photomerge *file* sources are JPEG, PNG and TIFF only (Add Files… offers those three;
the engine refuses other paths with "Photomerge takes JPEG, PNG or TIFF files or library photos"). HEIC, PSD / PSB
and native `.tessera-doc` files are no longer accepted as files. Library photos are still accepted by image id
whatever their format (RAW, DNG, HEIC, …): they are rendered through the library's develop path.
Why:
- Memory budget before decode: the stack budget is checked from each file's header before anything is decoded.
  JPEG / PNG (via `image::ImageReader::into_dimensions`) and TIFF (`tiff` decoder) give dimensions from the header;
  the bridge has no header-only size reader for HEIC, and PSD / `.tessera-doc` sizes need a full parse of a
  layered document, so a large one could exhaust memory before the check.
- Layers: PSD and `.tessera-doc` carry layers, masks, smart objects and effects; Photomerge would silently flatten
  them into one composite, losing the structure the user saved.
- Colour: flat files carry at most one embedded ICC profile the bridge reads directly; layered documents' profiles
  go through their own loaders.
Workarounds: import HEIC into the library and merge the library photos, or export PSD / Tessera documents to TIFF
first. Library HEIC / linear DNG have no header size either; they are counted right after their decode and
refused before the next one (unchanged from B5-19).

## Release note

**Photomerge, Auto-Align Layers and Auto-Blend Layers: stack size now depends on your Mac's memory.** A stack may
use up to half of the Mac's physical memory (about 50 bytes per source pixel), capped at 200 megapixels in total:
about 85 MP on an 8 GB Mac, 171 MP on 16 GB, and 200 MP on 20 GB or more. On 8 GB Macs some stacks that were
accepted before are now refused with a message naming the limit; use fewer or smaller images.
(Added by B5-23; no RELEASE-NOTES / CHANGELOG file or user-facing Photomerge doc page exists in the repo.)
