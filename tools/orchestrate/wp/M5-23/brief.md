# WP M5-23 — GPU-resident smart-filter stack and automatic transform routing

Read crates/compositor/COMPOSITOR.md (§12 resident renderer, §9.1 smart filters, the M5-21 transform section), crates/compositor/src/resident/** (incl. TRANSFORM.md, transform_gpu.rs, smart_gpu.rs), crates/compositor/src/render/smart_filters.rs, crates/filters/src/gpu.rs + compositor_adapter.rs (filters already have Metal evaluations), crates/transform/TRANSFORM.md, crates/gpu-core.
Today the resident (GPU) renderer falls back to CPU for any layer with a smart-filter stack, and the M5-21 displacement stage must be invoked explicitly. Make the resident renderer route automatically:
1. A per-layer smart-filter stack executes on the GPU when every stage has a GPU evaluation (filters' Metal kernels, the transform displacement stage, layer styles where M5-14 documented GPU routing); otherwise the stack falls back to CPU for that layer only, with the rest of the document staying resident. Intermediate textures are cached per stage keyed by (stage params, input revision) and invalidated by the existing dirty-rect/revision machinery; memory-bounded with the existing budget.
2. Transform stages feed the displacement texture path; chained transforms compose into one map when the kernels allow (document when they do not).
3. Parity tests: for every filter with a GPU path and for each transform kind, resident output vs CPU document render within the compositor's existing tolerance (bit-exact for the exact-math kernels, ≤1e-4 for resampled), at levels 0 and 2, including a stack of three stages and a nested smart object. Add a fallback test proving a CPU-only stage does not evict the rest of the document from the GPU.
4. Bench (ignored test, log numbers): 100-layer bench doc with 10 filtered layers, L2 viewport frame time before/after; target the interactive budget documented in §12.3.
Update COMPOSITOR.md (routing rules, cache policy, not-done list).
