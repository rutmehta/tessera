# WP M2-21 — GPU export path

M2-20 measured export at ~130% CPU: three raws with the Web preset took 36 s and a full-size 36 MP NEF 57 s (docs/08 target: 45 MP JPEG < 1.5 s, 100 JPEGs < 40 s). Read crates/export (streaming per-image path from M2-20, render_full/render_full_float, upscale, mask hooks), crates/image-core (Renderer, resident model, whole-level rendering from M2-17b, cache budget), crates/pipeline-gpu (managed output, resident presentation, readback), crates/tessera-ffi/src/export.rs (Engine::export_batch), crates/jobs.
Implement: export renders through image-core's GPU-resident Renderer at level 0 (or the level that covers the requested output size, then Lanczos-3 downsample on the GPU), with the managed output LUT for the target profile, one readback per image (or per band for images exceeding the GPU cache budget: render in horizontal bands with halo), then encode on CPU threads in parallel with the next image's render (pipeline: render N+1 while encoding N). Batch parallelism bounded by GPU memory. Keep a CPU fallback (`TESSERA_EXPORT_BACKEND=cpu`) and assert GPU vs CPU export within the docs/11 §1.3 full-chain tolerance. Apply masks (incl. AI mask hooks) and lens/geometry on the GPU path as the renderer supports; where the renderer still delegates to CPU for a stage, document it.
Bench (ignored, prints): the five fixtures with the Web preset and full-size JPEG, before/after; targets above. Tests: GPU export matches CPU export within tolerance; band rendering equals whole rendering; cancellation mid-batch leaves no partial files; XMP/ICC still embedded.
`cargo test -p export -p image-core -p tessera-ffi --release`, clippy -D warnings, fmt. engine-api unchanged. Allowed: Cargo.lock, Cargo.toml, crates/export/**, crates/image-core/**, crates/pipeline-gpu/**, crates/tessera-ffi/src/export.rs, apps/tessera-cli/src/export.rs, tools/orchestrate/wp/M2-21/**.
