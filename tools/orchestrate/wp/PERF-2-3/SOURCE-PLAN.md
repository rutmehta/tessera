# PERF-2 / PERF-3 source-only design notes

Inspected Tessera source and the `origin/wp/B5-prof` report. No builds, app/GUI, catalog, or tracked-file edits. Report timings were collected under load and are diagnostic, not a clean baseline. The report labels the Camera Raw test as a synthetic opaque PNG fixture; its “demosaic” wording in the phase-2 brief does not describe this input path.

## PERF-2 — Camera Raw global preview

### What is actually rendered

- [`crates/filters/src/camera_raw.rs`](/Users/rutmehta/Developer/tessera/crates/filters/src/camera_raw.rs) documents and validates an F32 RGBA document raster. `evaluate` reads those already-developed RGB pixels, converts document TRC + profile matrix to linear Rec.2020, constructs `pipeline_cpu::Image`/`RgbSource`/`RawImage`, then calls `image_core::Renderer::render_rgb_linear`. There is no CFA buffer or demosaic stage here. Do not add a demosaic cache for this benchmark.
- The 24 MP preview benchmark is in [`crates/tessera-ffi/tests/document_camera_raw_preview.rs`](/Users/rutmehta/Developer/tessera/crates/tessera-ffi/tests/document_camera_raw_preview.rs): 6000×4000 PNG; warm setting changes vary exposure while retaining clarity or vignette −40; 100% preview requests a 1600×1000 crop but the global filter needs the entire image.
- `Renderer::render_rgb_linear` already has an exact stage-keyed, byte-bounded RGB intermediate memo (`crates/image-core/src/rgb_render.rs`; exercising precedent: `crates/image-core/tests/rgb_memo.rs`). It can reuse stages before the first changed stage across repeated edits. `camera_raw::evaluate` uses a process-static Renderer configured to 256 MiB; profile transfer curves also have a separate static, 16-profile cache. The RGB memo is therefore not an absent feature to recreate.
- Source preparation is still repeated on every submit: full RGBA `Buffer::read`, three full planar Rec.2020 vectors, `Image`/`RawImage` wrappers, full-image content hashing (including row byte-vector allocations), and final source clone/output traversal. The reported 100%-global hotspot includes `Image::tile`, `Image::downsample_crop`, `camera_raw::encode_channel`, and output conversion. `encode_channel` here is document-profile TRC re-encoding, not sensor decoding. The preview crop is downstream of global filter evaluation, so do not claim that a crop alone limits this full-canvas work.

### Smallest defensible patch / ownership

1. First add stage-execution and allocation counters around a synthetic multi-submit test for local vs global edits. Pin the actual invalidation boundary: a vignette-only edit should retain all prefix stages whose keys are identical; the test should prove hits, not infer them from latency. Compare output bits with `pipeline_cpu::render_linear_scaled` + the existing ICC round-trip oracle on small patterned RGBA input.
2. The most contained candidate is reduce repeated source-identity construction/allocation: compute a stable digest while consuming tile/sample data (without per-row temporary `Vec<u8>`), and reuse the prepared immutable source (`RawImage` plus its ICC interpretation) across settings submits. Exact content identity is currently important: `FilterContext` has no document/layer ID, and tile revisions alone can alias two unrelated layers. Prefer a host-supplied stable document/layer/snapshot identity if the API owner can provide one; otherwise retain exact pixel digest validation. Cache must be bounded by payload bytes, keyed by source identity + extent + profile digest/transfer curves + interpretation version, and invalidated on any source tile/profile change. Reuse must not retain the full document indefinitely or conflict with PERF-5's single owner of `camera_raw.rs` buffers.
3. Coordinate PERF-2/5 ownership: PERF-2 should own the reusable prepared-source boundary or its API contract; PERF-5 should own peak transient/lifetime bounds in the same camera-raw path. Avoid two branches independently changing `Buffer::read`/plane/output allocations. Existing 256 MiB renderer cache excludes camera_raw's several full-frame intermediates and is not a whole-operation memory limit.

### CPU acceptance and limits

- RED/GREEN: synthetic 513×259 and a bounded larger fixture; submit unchanged source with two exposure-only edits and two vignette edits. Assert exact output against uncached reference, stage execution counts, source digest stability, invalidation when one tile/profile changes, cache byte cap, and release on clear/drop/cancel. Include two equal-revision but different-pixel sources to reject revision-only keying. Assert exact alpha preservation and `amount=0` identity.
- Keep performance and memory metrics separate: Rust counting allocator/live requested bytes for source buffers and renderer memo; RSS separately. Existing ignored 24 MP test is a diagnostic timing harness, not an asserted memory bound. A full 24 MP acceptance run belongs only after a cheap synthetic test and should report each edit, retained cache bytes, transient high-water, and warm/cold status independently.
- This likely improves repeated submit preparation and can preserve useful renderer-prefix hits, but does not establish that the 10.2 s global vignette kernel itself becomes 2–5× faster. The current global effect stage and final output TRC walk still run when their inputs/settings change; benchmark before selecting a numeric target.

## PERF-3 — vector drag

### Existing reuse and measured boundary

- `crates/compositor/src/render/live.rs` already has bounded `Prepared` geometry, per-tile live output, and per-primitive coverage caches. Live output is keyed by the digest of primitives intersecting that tile plus canvas/depth/coord; coverage is keyed by path geometry plus coord. Unchanged/distant tiles can be reused. A transform/geometry change changes primitive identity and correctly invalidates affected tiles. Do not describe all vector tiles as uncached.
- `crates/compositor/tests/live_render.rs` already checks `live_tiles`, `live_coverages`, partial damage and cold-render pixel equality after text/shape edits. `ResidentRenderer::render` also carries forward valid output blocks and derives damage from document revisions (`crates/compositor/src/resident/mod.rs`). The resident page buffers and upload buffers persist between frames.
- At step 372, B5-prof reports 152.5 ms median of 3 per-run medians and 579 CPU ms self samples in `ResidentRenderer::materialize`, 434 in `Compositor::live_tile`, 258 in `tile_from_normalized`, plus 176 `memmove`. These are aggregate CPU samples, not serial wall time. 4,915 MiB is whole-test RSS across the vector test, not per-frame allocation or a measured frame ceiling. The report also says 60 previews delivered median 14–15 frames. Treat these as workload clues, not proof a cache miss dominates.

### Smallest actionable CPU/engine changes

1. Instrument the synthetic drag fixture at engine seams first: changed output tiles, cache hits/misses, coverage rasterizations, uploaded pages/bytes, resident damage blocks, bytes copied/allocated by `live_tile`, `tile_from_normalized`, and `materialize`. Use deterministic transform updates and compare every frame to a fresh cold CPU compositor (exact depth-code equality); keep report timing distinct from sampled aggregate CPU.
2. Remove avoidable live-tile full-tile copies before attempting a new geometry cache. For an F32 tile, `live_tile` currently allocates interleaved `Vec<[f32;4]>`, then planar `Vec<f32>`, then `tile_from_normalized` copies that planar vector again into `Tile`. A narrowly scoped builder that composites/writes directly into the final planar Tile allocation could remove two frame-local buffers/copies while retaining the same primitive order and arithmetic. Preserve exact f32 bits and empty-tile/default behavior. `tile_from_normalized`'s F32 `.to_vec()` is itself a known full-buffer copy candidate; changing its ownership API should be limited to callers that can safely transfer the Vec.
3. `materialize` batches pending tile pages in groups of 512, parallel-converts each to `Vec<u8>`, then queues uploads. Measure whether geometry edits produce many pending pages; if so, make the batch/in-flight byte cap explicit and tune downward without changing output. Existing cache budgets are separate per live output, coverage, prepared geometry, compositor, and resident page pool; they are not a unified RSS bound. Avoid introducing an unbounded per-frame cache.
4. Do not reuse old coverage by merely omitting translation from the key: fractional translation changes antialias coverage and seams. Integer-shift overlap reuse is a possible later optimization only with pixel-exact tests across tile boundaries, fractional origins, transforms, stroke outlines and edits that alter path rather than translation. The first patch should target conversion/copy cost and bounded batching, which are directly supported by sampled hotspots.

### CPU acceptance

- Extend a seeded 20 MP shape-only drag fixture with a path that crosses multiple tile boundaries and includes both fractional and integer translation. Assert cold-vs-incremental frame equality after each pointer step, exact old-area erasure/new-area fill, unchanged distant tiles, cancellation/error cleanup, and counters proving damage locality. Add tiny cache/batch budgets to exercise eviction and cap behavior.
- Separate allocator high-water per frame (Rust requested/live bytes) from process RSS, Metal allocations and driver residency. Existing 4.9 GiB suite RSS must not be relabeled as a single vector-frame bound. Benchmark one cold frame plus warmed drag steps on a matched quiet host; report frame wall p50/p95, counts, changed area, allocations and uploaded bytes. Keep a separate end-to-end/UI path for input-to-presentation; the current engine report is not photon latency.
