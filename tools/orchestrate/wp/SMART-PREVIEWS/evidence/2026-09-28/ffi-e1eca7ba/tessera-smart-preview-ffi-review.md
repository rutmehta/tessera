## Findings requiring correction before UI exposure

### P1 — Sync acknowledges clean state before XMP directory publication is durable

Proposed `smart_preview.rs:438-452` durably writes recipe bytes with `atomic_local`, but uses `Sidecar::write_xmp` for XMP before acknowledging the journal clean. Current `crates/sidecar/src/lib.rs:28-59` syncs the temporary file and renames it without syncing the destination directory. Therefore synchronization can durably mark the local journal clean and delete its recovery intent while the new XMP directory entry is not durable. A crash can restore the old XMP; the clean local record is then discardable and the pending replay is gone. Publish the already-validated exact pending XMP bytes with the same durable helper (or explicitly sync the XMP parent) before `mark_synced`. Exercise failure after recipe publication and during XMP directory sync; local dirty state and replay intent must survive.

### P1 — Unguarded existing writers can race the synchronization baseline check

The notes correctly acknowledge writer gaps, but they are UI-release blockers: they can write between `smart_preview.rs:373-419` baseline validation and `:438-439` publication, so conservative baseline checks alone do not preserve both sides in that race. Specifically:

- `agent_runs.rs:450-477` writes original XMP/recipe without ID or destination admission. `run_agent` (`:576` onward) invokes an Agent/Console writer that also needs admission for its entire mutation phase; wrapping only its final `resync` is insufficient. Accept/revert agent edits need the same protection.
- `metadata.rs:205-229` (`Library`'s `edit_xmp`) writes original XMP under the catalog lock alone.
- `lrcat.rs:1288-1331` (`write_image`) replaces recipe and XMP directly.
- `assist.rs:1243-1294` (`name_person` with `write_sidecars`) calls `cull::people::name_person` and can publish original sidecars outside the new guard. Include sidecar undo/redo restoration through `edit_people`, not merely the initial naming command.

Before exposing Smart Preview open/save/sync, route all these original writers through stable ImageId admission and dirty-journal refusal, followed by existing destination protection over read/validate/write. Acquire ID gates before catalog/destination locks; do not insert them under `edit_xmp`'s already-held Engine lock, since new Develop/sync holds ID admission before requesting that lock. For multiple IDs, sort/deduplicate and acquire consistently. A deliberate fail-closed disable while a Smart Preview editor or dirty journal owns any affected image is acceptable until journal-aware merges exist. Truly external processes cannot share a Rust static gate; don't claim they do—retain external-change checks and define that separate limitation.

### P2 — Crash after journal acknowledgement strands the next synchronization

Proposed `smart_preview.rs:446-454` first advances the journal generation and clears dirty, then removes `sync-pending.json`. If that remove/sync fails or the process exits between those operations, the old pending file remains. A subsequent sync skips all cleanup because `snapshot.dirty` is false (`:370`). After the next local edit, sync loads the stale intent and rejects its generation (`:376-381`) permanently through the exposed API, despite the preceding sync having successfully published both sidecars. Reconcile acknowledged intents on clean reopen/sync, verifying their intended bytes against the acknowledged baseline, and clear them durably before accepting a new edit or writing a new intent. Add crash-point/restart coverage at acknowledgement-before-intent-removal.

### P1 — Unknown nested members inside arrays are silently lost on local save

Proposed `smart_preview.rs:497-513` only recurses when both values are JSON objects. Arrays are ignored, yet `save_local_recipe` replaces complete `settings` and `history` values at `:475-487`. An unknown property inside an existing `settings.adjustments[]`, `point_colors[]`, or history entry is dropped by typed recipe deserialization/serialization, passes `preserve_unknown`, and is then durably erased. This violates the stated reject-unsupported-nested-data rule and exact unknown-field preservation requirement. Compare/preserve array contents by stable identity where edits support that, or reject affected documents conservatively before editing/saving. Cover an unknown field inside an array element, not just top-level recipe/envelope unknowns. Likewise handle object-to-nonobject transitions explicitly when they could erase unknown content.

## Scope observations and required verification

- Proxy save selects local `SmartPreviewJournal` persistence and holds the ID authority guard while saving; it does not canonicalize or write the original destination. Session and save-worker lease clones retain admission. Initial proxy renderer selection is CPU. These are appropriate source-level choices, not executed integration evidence.
- `local_smart_preview` checks for the journal before calling `open` (`smart_preview.rs:158-167`), so the ordinary no-record read does not create per-image directories. Existing journal reads still invoke the store's directory-ensure/sync path; a dedicated read-only constructor would separate that behavior cleanly, but no new absent-record creation defect is established here.
- Full-quality Original and rendered exports both call `recipe_and_xmp` before reading the original (`export.rs:1153-1183` current source); the proposed helper checks the dirty local journal and missing original under ID read admission. No path substitutes proxy pixels for export. This check is a snapshot at recipe-read time, not a lock over the entire export. Avoid claiming stronger concurrent latest-edit semantics without an export-level protocol.
- Original opens, direct recipe replacement, core selection operations and assist confirmations gain the ID gate. Export/get_recipe dirty checks are useful but do not repair the missing writer admission above.
- The sync intent protects interrupted two-file publication before acknowledgement, and journal CAS protects a stale acknowledgement. It needs the durability and post-ack recovery fixes above before these claims cover all introduced crash points.
- Exact-byte sidecar comparison is conservatively conflict-prone even for benign foreign metadata/selection changes. That is explicit in the patch and preserves data outside the race noted above. Dirty stale-source conflicts have no resolution UI/API here; never offer discard as a workaround because dirty discard correctly refuses.
- Build is synchronous, bounded and atomic at directory publication; it has no in-progress cancellation. Status reads decode the asset and hash an available original, so keep status off the main thread and avoid per-cell repeated hashing. Offline saves intentionally do not regenerate Library thumbnails; UI must identify that limitation.
- Apply/type-check and run focused session save/reopen/offline-source tests, all writer-conflict cases, partial-sync/restart failure injection, unknown-array preservation, and Original/rendered export rejection. The patch's helper tests alone do not verify an actual offline Develop session or reconnect workflow.

Conclusion: do not expose the integrated editing/sync UI on this patch as written. The bounded journal/admission primitive approval remains unchanged; these findings concern newly proposed integration behavior.

It syncs the local directory and is invoked before proxy opening, local saving and synchronization. This works without reading the original volume and also handles an acknowledged intent surviving into a later dirty generation. Mismatched clean-state intents fail closed. Restart-before-cleanup and subsequent-edit coverage is present.
4. **Unknown array members — resolved.** `validate_local_document` compares original stored fields against the OLD typed recipe projection; recursive object and array traversal (`smart_preview.rs:495-547`) rejects unrepresented nested members and structural loss before build/open/save. Comparing the old representation avoids incorrectly rejecting legitimate removal/reordering in the new edit. Top-level unknown recipe/envelope values remain in the raw JSON envelope.
