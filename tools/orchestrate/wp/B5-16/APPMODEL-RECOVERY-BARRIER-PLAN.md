## 1. Minimum data model and API boundary

Keep all coordinator state MainActor isolated. Reuse the existing DevelopCloseKey at AppModel.swift:277 (owner ObjectIdentifier plus stable imageID), holding a strong EngineLibrary in every live record. Never use mutable itemID or folder path as recovery identity. Remap to an itemID only at presentation/commit time. Two library instances pointing to the same folder are distinct owners; cross-instance writer leases remain outside this slice.

Proposed record, separate from navigation:

- key, strong owner, strong controller, immutable display name/source URL fallback, controller/session identity UUID;
- phase: active, saving(attemptID), failed(error text, optional authoritative durability detail), or closed;
- one shared result-bearing in-flight task, plus attemptID used to reject stale completion writes;
- workspace bookmark (stable selected/focused/anchor image keys, mode, explicit edit target, Review return state), not a closure capturing a replaceable AppModel.library;
- error/retry state observable to recovery UI even when no viewport is attached.

Use an observable recovery object collection, or an observable presentation projection over ignored operation storage. Do not put all recovery state in @ObservationIgnored dictionaries with no notification. Keep active/recovery records and in-flight opens as different types: today's PendingDevelopClose is incorrectly reused for both task kinds. A real engine session without a captured EngineLibrary is an invariant failure: retain controller under a session UUID and block destructive transitions/quit, rather than fire-and-forget it or invent a current owner. Normal open captures its nonoptional owner before suspension.

Suggested interface semantics (names are proposals, align with A Core result):

- requestSaveClose(key) -> shared Task<SaveOutcome, Never>. Outcome is saved, blocked(recovery key/error), or superseded for caller intent; cancellation is never equivalent to saved. Core success requires accepted host settings AND masks plus native durability repair/close. Host failure keeps the same controller usable.
- captureSaveBarrier(owner, imageIDs, policy) -> barrier with exact owner/keys, operation UUID and result. Policies distinguish initiating close from observing pending cleanup. Review's observer must not silently initiate arbitrary edit-session closes. Consumers requiring current controls use an initiating gate.
- retryRecovery(key): reuse retained controller, deduplicate simultaneous retry clicks, refresh failure on rejection. A failed record is not converted into an empty successful barrier merely because its task finished.
- cancelIntent(intentID): cancels only the requested action. It does not cancel/remove an in-flight durability operation or forget its owner. A successful close may still finish after intent cancellation.

When multiple keys are involved, await/drain every already-started operation and retain every failure. Do not early-return and drop later cleanup tasks. Blocking one consumer must not erase another consumer's recovery record. Avoid treating a captured task list as the whole truth: a cancelled open can create a recovery entry while that task is being awaited. Before returning saved, inspect the same-key open/close generation and recovery registry again. If another same-key open could start during the gate, reserve those keys synchronously before awaiting, release reservation on every outcome, and prevent new opens until the saved-reader/mutation is handed off. This is a host admission guard, not a new native writer lease.

## 2. Intent, attempt and owner tokens are different

Maintain a monotonically replaced navigation intent UUID independent of save-attempt UUIDs and existing loadGeneration. Capture owner, target stable IDs, old workspace bookmark and an explicit action enum (navigate, folder URL, Layers request ID, output request, Agent request, quit). Prefer data payloads plus a central commit dispatcher over arbitrary long-lived closures.

A new navigation intent supersedes the old continuation but joins an existing same-session save attempt. Completion always updates the matching recovery record, even if its consumer is obsolete. It applies navigation only when intent UUID, captured owner, target identity and action-specific preconditions still match. An old result cannot clear a newer record or change a replacement library's status. Read-only Review preview retains its existing loadToken and reviewGeneration checks as consumer tokens; it must not supersede global navigation intent. Independent outputs/Agent actions use their own operation UUIDs, plus target reservations, rather than one global token that cancels unrelated work.

Keep Editing invalidates the blocked navigation, retains the failed session/pending changes, restores its bookmark and callbacks, and enables editing after any in-flight save settles. If close already succeeded, reopen only after that same result says saved; never reinstall a closed controller. Missing/deleted source: show retained photo-specific recovery and Retry; do not select a different item that reused the index or claim editing is possible. Do not replace a newer workspace merely because a stale recovery completed; restoring an offscreen owner's workspace is an explicit user action through the same navigation gate.

Retry Save resumes at most the latest still-valid captured action once, after all its keys pass. An invalid/cancelled intent remains cancelled even if saving later succeeds. Repeated failures remain visible. Initial UI has Retry Save and Keep Editing / Cancel; Quit has Cancel Quit. No Discard: recipe may already be published while XMP/index repair is pending. Never infer durability stage from an error string; absent native detail use neutral wording such as 'Could not finish saving; your editing session is retained.' No crash/power-loss recovery claim.

## 4. Cancelled opens, concurrency and termination

Open task completion cannot simply 'await close(); return' when owner/token changed. Keep the just-created controller and original owner locally, perform the A result-bearing cleanup, register blocked cleanup strongly on failure, then settle/remove the open ticket. Every same-key barrier waits for this settlement, including when there was no closing task at capture time. A weak AppModel capture must not be the sole owner of recovery: app-lifetime coordinator owns open tickets until settled; shutdown drains it before release. No detached task merely ignores a close error.

Quit uses applicationShouldTerminate -> terminateLater while an app-wide operation joins all active/recovery sessions and cancelled-open cleanup, across owners. Freeze new opens/navigation/mutations admitted by this coordinator while termination is pending. Reply once per termination request: true only when all relevant Develop gates and existing Document unsaved-close decisions succeed; false on failure/cancel, keeping recovery UI/window alive. Retry after a false reply starts a fresh termination request, not a second reply to the old one. Never discard a document to make Develop Quit pass. Last-window close must be intercepted before destruction with a window delegate/host coordinator that composes with current delegates; returning true from applicationShouldTerminateAfterLastWindowClosed is too late to preserve its recovery surface. Cancel Quit leaves application, owner and recovery available. Background unrelated jobs retain their existing shutdown contracts; this plan does not claim universal job durability.
