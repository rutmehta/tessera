## 1. Minimum data model and API boundary

Keep all coordinator state MainActor isolated. Reuse the existing DevelopCloseKey at AppModel.swift:277 (owner ObjectIdentifier plus stable imageID), holding a strong EngineLibrary in every live record. Never use mutable itemID or folder path as recovery identity. Remap to an itemID only at presentation/commit time. Two library instances pointing to the same folder are distinct owners; cross-instance writer leases remain outside this slice.

Proposed record, separate from navigation:

- key, strong owner, strong controller, immutable display name/source URL fallback, controller/session identity UUID;
- phase: active, saving(attemptID), failed(error text, optional authoritative durability detail), or closed;
- one shared result-bearing in-flight task, plus attemptID used to reject stale completion writes;
- workspace bookmark (stable selected/focused/anchor image keys, mode, explicit edit target, Review return state), not a closure capturing a replaceable AppModel.library;
- error/retry state observable to recovery UI even when no viewport is attached.

Use an observable recovery object collection, or an observable presentation projection over ignored operation storage. Do not put all recovery state in @ObservationIgnored dictionaries with no notification. Keep active/recovery records and in-flight opens as different types: today's PendingDevelopClose is incorrectly reused for both task kinds. A real engine session without a captured EngineLibrary is an invariant failure: retain controller under a session UUID and block destructive transitions/quit, rather than fire-and-forget it or invent a current owner. Normal open captures its nonoptional owner before suspension.

Suggested interface semantics (names are proposals, align with A Core result):

- requestSaveClose(key) -> shared Task<SaveOutcome, Never>. The shared durability outcome is exactly saved or failed(recovery key/error), identical for every joiner of that attempt. It never contains superseded or caller cancellation. Superseded/cancelled belongs only to a separate per-caller ActionDispatchOutcome after observing the shared durability result; cancellation is never equivalent to saved. Core success requires accepted host settings AND masks plus native durability repair/close. Host failure keeps the same controller usable.
- captureSaveBarrier(owner, imageIDs, policy) -> barrier with exact owner/keys, operation UUID and result. Policies distinguish initiating close from observing pending cleanup. Review's observer must not silently initiate arbitrary edit-session closes. Consumers requiring current controls use an initiating gate.
- retryRecovery(key): reuse retained controller, deduplicate simultaneous retry clicks, refresh failure on rejection. A failed record is not converted into an empty successful barrier merely because its task finished.
- cancelIntent(intentID): cancels only the requested action. It does not cancel/remove an in-flight durability operation or forget its owner. A successful close may still finish after intent cancellation.

When multiple keys are involved, await/drain every already-started operation and retain every failure. Do not early-return and drop later cleanup tasks. Blocking one consumer must not erase another consumer's recovery record. Avoid treating a captured task list as the whole truth: a cancelled open can create a recovery entry while that task is being awaited. Before returning saved, inspect the same-key open/close generation and recovery registry again. If another same-key open could start during the gate, reserve those keys synchronously before awaiting, release reservation on every outcome, and prevent new opens/mutations through confirmed reader capture or operation completion as specified in section 7. Enqueueing a worker is not a completed handoff. This is a host admission guard, not a new native writer lease.

## 2. Intent, attempt and owner tokens are different

Maintain a monotonically replaced navigation intent UUID independent of save-attempt UUIDs and existing loadGeneration. Capture owner, target stable IDs, old workspace bookmark and an explicit action enum (navigate, folder URL, Layers request ID, output request, Agent request, quit). Prefer data payloads plus a central commit dispatcher over arbitrary long-lived closures.

A new navigation intent supersedes the old continuation but joins an existing same-session save attempt. Completion always updates the matching recovery record, even if its consumer is obsolete. It applies navigation only when intent UUID, captured owner, target identity and action-specific preconditions still match. An old result cannot clear a newer record or change a replacement library's status. Read-only Review preview retains its existing loadToken and reviewGeneration checks as consumer tokens; it must not supersede global navigation intent. Independent outputs/Agent actions use their own operation UUIDs, plus target reservations, rather than one global token that cancels unrelated work.

Keep Editing invalidates the blocked navigation, retains the failed session/pending changes, restores its bookmark and callbacks, and enables editing after any in-flight save settles. If close already succeeded, reopen only after that same result says saved; never reinstall a closed controller. Missing/deleted source: show retained photo-specific recovery and Retry; do not select a different item that reused the index or claim editing is possible. Do not replace a newer workspace merely because a stale recovery completed; restoring an offscreen owner's workspace is an explicit user action through the same navigation gate.

Retry Save resumes at most the latest still-valid captured action once, after all its keys pass. An invalid/cancelled intent remains cancelled even if saving later succeeds. Repeated failures remain visible. Initial UI has Retry Save and Keep Editing / Cancel; Quit has Cancel Quit. No Discard: recipe may already be published while XMP/index repair is pending. Never infer durability stage from an error string; absent native detail use neutral wording such as 'Could not finish saving; your editing session is retained.' No crash/power-loss recovery claim.

## 4. Cancelled opens, concurrency and termination

Open task completion cannot simply 'await close(); return' when owner/token changed. Keep the just-created controller and original owner locally, perform the A result-bearing cleanup, register blocked cleanup strongly on failure, then settle/remove the open ticket. Every same-key barrier waits for this settlement, including when there was no closing task at capture time. A weak AppModel capture must not be the sole owner of recovery: app-lifetime coordinator owns open tickets until settled; shutdown drains it before release. No detached task merely ignores a close error.

Quit uses applicationShouldTerminate -> terminateLater while an app-wide operation joins all active/recovery sessions and cancelled-open cleanup, across owners. Freeze new opens/navigation/mutations admitted by this coordinator while termination is pending. Reply once per termination request: true only when all relevant Develop gates and existing Document unsaved-close decisions succeed; false on failure/cancel, keeping recovery UI/window alive. Retry after a false reply starts a fresh termination request, not a second reply to the old one. Never discard a document to make Develop Quit pass. Last-window close must be intercepted before destruction with a window delegate/host coordinator that composes with current delegates; returning true from applicationShouldTerminateAfterLastWindowClosed is too late to preserve its recovery surface. Cancel Quit leaves application, owner and recovery available, and follows the explicit restoration protocol in section 7 if any Develop session already closed successfully before a later veto. Background unrelated jobs retain their existing shutdown contracts; this plan does not claim universal job durability.

## 7. Independent-review correction: precise lifecycle contracts

Revision request 58434c0c-9ea3-435c-b5f7-09b48036adf7 supersedes ambiguous wording in plan 0d4d3478. The caller-map baseline remains 447772f5. Current-main 2cf4df3e was fetched for this revision; source spot checks of DocumentWorkspace.close/discard and ExportController.start confirm the destructive-close and detached-output boundaries below. This is still documentation only, not an implemented API or acceptance claim.

### Shared durability versus per-caller dispatch

For a given (session identity, attemptID), store one immutable terminal DurabilityOutcome: saved or failed. Every joiner obtains that same outcome even if its UI request was cancelled or superseded. A cancelled waiter may stop awaiting, but cannot mutate the shared task/result. A new retry creates a new attemptID/result; it cannot rewrite an earlier failure. Per-caller dispatch separately returns performed, blockedBySave, cancelled, or superseded after checking its own intent/operation token. Example: callers A and B join attempt 1; A is superseded; attempt 1 succeeds. Both durability observations are saved, A dispatch is superseded, B may perform once. If attempt 1 fails, both observe the same failure; retained recovery does not depend on either caller's dispatch state.

### Quit decision order and late-veto restoration

Use a prepare/commit protocol for termination: capture the prior Develop destination/bookmark and strong owner first, freeze relevant input, collect Document Save/Cancel/Don't Save decisions without disposing Document controllers, perform requested Document saves, then request Develop closes. Existing DocumentWorkspace.close is NOT this preparation API: its save callback and Don't Save path call discard immediately. A and the assigned B Document owner must introduce a non-disposing decision adapter before composing it with termination. A Don't Save decision for a document is staged until the final termination commit and is not permission to discard Develop edits. Cancel during this preparation replies false without closing Develop. Frozen document generations invalidate stale preparation decisions if changes slip through.

Even with preparation ordered first, implement a late-veto path (Document revalidation failure, another termination participant veto, or user Cancel while Develop close completes). Reply false exactly once and retain the window. For each successfully closed Develop session, retain its owner/image and restoration bookmark until termination commits or restoration settles. Reopen the previously visible editing destination using that exact strong owner/image, never current AppModel.library by accident. Reattach normal frame/save/failure callbacks and refresh history/settings before enabling its controls. Restore only if termination token and destination identity still match; do not steal a newer workspace. With navigation frozen this should be the same workspace. Failed-close controllers remain alive and are reattached rather than reopened. Offscreen successfully closed records need not all reopen; their saved state is terminal, while the prior visible editor must become usable again.

If reopening fails (source removed or open error), keep a persistent restoration record and disabled affected controls with Retry Open; do not claim Cancel restored usable editing. Retrying Quit joins any restoration open/cleanup before closing again. Document controllers remain undisposed until final commit, so a later Develop failure cannot silently lose their unsaved work. Window-close cancellation uses the same restoration protocol without issuing an NSApplication termination reply. Deterministic tests inject successful Develop close followed by Document veto, prove original owner/image reopen and callbacks, and separately inject reopen failure then successful retry. Another test injects early Document Cancel and requires zero Develop close calls.

### Exactly-once openFolder request settlement

Give every openFolder invocation a FolderRequest record created synchronously: request UUID, URL, captured source owner, optional then callback, current phase, and terminal outcome slot. The app-lifetime coordinator owns it through settlement even when superseded; loadGeneration controls installation, not callback ownership. MainActor finishFolderRequest(id, outcome) atomically marks terminal and clears/takes the callback BEFORE calling user code, so callback reentry cannot finish it twice. Map installed or completed in-place rescan to loaded=true; cancelled, superseded, or terminal scan/open failure to loaded=false. Document this Bool mapping for existing tether/import callers, preferably retain richer internal outcomes.

A retryable save failure leaves the request blocked and callback pending while Retry/Keep Editing is presented. Retry continues that same request UUID and eventually settles once; Keep Editing/Cancel settles false. A newer folder request explicitly settles the old request false immediately, even if its non-cancellable scanner still runs. The old worker retains any resources it needs to drain but cannot install, alter status, or call then again. If terminal failure already delivered false, a later explicit retry is a NEW folder request with a new callback contract. An obsolete generation guard must settle or confirm prior settlement before returning, never silently drop then. On app cancellation/teardown settle outstanding callbacks false while coordinator is alive. Deterministic tests use suspended scan continuations: supersede A with B, observe A false once, finish B true once, then finish A late with no second callback; add callback-triggered reentry and blocked-save Retry versus Cancel cases.

### Concrete output reservation through capture, not dispatch

Define a MainActor OutputReservation record: UUID, strong EngineLibrary owner, frozen explicit image-ID set (resolve album/view membership), per-image host edit/save generation, immutable output settings/target payload, and phase saving -> reading -> captured/completed -> released. Acquire synchronously BEFORE awaiting save. Admission must reject/defer same-target host setting/mask edits, opens, Agent writes, and any other in-app recipe writer; guarding only UI enabled state is insufficient. Pre-existing writers drain before save/capture. Same catalog/image through a different EngineLibrary instance must also conflict using the existing source/catalog identity mapping; do not rely only on ObjectIdentifier for this admission check. If an uncovered writer cannot be gated, fail the protected output closed or explicitly leave this slice unaccepted; a host token does not prove a global native lease.

Hold this reservation while the shared save result is awaited, while the worker is enqueued, and while it reads recipes/pixels. On successful save, update the captured generation from that same operation, then transition to reading and pass the reservation token/immutable payload to the worker in one MainActor turn. The worker's terminal/capture callback returns the same token. No await or Task.detached scheduling implies capture occurred. The current exportBatch interface does not expose an all-target immutable recipe-capture acknowledgement, so the conservative initial implementation retains admission until exportBatch returns, including cancellation drain. Release early only after A adds and validates an explicit acknowledgement that ALL relevant inputs are captured immutably; it cannot mean just first-image capture in a batch.

For Print, hold through all thumbnail/composer inputs and print-image recipe reads, conservatively through operation completion when no narrower capture signal exists. Each sheet/watermark preview owns a finite read reservation; release on confirmed completion/failure, not just a cancel request. A displayed idle sheet holds no perpetual reservation: start acquires a fresh one for its current target/settings. If user changes a target while a preview worker is reading, invalidate its presentation token and request cancellation, but retain its reservation until the worker acknowledges drain. New overlapping work waits or reports busy; do not enqueue unbounded stale previews. Save failure before launching a worker can release the output admission record immediately while preserving independent recovery. Completion/failure/cancel cleanup is token-checked, exactly once, including stale UI consumers. Edits on unrelated targets remain available.

Proposed integration points: A's recovery/admission coordinator owns acquisition/release; ExportController.renderWatermarkPreview/start and PrintController.prepare/run accept captured owner/payload plus a reservation handle or execute inside a coordinator-owned operation wrapper. The wrapper, not a dismissible sheet, owns the handle until native/read work completes. No changes here authorize new leases or claim external-process mutation protection. Tests pause the worker between dispatch and first/all-target read, attempt conflicting edits and another-owner/same-source mutation, and assert rejection/defer plus unchanged captured generation; cancellation before read must not release until drain, while cancellation before worker launch releases once.
