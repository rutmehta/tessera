# WP M5-34 — Interactive text and shape editing: keystroke-to-frame under 16 ms on real photos

Measured by Machine B (B5-10, details in origin/wp/B5-10:tools/orchestrate/wp/B5-10/NEEDS.md — fetch it with `git show origin/wp/B5-10:tools/orchestrate/wp/B5-10/NEEDS.md`): on a 20 MP document, typing 274 px text at Fit gives 46 ms for the first key, **1072 ms median and 1844 ms p95** over 43 keys, growing with every glyph, because crates/compositor/src/render/live.rs re-rasterises every glyph into every tile on each edit (FFI call < 0.1 ms; Rust bench without a photo layer 74 ms median). Shape layers likely have the same issue.
Read crates/compositor/TEXT_VECTOR.md, crates/compositor/src/text_vector.rs, render/live.rs, render/exec.rs (live/tile scheduling, dirty rects, caches), render/cache.rs, crates/typography (shaping/layout/raster), crates/vector, COMPOSITOR.md §5 (revisions, stamps, caches) and §7 (dirty-rect compositing).
Deliver:
1. Text and shape layers rasterise once per (model revision, level, transform) into a cached layer raster (tiled, sparse), with a **glyph-run cache** (shaped runs + rasterised glyph coverage keyed by font/size/level) so an edit only re-shapes the affected paragraph and re-rasterises the glyphs whose positions changed.
2. An edit invalidates only the **damaged rect** (union of old and new bounds of the changed run/lines, plus effect halos if the layer has styles) instead of the whole layer; downstream compositing re-runs only for those tiles.
3. Same for shape layers: path edits invalidate the union of old/new stroke+fill bounds; the rasterised path is cached per level.
4. Bench (ignored test, log numbers) reproducing Machine B's case: 20 MP photo layer + a 274 px text layer, 43 sequential keystrokes at the Fit level (L2/L3 for a ~1400 px viewport): **median < 16 ms, p95 < 25 ms** per keystroke to a completed viewport frame on CPU; same for dragging a shape handle. Existing text/vector parity tests stay exact.
