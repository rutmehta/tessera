## Minimal proposed API

Keep an untrusted serializable descriptor separate from a privately constructible immutable `ValidatedPinnedSnapshot<'a>` borrowing its bytes/declarations. A validation method returns typed **current settings**, explicit source/process/recipe owner and requested-state hash; do not return a mutable/publicly constructible validated wrapper or permit unchecked Deserialize into it. Keep exact original recipe JSON bytes as the authority for byte round-trip; do not replace them with Recipe::to_json output. No path canonicalization, metadata/open, decoder or renderer calls belong here. Paths/suffix/route/digest/length are structurally parsed declarations, not evidence of files or rendering.

Require explicit raw top-level schema_version integer3 and a non-null valid image_id matching the descriptor's recipe_image_id before Recipe::from_json. Require explicit source_kind Raw and process_version Native/revision2 before defaulting; make the raw-presence policy explicit in tests. Require an actual settings object, with parsed geometry equal to default. Missing/old/future/mistyped headers must not become supported via migration/default values. [Recipe::from_json](/Users/rutmehta/Developer/tessera/crates/engine-api/src/recipe/mod.rs:423) normalizes selection and raises old schema numbers; [Recipe/default source/process](/Users/rutmehta/Developer/tessera/crates/engine-api/src/recipe/mod.rs:229) supply missing values. These conveniences are unsuitable as the header admission test.

## Duplicate and unknown keys

Before any serde_json::Value/header collapse, reject duplicate object members recursively, comparing decoded JSON key strings. This includes nested settings/history objects and escaped-equivalent keys such as `schema_\u0076ersion`; both conflicting value orders must fail. A Value parser can retain only one duplicate value, losing the evidence needed for unambiguous admission. Preserve the exact original bytes after parsing succeeds; duplicate rejection does not require canonicalizing them.

[DevelopSettings and nested settings](/Users/rutmehta/Developer/tessera/crates/engine-api/src/recipe/settings.rs:17) deserialize with defaults and generally ignore unknown members. Exact byte preservation alone does not prevent the typed requested-state hash from omitting a future setting. Reject unrecognized members anywhere within current `settings`, including array/enum payload objects; return a path to the rejected member. Do not change global Recipe/DevelopSettings deserialization behavior for this narrow descriptor API. One bounded implementation is comparing raw settings object key structure recursively against serialization of the successfully parsed typed settings, while preserving supported scalar/alias representations and checking array lengths; it must have nested enum/array/custom-profile tests. Alternatively use a strict field-tracking deserializer. Do not implement a shallow top-level settings whitelist only. Avoid silently treating raw unknown settings as harmless top-level recipe extensions.

Top-level unknown recipe metadata may remain preserved in exact bytes under an explicit policy, because this API validates current settings only. It must not claim that extensions are understood/rendered. [RecipeHash](/Users/rutmehta/Developer/tessera/crates/engine-api/src/recipe/mod.rs:293) excludes selection/history/IDs/unknown members. Compare the descriptor's claimed RecipeHash to the parsed recipe's actual RecipeHash, but call it **requested-state consistency**, not an exact-payload digest, signature, file verification or pixel-cache identity. Whitespace/member ordering, metadata and history can change without changing it. A separately computed domain-separated digest over exact raw bytes can identify the payload if desired; it is not a substitute for the semantic checks.

## History boundary — choose explicitly

For this minimal task, recommend **current-settings snapshot semantics**. History remains preserved and syntactically parsed, but is non-authoritative metadata: no replay selects or replaces pinned settings, no undo/edit behavior is exposed, and the result does not claim full Recipe validity. A history head that would replay another exposure must not override current settings/hash. Do not call the return value a fully validated Recipe. Selection normalization in the parser likewise must not overwrite the retained raw payload.

If the plan instead requires whole-recipe integrity, [Recipe::validate](/Users/rutmehta/Developer/tessera/crates/engine-api/src/recipe/mod.rs:405) must be called explicitly; from_json does not call it. Even that is not a complete strict-history guarantee: [History::validate](/Users/rutmehta/Developer/tessera/crates/engine-api/src/recipe/history.rs:281) checks limited structure; [state_at](/Users/rutmehta/Developer/tessera/crates/engine-api/src/recipe/history.rs:183) applies JSON patches then deserializes settings, which can drop unknown patch-created fields. Non-head branches are not all replayed. Strict history validation would need an additional explicit policy for history.base, patches, unknown targets and off-head branches, and is outside the proposed minimal snapshot boundary. Do not accidentally promise it by invoking one validation method.

## Minimal discriminating tests

- Exact payload bytes survive validation and descriptor round-trip, including whitespace/order and retained top-level metadata/history. Typed current settings/hash agree; no serialization rewrite is used.
- Explicit schema3/owner/Raw/Native2/default geometry positive control; missing/null/string/float/negative/old/future schema; missing/null/wrong image ID; omitted/wrong source/process members; nondefault geometry reject with typed errors before normalized admission.
- Duplicate schema/owner/process keys in both orders, nested settings duplicate and escaped-equivalent duplicate reject. Ordinary distinct nested keys remain accepted.
- Unknown current-settings top-level, nested field and array/enum payload members reject even when the supplied RecipeHash equals the parser's otherwise ignored-field hash. Retained allowed top-level extension is a distinct positive control.
- Changed requested setting or mismatched claimed hash rejects; same semantic settings with different whitespace/metadata retain exact differing bytes while sharing RecipeHash. Owner matching is checked separately because RecipeHash excludes IDs.
- History policy test: current settings remain authority regardless of a different replay head; no replay-derived substitution or full-history-validity claim. Malformed JSON/typed recipe input still fails parsing. If root chooses strict-history semantics instead, replace this test with strict replay/unknown-target cases before implementation.
- Declaration separation: syntactically valid descriptors can name a nonexistent path and arbitrary asset digest/length without any I/O; validator neither asserts asset existence nor proves route/suffix is decodable. Validated type cannot bypass checks through deserialization or mutate underlying data while borrowed.

No product render admission follows from any passing descriptor test. The constrained CPU feasibility probe is separate evidence, not an implementation of this validator or a reason to accept unknown settings/dependencies.

Specific implementation cases worth covering, without adding render admission:

1. An enum's accepted keys depend on its selected variant. `denoise.method={"kind":"off","model":{"id":"x","version":"1"}}` must reject the ignored extra model even though model belongs to another legitimate variant. Conversely a known Neural variant with a valid ModelRef is structurally admissible here; whether inference exists is a later renderer decision.
2. Recursive checking must descend into arrays and flattened mask payloads: `locals.adjustments[].components[]` flattens MaskKind into the component object; unknown keys there and inside a nested ModelRef must reject. Default-field omission remains accepted. Unknown enum tags themselves must retain typed decode failure rather than becoming defaults.
3. CameraProfileRef and LensProfileRef deliberately support legacy bare-string representations through custom untagged deserializers (settings.rs:322,476). If raw/canonical JSON key-shape comparison is used, known scalar-to-object normalization needs a deliberate narrow policy. Do not reject all typed-supported strings accidentally, nor use a blanket object/scalar mismatch escape that could hide unknown keys. A canonical full-object positive control plus each supported legacy-form control is useful.
4. **Finite raw JSON can overflow typed f32.** Locked serde_core1.0.229 `de/impls.rs:222,450` converts a visited f64 to f32 using `as`; serde_json1.0.151 Value numeric deserialization dispatches through number visitors. A value such as ±1e100 can therefore become nonfinite when settings are parsed from Value. serde_json1.0.151 `value/from.rs:30` serializes nonfinite f32 to Value::Null. A keys-only comparison and subsequent RecipeHash can miss this lossy transformation. Reject nonfinite typed settings or detect supplied-number→canonical-null transitions, including nested array values; add ±1e100 exposure tests. This is parser/hash integrity, not a restriction to slider ranges or renderer support. Ordinary finite representable numbers, including values beyond UI slider ranges, are not automatically rendering failures in this descriptor slice.
5. Header presence applies to process subfields too: `process_version={}`, missing family or missing revision must not inherit Native2 defaults. Schema must be an integer representation, not "3",3.0,null or a normalized old version. Duplicate escaped-equivalent keys in the outer descriptor and inner recipe payload both reject before Value collapse.
6. The wire's stored RecipeHash is mandatory and must be checked on reopen; constructors compute it from typed current settings. Exact payload bytes independently participate in requested-input identity, so whitespace/history/metadata changes alter identity while locator-only changes do not. Suffix normalization must be identical at construction and reopen; no I/O or content proof follows from a matching digest declaration.
