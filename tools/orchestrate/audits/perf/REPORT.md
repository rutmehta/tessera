# Tessera performance audit

## Executive finding

Tessera has a genuinely optimized engine fast path, but the application does not consistently preserve that advantage. The strongest source-backed causes of perceived slowness are synchronous work behind main-actor FFI calls, expensive thumbnail work before cache lookup, insufficient separation of interactive and background work, and document rendering paths that lose viewport locality or GPU residency. This is not evidence that the entire engine is unoptimized, or that replacing SwiftUI would solve the problem.

This is a diagnosis, not an implementation. No application/engine source was edited. Audit files and Swift build/test scratch are confined to `tools/orchestrate/audits/perf/`; Cargo uses the expressly requested `/Volumes/betterSSD/tessera-cache/target/audit-perf`. No app window was activated or driven.

### Why no app self-test or launch-time sample was taken

The requested background-only launch cannot be guaranteed with the current executable. `apps/mac/Sources/Tessera/App/TesseraApp.swift:90-108` sets regular activation policy and unconditionally calls `NSApp.activate()` during launch. `open -g` suppresses Launch Services activation, not a subsequent explicit activation by the app. `--front` is not a suppression switch; it adds `orderFrontRegardless()` at lines 173-175. No Tessera process was already running when checked. Therefore I did not launch it, run the app self-tests, or pretend to have an Instruments/sample capture. `xctrace` is installed, but that does not remove the foreground constraint. No binary patch, debugger injection, or source modification was used to bypass it.

Located self-tests include `--benchmark --stub 20000`, `--develop-selftest`, `--develop-panels-selftest`, `--document-selftest`, `--export-selftest`, and `TESSERA_SELFTEST_CROP` / `TESSERA_SELFTEST_UPRIGHT`. Their limits matter even when a future foreground-safe run is permitted:

- `AppModel.swift:1342-1365` sends exposure updates through the controller and reports **engine `renderMs`**, not event-to-display latency.
- `DevelopTools.swift:449-484` similarly reports engine frame times; line 470 explicitly flushes when the display link is paused by occlusion. Background presentation therefore is not equivalent to foreground dragging.
- Rust `FrameInfo.render_ms` starts at sink creation (`crates/tessera-ffi/src/develop.rs:1120,1402`), excluding input/JSON/preflight, time coalesced before sink creation, the main callback backlog, drawable acquisition, and actual display. It can include queue/serial-lock waiting after creation. It is neither pure shader time nor input-to-photon latency.
- Document `render_ms` starts at the first pending request and ends before Swift presentation (`crates/tessera-ffi/src/document/render.rs:359-365,424-433,515-538`). Do not compare these two readouts as if they had identical boundaries.
- Swift source search found correctness tests and timeout waits, not dedicated XCTest `measure`-style frame/scroll performance tests. Test execution duration is not UI frame latency.

No current launch-to-first-grid time, 1k/20k scroll FPS, first loupe presentation time, app slider input-to-display p95, or export-versus-interaction contention number is claimed.

## What already works, and what not to blame

### Launch and grid

Real folder opening is already detached: `AppModel.swift:332-356` calls `EngineLibrary.scan` outside main; `EngineLibrary.swift:110-138` opens the index/engine, scans and prepares initial rows there. Warm folder scanning still walks/stats source and sidecars (`crates/index/src/lib.rs:210-234`), but it is incorrect to label that entire scan a main-thread operation. The main-actor install/facets/focus path is the problem after the scan.

The grid is `NSCollectionView` with reusable layer-backed cells and arithmetic viewport layout, not SwiftUI views embedded in each cell. `ThumbnailCell.swift:32-39,57-65` cancels old subscriptions and validates represented identity; unchanged identity avoids rerequest. Layout work is bounded to intersecting rows in `UniformGridLayout.swift`. Thumbnail ImageIO decode is forced with `kCGImageSourceShouldCacheImmediately` on the worker in `ThumbnailLoader.swift:225-261`, before main delivery. The synthetic/local-file path uses ImageIO size-limited thumbnails; this does not establish that engine JPEG requests are equally cheap.

No `ObservableObject`/`@Published` broadcast architecture was found in the inspected app Sources. `@Observable`, `@ObservationIgnored`, scoped observation and explicit AppKit notifications already separate hot state. There can still be broad O(N) rebuilds and repeated work in notification handlers; a blanket “migrate to Observation” recommendation would be obsolete. Selection is not the same workload as passive scrolling.

Decoded cache budgets are 512 MiB thumbnails + 768 MiB previews (`ThumbnailLoader.swift:102-112`), before engine/GPU/source caches. These are caps, not measured resident memory. The cache uses `entries.min` to find each LRU victim under its lock (`:70-79`), O(C) per eviction; this is a secondary cache-pressure issue, not ranked ahead of the disk cache. There is no coordinated grid prefetch implementation; loupe prefetches next/previous/next+2 (`LoupeView.swift:90-93`). RAW requests have engine single-flight, Swift concurrent subscribers can still duplicate decode, and no global queue-length bound ties all work to visible cells.

RAW preview policy is not “render every file.” Unedited RAW prefers a sufficiently large embedded JPEG; absent/small previews use bilinear CPU rendering (`crates/previews/src/raw.rs:27-81`). Edited RAW uses recipe rendering on miss (`:92-127`). On a fresh engine, even a disk hit can first open RAW, read/hash original bytes, and decode embedded preview before lookup (`:27-44`). A live engine's `State::Ready` bypasses that via the request-key map (`crates/tessera-ffi/src/preview.rs:31-62`). That distinction is important for warm-session versus cold-relaunch tests.

### Loupe and Develop

The loupe shows cached preview first and avoids letting late thumbnails replace an engine frame. Source decode is full-resolution work off-main, while interactive rendering chooses a screen-appropriate pyramid level, adaptively coarsens expensive paths and refines on mouse-up to screen level, not automatically L0 (`develop.rs:383-410,1087-1104,1820-1834`). The display link coalesces settings and pauses while idle. The worker's `interactive_pending` mechanism renders latest state rather than repeatedly cancelling productive interactive frames.

The resident path really writes IOSurface-backed GPU textures. Normal resident photo frames do **not** copy full pixels through UniFFI. Histogram publication still requires GPU completion/readback, but only 4×256×4 bytes are read (`crates/pipeline-gpu/src/resident.rs:1600-1704`). Nonresident fallback collects/writes level pixels and computes histogram with fresh band threads (`develop.rs:1334-1382,1483-1551`). Local edits, lens blur/depth and some source/recipe combinations can fall back; a Metal backend label is not proof every recipe is resident.

Ordinary render callbacks are outside the session state lock, although the serial render/sink context remains held during publication; Swift dispatches asynchronously to main. This avoids a blanket worker→main synchronous deadlock. Main can still block in setters/histogram/history behind shared state, especially expensive preflight. Saving and explicit develop close are backgrounded; do not confuse Rust writer flush waits with a normal main-actor close wait.

### Layered documents and export

Engine tiles are 256×256. Document surface dimensions are rounded to 128-pixel increments and use a three-surface ring (`DocumentViewport.swift:274-294`); surface size is not evidence of limited GPU composition. Normal document GPU presentation imports IOSurface without full CPU readback, then waits for GPU completion on its worker (`document/render.rs:490-495`). Explicit `read_level` and lower `gpu_core::read_buffer` paths do copy to CPU, but the viewport normally does not call them. CPU fallback is a CPU producer into IOSurface, not a GPU readback.

Smart-filter handling is nuanced: normal FFI bakes are queued, old/unfiltered content can remain visible, prefixes and presented documents are cached. Lower compositor smart-source fallback can be layer-local; it is not always whole-document fallback. Direct layer styles are the separate whole-document fallback in hotspot 4. Channel visualization additionally requests CPU thumbnails up to 4096 pixels on main when components are hidden (`ChannelOverlay.swift:61-104`), not in the default all-components-visible mode.

Document rendering is request/coalescing driven and sleeps on a condition variable when idle, not a permanent 60 Hz compositor loop. Its Swift listener already coalesces latest frame, changed layers and history (`EngineDocumentBackend.swift:323-365`), unlike the photo Develop callback path. Some model/history refresh still happens both immediately after a command and after callbacks.

Library photo export is detached (`ExportController.swift:273-289`), serial source render with one overlapping encoder, and bounded GPU bands. It is not an unbounded file-per-thread export implementation. Full-resolution development before small Web output is an intentional accuracy default. Export uses its own cached GPU device/queue, not the engine document queue (`crates/export/src/gpu.rs:43,238-241`; `crates/pipeline-gpu/src/context.rs:45-52`). Contention is for physical GPU/unified-memory resources, not proof that a document wait drains the separate export queue.

## Root-cause themes

1. **Asynchronous-looking Swift does not make synchronous FFI asynchronous.** A `Task { @MainActor ... }` that sleeps and then calls SQL, JSON/history, rendering preflight or export still blocks the UI. Mutex waits import worker latency into UI latency.
2. **Cache access frequently performs the work the cache should avoid.** Original decode/hash precedes persistent-cache lookup; cache maintenance globally scans on each insertion. Correct reuse identity exists, but the cost model is wrong at scale.
3. **Small visible output does not ensure small computation.** Full-level GPU document calls, L0 style evaluation, automatic Upright and detail work escape the intended viewport/pyramid budget. Fallthrough from resident to CPU creates cliffs rather than gradual degradation.
4. **Priority without admission control is incomplete.** Running preview work cannot be preempted, obsolete open/decode continues, and document/detail/filter/export jobs live outside a single resource/pressure policy.
5. **The metrics stop before the user sees the result.** Engine readouts and checked-in baselines exclude critical app stages. A low render median is compatible with a slow app. Quantify main-thread occupancy and input-to-presentation age before optimizing another shader.
6. **Artifact ambiguity undermines diagnosis.** A stale local bundle, debug-default Swift packaging, copied FFI archive and a live/shared benchmark host can make measurements describe a different program or machine state than intended.

## Quick wins: each plausibly under one hour

These are narrow changes to schedule later, not patches made during this audit.

1. **Use item.groupID in cell suggested-best lookup**, with range/singleton/remap tests. Removes the concrete linear search in hotspot 10 without touching grid architecture.
2. **Make performance/release invocations explicit**: require `Support/make-app.sh release` in the performance runbook and print commit/config/archive digest next to results. Do not time the existing unproven bundle and label it current release.
3. **Add a nonactivating test launch flag** guarding `NSApp.activate()` and prohibit `--front` in the background audit command. Verify foreground application identity before/after. This unlocks safe measurements rather than asserting speedup.
4. **Skip install's empty All Photos search when matches are not being applied**, deferring optional facet refresh, provided sidebar counts remain correct. This removes redundant launch work, not the broader async catalog problem.
5. **Suppress per-frame detail requests during active gestures**, followed by a guaranteed settle refresh. Small scheduling change with a clear request-count oracle; do not disable detail permanently.
6. **Limit frame diagnostics to opt-in logging** in audit runs; existing flags are already conditional. Check run environment rather than spending time deleting non-hot error logs.
7. **Correct benchmark labels/documentation** to say “engine sink time,” record pyramid level/backend and add “not app input-to-display.” This prevents false passes; it is not itself a runtime optimization.

Do not use “increase every pool,” “disable color management,” “force GPU for every recipe,” “export lower resolution by default,” or “rewrite the grid in SwiftUI” as quick wins. They either worsen contention, change output, or discard existing performance work.
